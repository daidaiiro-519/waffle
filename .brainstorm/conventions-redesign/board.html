Q1

規約と仕様の境界は、どこか

新しい論点

この Skill が持ってよいものと、持ってはいけないものを、何で分けるか。

v2直した答え
決定規約は、仕様を知らないまま書けるものに限ります。理由は、依存の向きです ── 仕様は外から注入されるもので、規約はそれを受け取る側です。規約が仕様を知ると向きが逆転し、プロダクトが変わるたびに規約が動きます。物差しは変わりません ── 軸の値だけから書けるか。

規約から仕様へ向かう矢印はありません。規約が与えるのはどう書くかだけで、何を作るかは仕様が与えます。

なぜ依存の向きか ・ 落とした案 4件

なぜ依存の向きが理由なのか

規約は、仕様を受け取って実装へ落とすときの「どう書くか」を与える。仕様は SpecSchema が実装できる高さまで落として渡すもので、外から注入される。受け取る側が渡す側を知ると、向きが逆転する ── そのとき規約は、プロダクトの数だけ枝分かれし、プロダクトが変わるたびに動く。共有が壊れるのは、その結果にすぎない。

そこへ至った道筋

  1. 概念実装で「正しい要求に、1行の JSON と終了コード 0 を返す」と書いた
  2. これはその道具の約束であって、規約ではないと気づいた
  3. いったん「形態ごと外す」と判断したが、それは行き過ぎだった ── 捨てるべきは文書であって、軸ではない
  4. 分かれ目を軸の値だけで書けるかに定めたが、理由を「共有が壊れるから」と置いた
  5. それは結果であって理由ではない ── 本当の理由は、仕様が外から注入されるという向きである

落とした案と、落とした理由

案何が壊れるか
規約が、プロダクトの事情まで見て書かれる向きが逆転する ── プロダクトが変わるたびに規約が動き、腐る
境界を決めず、書きたいものを書く同じことが起きる ── どこまでが仕様かを言えなくなる
振る舞いを丸ごと外す形態の作法まで失う ── 終了コードの使い方は、仕様を知らずに書ける
仕様と規約を1つの場所に混ぜる受け取る側と渡す側が同じ場所になる

形態とは、何か

形態の値は、何として作るか

  cli ・ tui ・ webapp ・ backend-api ・ batch ・ mcp-server ・ hook …

「何のために作るか」ではない
  在庫を管理するため ／ 社内向け　　→　仕様の側。軸ではない

それぞれが、その形が持つ不変の概念を持っている

  backend-api　呼び出し元起因とこちら起因の区分 ／ 冪等な操作
  cli　　　　　引数と終了コード ／ 標準出力は結果、標準エラーは診断
  batch　　　　1件の失敗で全体を止めるか、飛ばして続けるか ／ 再実行
  webapp　　　外から来た入力は、内へ渡す前に検証する
  mcp-server　手続きの一覧を返す ／ 知らない手続きは失敗として返す

この不変の概念は、外部に出どころがある
  RFC ・ POSIX の慣習 ・ MCP の仕様 ・ その形の定石
  → 書き写さない。指す

粒度は、作る形そのものです。「無いものを求められたときの返し方」のような個別の場面まで砕くと、それはその形の不変の概念ではなく、一場面での使い方になります。
利用者と接するかどうかは問いません ── バッチもバックエンド API も利用者とは接しませんが、外から見える形は持っています。

だから、こちらが持つのは選択だけ

3つの軸すべてで、同じ形になる

  言語　　　　　公式　Go には error という型がある　　　　　書かない
  　　　　　　　　　選択　失敗は返り値で返し、panic で流さない　書く

  アーキテクチャ　原典　1つのポートに複数のアダプターが差さる　　書かない
  　　　　　　　　　選択　アダプターどうしは、互いを参照しない　　　書く

  形態　　　　　公式　404 は資源が無いことを表す　　　　　　　書かない
  　　　　　　　　　選択　呼び出し元起因は 400 と 404 の2つに留め、
  　　　　　　　　　　　　独自の区分を足さない　　　　　　　　　　　書く
何を持つか腐るかなぜ
公式や原典の内容を、こちらへ書き写す腐る向こうが動けば、こちらは黙って古くなる
出典（リンク ・ 引用した文字列 ・ 取得日）腐らないが動いたら分かる引用した文字列を、原文に当てられる
その出典のもとで、私たちが決めた選択腐らない私たちが決めたことなので、私たちが変えない限り有効である

言語の内容をこちらで管理すれば、必ず腐ります。アーキテクチャも形態も同じです ── どれも外に出どころがあり、こちらは追いつけません。
出典を指し、その上で私たちが決めたことだけを書けば、腐るのは出典との対応だけになります ── そしてそれは、引用した文字列で見つけられます。

宣言が持つのは、これだけです。「この宣言に効く規約はこの何本」という一覧は持ちません ── 効く規約は、選んだ値と規約の適用条件をそのつど突き合わせて求めます。

なぜ1本か ・ 落とした案 5件

なぜ宣言は1本の文書か

選択どうしは互いの候補を狭める ── 形態を選ぶとアーキの候補が狭まり、アーキと言語で置き方が決まる。 一緒にしか決められないものは、1本の文書になる（文書＝一緒に決まるもののまとまり）。 承認も一度で済む ── 「この構成でいく」という1つの決定である。

なぜ形態だけが複数になるか

言語やアーキテクチャを2つ選ぶなら、それは別の成果物である ── 宣言が2つになる。 形態は違う ── 1つの成果物が、端末からも道具からも使える形をとれる。 どちらの形も同じ実行ファイルが持つので、宣言は1つのままである。
当て方は変わらない ── その値を持っているかで当てる。

落とした案と、落とした理由

案何が壊れるか
軸ごとに文書を割る名前に宣言を入れることになる ── choice-cli-language のようになり、宣言ごとの一式を管理する形に戻る
宣言でフォルダを切る文書がすでに言っていることを二重に持つ ── しかもフォルダは機械で引けない
効く規約の一覧を、宣言に持たせる保存した一覧が古くなる ── 規約が1件増えるたびに直して回る
形態ごとに宣言を分ける選択が丸ごと重複する ── 言語もアーキも道具も、理由まで同じものが並ぶ
主題を適用条件に入れる仕様が規約を動かすようになる ── 依存の向きが逆転する（Q1）

この決定を採ると、引き受けること

宣言の文書に、機械が読む節を1つ置くことになります（「この選択がつくる適用条件」）── ほかの節にも軸の値が文中に出てくるので、拾う場所を限る必要があります。
複数の値をとれるのは形態だけと決めておく必要があります ── 言語やアーキが2つ現れたら、それは宣言が2つです。
そして条件が当たるのは、宣言の全体です。form = cli の規約は、実際には成果物のうち端末から呼ばれる部分にだけ効きますが、どの部分に効くかを機械には言えません ── 適用範囲の欄で補いますが、それは文章なので絞り込みには使えません。
同じ条件で違う選択をしたい相手が2つあると、書けません。同じ言語を選んだ2つのチームが別の流儀を採りたいとき、写しを作らない設計なので分けられません ── 相手を条件に足すと、Q1 の境界と衝突します。

Q4

CodingSchema と coding-skills は、それぞれ何を持つか

新しい論点

型と Skill の分担はどこにあるか。

決定CodingSchema は「形」を、coding-skills は「使い方」を持ちます。 型は軸の一覧 ・ 文書の種類と背骨 ・ 適用条件の欄 ・ 出典の欄を定め、Skill は物差し ・ 手順 ・ ガードレール ・ 道具を持ちます。 道具は型に依ります ── 欄が無ければ、絞ることも当てることもできません。 そしてどちらも判断は持ちません。

この決定を採ると、こうなる

持ち物の分担

CodingSchema が定めるもの　── 形
  軸の一覧　　言語 ／ アーキテクチャ ／ 形態
  　　　　　　　　適用条件に書ける軸名を定める。値は自由（go も rust も、型を変えずに書ける）
  文書の種類　　選択 ／ 規則 ／ 構造 ／ 振る舞い
  種類ごとの背骨　どの節を持つか
  適用条件の欄　軸の値の組を書く場所
  出典の欄　　　リンク ・ 引用した文字列 ・ 取得日
  芯　　　　　　id ・ 種類 ・ 主題 ・ まとまる理由 ・ 承認

coding-skills が定めるもの　── 使い方
  境界の物差し　軸の値だけから書けるか
  軸の物差し　　それが無いと、その種類が1件も書けないか
  手順　　　　　宣言する → 規約を書く → 重なりを見る → 差分を見る
  ガードレール　固有名を書かない ／ 写しを作らない ／ 公式を書き写さない
  道具　　　　　絞る ・ 並べる ・ 差分を出す ・ 出典を原文に当てる

どちらも持たないもの　── 判断
  矛盾かどうか ／ 消すかどうか ／ 承認　　→　人
CodingSchemacoding-skills
何であるか文書の型使い方の手順とガードレール
読む相手機械（検査 ・ 描画 ・ 絞り込み）人と AI
軸について持つもの一覧　── どの軸名が書けるか物差し　── 何が軸になるか
変わるとき軸か種類が増えたとき ／ 節が増減したとき決め方が変わるとき（物差しが変わる）
守る相手abstract schema の契約この盤の決着

なぜこの分け方か ・ 落とした案 4件

なぜこの分け方か

型は機械が読むもので、Skill は人と AI が読むものである。 読む相手が違えば、変わる理由も違う ── 節が1つ増えるのは型の話で、物差しが変わるのは Skill の話である。 混ぜると、片方を直したいときにもう片方も動かすことになる。

道具が、型に依る理由

形が揃っているから、道具が働く

  適用条件の欄があるから　→　絞れる ・ 重なりを並べられる ・ 差分を出せる
  出典の欄があるから　　　→　引用した文字列を原文に当てられる
  種類の欄があるから　　　→　背骨が揃っているかを検査できる
  軸の一覧があるから　　　→　知らない軸名で書かれた条件を、その場で弾ける

欄が無ければ、道具は書けない
  だから道具は Skill の持ち物ではなく、型に依っている

道具はどちらの持ち物か

道具（絞る ・ 並べる ・ 差分を出す ・ 出典を当てる）は、 型が持つ欄が無ければ書けない。だから型に依る。 ただしいつ呼ぶか（書くとき ・ 選ぶとき）は Skill が決める ── 呼ぶ側と、依る先が違う。

落とした案と、落とした理由

案何が壊れるか
手順を型に持たせる物差しが変わるたびに型が動く ── 文書の形は変わっていないのに、版が上がる
文書の形を Skill に持たせる機械が検査できない ── 形の定めが、人向けの文章の中にしかない
道具を Skill だけの持ち物にする欄が変わったときに気づけない ── 道具は欄に依っているので、型と一緒に動く必要がある
判断を、どちらかに持たせる機械が見られるのは形だけである ── 矛盾かどうかは読まないと分からない

この決定を採ると、引き受けること

型と Skill は、別々に版が上がります。物差しを直しても型は動かず、節を足しても物差しは動きません。
道具は、型の欄が変わったら一緒に直すことになります ── 依っているのは Skill ではなく欄だからです。
ただし、道具は思ったより少なくて済みます ── 絞る ・ 並べる ・ 差分を出す ・ 効かないものを見つけるは、どれも適用条件で絞るの言い換えなので、汎用の問い合わせ1つで書けます。出典を原文に当てるのは、すでに別の Skill が持っています ── 作り直しません。

Q5

置き場所を、どう切るか

持ち越した決着の見直し

「正本は1段。フォルダを切らない」と決めていたが、種類で切ってはいけない理由は何か。

決定切ってよいのは、文書がその値を1つしか持たないものだけです。 文書の種類は1つしか持たないので切れます ── declarations/ ・ rules/ ・ structures/ ・ behaviors/。選択も含めて4つとも切ります ── 入口だから上に置く、という例外を作らない。入口は種類で見つかるからです。 軸は複数もつことがあるので切れません（`language ＋ architecture` の規則は、どちらにも置けない）。 そして機械は置き場所を見ません ── 前置きの種類と適用条件で判断するので、1段に置いても同じ一式が出ます。 フォルダは人が見つけるためのものです。

この決定を採ると、こうなる

.coding/
  declarations/       選択（宣言）
  rules/              規則
  structures/         構造
  behaviors/          振る舞い

切ってよいかの物差し

物差し ── その値を、文書が1つしか持たないか

  文書の種類　1つしか持たない　　→　置き場所が一意に決まる　切ってよい
      declarations/ ／ rules/ ／ structures/ ／ behaviors/　── 4つとも切る。例外を作らない

  軸　　　　　複数もつことがある　→　置き場所が決まらない　　切れない
      「Go ・ hexagonal における置き場所」は
      language でも architecture でもあるので、どちらにも置けない

  主題　　　　形を決めないもの　　→　種類とずれる　　　　　　切らない

機械と人で、見るものが違う

機械は前置きの種類と適用条件で判断する。置き場所を見ない
  → 1段に置いても、フォルダで切っても、同じ一式が出る

フォルダは人が見つけるためにある
  → だから種類 ・ 置き場所 ・ id の頭の3つが揃っていなければならない
     揃っていないと、人がフォルダで探して見つからない

揃っているかは検査が見る
  規則を structures/ へ置くと　→　「規則 は rules/ に置く」と出る

置き場所を変えても、集まり方は変わりません。 実際に1段へ移して同じ一式が出ることと、規則を structures/ へ置くと検査が捕まえることを、確かめました。

持ち越した決着との関係 ・ 落とした案 4件

持ち越した決着は、何を却下していたのか

「フォルダを切らない」は軸で切ることを却下していた。 理由は「宣言している欄と二重になる」と書いていたが、それは浅かった ── 本当の理由は、1つの文書が複数の軸の値を持つので、置き場所が一意に決まらないことである。 文書の種類は1つしか持たないので、この理由は当たらない。

二重に持つことにならないか

なる。種類は前置きにも書かれ、置き場所にも現れる。 ただし機械は前置きだけを見るので、置き場所が古くなっても集まり方は壊れない。 そして食い違いは検査が捕まえる ── 腐りを防ぐのではなく、見つかる形にしておくという扱い方（Q8 の持ち越し）と同じである。

落とした案と、落とした理由

案何が壊れるか
1段のままにする人が探せない ── 画面がまだ無いので、フォルダの並びが唯一の入口である
軸で切る置き場所が一意に決まらない ── 複数の軸の値を持つ規約を、どこにも置けない
機械にも置き場所を見せる置き場所が意味を持ってしまう ── 動かすと集まり方が変わり、前置きと二重の正本になる
置き場所と種類の食い違いを、検査で見ない人が探して見つからない ── 機械は困らないが、人はフォルダで探す

この決定を採ると、引き受けること

種類 ・ 置き場所 ・ id の頭の3つを、揃えることになります。検査が見ますが、揃える手間はあります。
種類が増えたら、フォルダも増えます ── 種類は閉じていないので（Q2）、そのときに1つ増えます。
