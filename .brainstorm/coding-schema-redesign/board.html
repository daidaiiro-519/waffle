新しいブレスト ／ CodingSchema と coding-skills

Coding を組み直す

CodingSchema と coding-skills は1つの主題である。schema が形を定め、Skill がそれを使う ── 片方だけを組み直すことはできないので、この回では両方を扱う。
CodingSchema は concrete schema であり、守るべきは abstract schema の共通契約である。SpecSchema も concrete なので、そこから引くのは兄弟から借りることになる。
論点16 は、いまの実装（規約が文書の単位）を前提にした決着だった。新しい概念では前提が変わるので、どこを引き継ぎ、どこを変えるかを仕分ける。

この回が扱う範囲

層何を持つかこの回での扱い
abstract schema全部の型が共通で持つ契約 ── ID ・ 状態 ・ 変更の記録 ・ 引き方 ・ 検査の名前 根拠にする。CodingSchema はこれを守る
concrete schema型ごとの構造。CodingSchema ・ SpecSchema ・ ADR ほか CodingSchema がこの回の対象（それを使う coding-skills も一緒に扱う）。SpecSchema は兄弟なので根拠にしない
document実際の文書1本結果として決まる

今日の誤りは、ここを踏み外したことだった。 CodingSchema を組むのに、SpecSchema の決着（文脈の地図 ・ 索引 ・ 業務の層）を引いていた ── 兄弟から借りていた。引くべきは abstract の契約と、Coding 自身の決着（論点16）である。

CodingSchema の概念図

概念何であるかどこから来るか
規則守るべき言明1件。ID ・ 言明 ・ 検証方法 ・ 出典 ・ 適用条件 芯の4つは論点16 の決着。適用条件はここで足す
適用条件その規則がどこで効くか。軸の値で書く。空なら、どの場面でも効く 新しく足す
軸言語 ・ アーキ ・ 用途。適用条件が値をとる次元論点16 の決着
層軸の組。保存せず、条件から計算して求める論点16 の決定（あらかじめ並べない）
文書一緒に決まる規則のまとまり。承認の単位 変える。論点16 では「規約（種 × 層）」だった
決めごとの種類規則 ・ 構造 ・ 道具 ・ テストの4つ。文書の背骨を決めるQ6 で新しく立てる
種別コーディング ・ テスト ・ アーキ ・ 技術スタック。前置きの欄で横断に使う 論点16 の決着
abstract の契約ID ・ 種類 ・ 版 ・ 状態。10 の型すべてが必須で持っている 実測 ── 各 schema の最新版を数えた（2026-09-09）

abstract の契約は、実際に測って確認した。 10 の concrete schema すべてが必須で持つのは documentId ・ documentType ・ schemaRef ・ content の4つで、status は8つが持つ。
ただし、決着で abstract が持つとした「変更の記録 ・ 引き方 ・ 検査の名前」は、まだどの schema にも無い ── 決めたが実装されていない。CodingSchema を組むときに、そこを当てにはできない。

1つの目的から、何ができあがるか

ここが結論です。目的を宣言すると、選択が決まり、その組に適用条件が合う決めごとが、すでに書かれているものの中から集まります。書くのは選択の記録だけで、決めごとは1件しか無く、宣言ごとに写しません ── 下は「バックエンド API を Rust ・ hexagonal で作る」と宣言したときの一式です。

宣言は、一式を持たない

宣言が持つのは選択だけです。効く決めごとは、選んだ値と決めごとの適用条件を突き合わせて、そのつど求めます。

宣言が持つもの
  用途 = backend-api ／ アーキ = hexagonal ／ 言語 = rust ／ 実行環境 = resident
  道具 = rustfmt ・ clippy ・ cargo test ・ thiserror
  ── これだけ。5本の選択の記録に書いてある

宣言が持たないもの
  「この宣言に効く決めごとは、この9本」という一覧
  ── 保存すると古くなる。決めごとが1件増えたとき、直して回ることになる

一式は、そのつど突き合わせて求める
  宣言の値　　　 language = rust
  決めごとの条件 language = rust
  　　　　　　　 → 合うので、この宣言に効く
何が起きたとき一式はどうなるか誰が直すか
決めごとを1件増やした条件が合う宣言すべてに、自動で入る誰も直さない
決めごとの条件を狭めた合わなくなった宣言から、自動で外れる誰も直さない
宣言の選択を変えた（rust → go）効く決めごとが入れ替わる選択の記録を1本直す

「この宣言にはこの14本」と保存すると、保存した一覧が古くなります。フォルダを生成して置く案を落としたのと同じ理由です（Q2）── 置くものが無ければ、古くなりません。

「どの目的でも同じ」とは言っていない

適用条件は「どこで効くか」を書く欄です。目的に依存するなら、その条件を書けばよい ── 無理にまとめません。

主題は同じ「失敗の運び方」でも、条件が違えば別の文書になる

  language = rust
      回復可能な失敗は Result で返す
      言語の仕組みから出ている。どの目的でも成り立つ

  language = rust ＋ purpose = backend-api
      失敗は、応答の状態コードへ写す
      呼び出し元が居るときだけ成り立つ

  language = rust ＋ purpose = batch
      1件が失敗したとき、飛ばして続けるか止めるかを決めておく
      まとめて処理するときだけ成り立つ

まとめているのではない。条件を書いているだけである
条件の広さ効く範囲例
空すべての宣言ID を持つ、承認を受ける
language だけその言語を選んだ宣言すべて回復可能な失敗は Result で返す
language ＋ purposeその組を選んだ宣言だけ失敗を応答の状態コードへ写す
language ＋ architectureその組を選んだ宣言だけ単体テストは対象と同じファイルに置く

反例が出たら、条件が広すぎたということです。「API では成り立つが、バッチでは成り立たない」決めごとが language = rust だけの条件で書かれていたら、それは条件の書き誤りです ── 直し方は、条件に purpose を足して2件に割ることです。
共有される範囲は、条件の広さで決まります。広く書けば多くの宣言に効き、狭く書けばその組だけに効く ── どちらも同じ仕組みで、まとめる作業も、写す作業も要りません。

まだ崩れうるところ

問いいまの答え崩れうる点
ある目的だけ、共有の決めごとから外れたいときは選択を変える（別の言語 ・ 別のアーキを選ぶ）選択を変えずに、1件だけ外したいという要求が出たときに、答えが無い。目的を軸に足せば書けるが、軸が1つ増える
共有の決めごとを直すと、全部の目的に効くそのとおり。だから直す場所は1か所ある目的で困る変更を、誰が止めるかを決めていない ── 承認は文書単位だが、影響は目的をまたぐ

どちらも「共有すること」の裏側です。写しを作らない代わりに、1本の文書が複数の目的へ同時に効きます。

# Rust における失敗の運び方

## 概要

回復可能な失敗を値として運び、回復不能な失敗だけをパニックに任せる。

## 用語と区分

| 区分 | 意味 | 表し方 | 呼び出し元の扱い |
|---|---|---|---|
| 回復できる失敗 | 入力や外部の状態が、想定の範囲で崩れた | `Result::Err` | 受け取って分岐する |
| 回復できない失敗 | 前提そのものが壊れている | `panic!` | 受け取らない。プロセスが終わる |
| 想定していない状態 | 実装の誤り | `unreachable!` | 開発時に落として気づく |

## 規則一覧

| ID | 言明 | 水準 | 適用範囲 |
|---|---|---|---|
| RS-ERR-01 | 回復可能な失敗は `Result` で返し、`panic!` で流さない | 必須 | 公開関数すべて |
| RS-ERR-02 | 失敗型は `Error` ・ `Send` ・ `Sync` を実装する | 必須 | 公開関数の失敗型 |
| RS-ERR-03 | `Result` を捨てない。捨てる場合は理由を残す | 必須 | 全体 |
| RS-ERR-04 | `()` を失敗型にしない。運ぶ値が無くても、名前のある型を作る | 必須 | 公開関数の失敗型 |

## 規則の詳細

### RS-ERR-01　回復可能な失敗は `Result` で返し、`panic!` で流さない

| 項目 | 内容 |
|---|---|
| 水準 | 必須 |
| 適用範囲 | 公開関数すべて |
| 選んだ理由 | 呼び出し側が回復の可否を選べなくなり、失敗が制御の外へ出る |
| 検証方法 | `cargo clippy -- -D clippy::unwrap_used -D clippy::expect_used` |
| 違反の見つかり方 | その関数を読むと分かる。`panic!` で流している |

### RS-ERR-02　失敗型は `Error` ・ `Send` ・ `Sync` を実装する

| 項目 | 内容 |
|---|---|
| 水準 | 必須 |
| 適用範囲 | 公開関数の失敗型 |
| 選んだ理由 | 呼び出し側がスレッドをまたいで運べなくなる |
| 検証方法 | 型に対する静的な検査 |
| 違反の見つかり方 | その型の定義を読むと分かる |

## 適用範囲外

- 失敗をどう記録するか（記録の宛先・形式）
- 失敗を利用者へどう見せるか

|---|---|---|

| `Result` の取りこぼしの検出 | `clippy`（道具の選択） | 機械で見られるため |

# 依存の向きと反転

## 概要

依存は外側から内側へ向き、内側が外側を必要とするときだけ反転させる。

## 用語と区分

| 語 | 意味 |
|---|---|
| 一次のポート | 向こうが会話を始める側の、会話の形 |
| 二次のポート | 内側が外側へ求める機能の宣言 |

## 構成要素

| 要素 | 責務 | 知ってよいもの | 知ってはならないもの |
|---|---|---|---|
| 内側 | 業務の判断を持つ。入出力をしない | 言語の標準機能 | 外部技術、外側の要素 |
| 外側 | 外部との入出力を持つ | 内側、外部技術 | ほかの外側 |
| 一次のポート | 向こうが始める会話の形 | 内側 | 実装技術 |
| 二次のポート | 内側が外側へ求める機能 | 内側 | 実装技術 |

## 依存の許可

| 参照元 \ 参照先 | 内側 | 外側 | 一次のポート | 二次のポート |
|---|---|---|---|---|
| 内側 | 可 | 不可 | 可 | 可 |
| 外側 | 可 | 不可 | 可 | 可（満たす） |
| 一次のポート | 可 | 不可 | ─ | 不可 |

フォルダ構成とテスト配置は、構造ではなく規則

物差しは1つ ── 違反は、どこを見れば分かるか

  「単体テストは、対象と同じファイルに置く」
      → そのファイルを1つ見れば分かる　　　　規則

  「アダプターは adapter/ の下に置く」
      → そのファイルの場所を見れば分かる　　　規則

  「アダプターどうしは、互いを参照しない」
      → 2つのアダプターの間を辿らないと分からない　構造

  「内側は、外側を知ってはならない」
      → 依存の向きを辿らないと分からない　　　構造

置き場所は、1か所を見れば分かります。だから規則です。関係は、2か所以上を辿らないと分かりません ── そこが分かれ目です。
ただし、配置の規則は構造を守るための手段として置かれます。Rust でクレートを分けるのも、Go でパッケージを分けるのも、依存の向きという構造を、言語の仕組みで守らせるためです ── 規則が構造を支える、という関係はありますが、同じ種類ではありません。

この軸を変えると何が変わるか主に動く種類

軸ごとに、主に動く種類があります。直交しているのは「どの升も在りうる」という意味であって、「どの升も同じくらい埋まる」という意味ではありません。

振る舞いは、用途と実行環境にかかる

振る舞いは外から観測できるものである。
だから、観測面を決める軸にしかかからない。

  用途　　　　何を作るかが、観測面を決める

      backend-api　HTTP の応答と状態コード
      mcp-server　 JSON-RPC の応答

  実行環境　　動き続け方が、観測面を変える

言語 ・ アーキテクチャ ・ 道具は、振る舞いを変えない
  Rust で書こうが Go で書こうが、hook が返すのは
  1行の JSON と終了コード 0 である

これは反証できる言い方にしてあります。言語を変えて振る舞いが変わるなら、それは振る舞いの決めごとではなく、内部の作りが観測面へ漏れているということです ── そのときは、漏れているほうを直します。
いま「テスト」と呼ばれてきた文書のうち、言語やアーキにかかっていたものが規則と構造へ移ったのは、この理由からです（Q6）。

Q10

CodingSchema は、何ができなければならないか

新しい論点　── Coding

ここまでの決定は、どんな能力を要求しているか。そのうち、CodingSchema が持つべきものはどれか。

決定7つです。 適用条件で絞る ／ 重なりを並べる ／ 選択の差分を出す ／ 効かない決めごとを見つける ／ 出典を原文に当てる ／ 種類ごとの形を検査する ／ 描く ・ 落とす。 どれも「適用条件」と「軸」を知らないとできないので、abstract schema には置けません ── そこは ID ・ 種類 ・ 版 ・ 状態 ・ 検査の名前しか知らないからです。 そして判断は1つも持ちません。矛盾かどうか・消すかどうか・承認は、人に委ねます。

7つのうち5つは、同じ1つの操作でできています ── 適用条件で絞ること。 絞る相手が、宣言（画面）／書いている決めごと（重なり）／変える前と後（差分）／どの選択にも当たらないもの（効かない）と違うだけです。 新しい仕組みは、ほとんど要りません。

なぜ abstract に置けないか ・ 落とした案 4件

なぜ abstract schema に置けないか

abstract schema が知っているのは、どの型でも共通に持つものだけです ── ID ・ 種類 ・ 版 ・ 状態 ・ 検査の名前。 適用条件も軸も、そこには無いので、絞ることも重なりを見ることもできません。

能力要る欄abstract が持つか
適用条件で絞る適用条件持たない
重なりを並べる適用条件持たない
出典を原文に当てる引用文字列 ・ 取得日持たない
種類ごとの形を検査する文書の種類（この4値）種類という欄は持つが、値は知らない

abstract が持つのは「検査の名前」までです。 中身は CodingSchema が持ち、abstract はそれを名前で指します。

そこへ至った道筋

  1. Q9 まででいくつも「見せる」と決めたので、それを誰が持つかを問うた
  2. 能力を1つずつ書き出し、要る欄を並べた
  3. どれも適用条件か軸か出典を要る ── いずれも abstract には無い
  4. よってCodingSchema が持つ。abstract は名前で指すだけになる
  5. そのうえで判断を持たせないと決めた ── 機械が見られるのは形だけである
