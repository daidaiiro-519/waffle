# 出典 ── 規則は、何を根拠に書けるか

## 概要

**出典を書けない規則は、規則として置けない。**
「誰かがそう決めた」しか言えないものは、他のプロジェクトへ持って行けない。

## 認める出典

| 種類 | 何を指すか | 添えるもの |
|---|---|---|
| 規格 | 言語仕様、RFC、プロトコルの仕様 | 版と、何を裏づけるか |
| 文献 | 公式ガイド、公式リファレンス、確立した文献 | 落とした日と、何を裏づけるか |
| 実測 | 自分で数えた記録 | 測った対象、件数、測った日 |

## 認めない出典

| 種類 | なぜ認めないか |
|---|---|
| このプロジェクトの決めごと | 場面が変われば成り立たない** ── 入れた時点で、どの場面でも同じ答えを返すという前提が壊れる** |
| 要約されたもの | 言い換えた時点で、原典とは別のものになる |
| 出典を持たない経験則 | 正しいかもしれないが、確かめる先が無い |
| 独自の解釈 | **原典と衝突しうる。**しかも衝突していることに誰も気づけない |

**原典を持つ規則どうしは、基本的に衝突しない。**
どれも同じ唯一の正を指しているためである。
**衝突は、独自の解釈が混ざったところで起きる。**

実際に起きたこと（2026-09-06）──
`RH-TP-03`「出力ポートの偽物は `adapter` へ置かない」を置いていた。
根拠は「偽物は内側のテストのための道具であり、外側の実装ではない」と書いてあった。
ヘキサゴナルの原典を読むと、逆のことが書かれていた ──
`an adapter to a "mock" database` と、**偽物をアダプタの一種として数えている。**
出典を持たない規則は、こうして原典と反対のことを言ったまま残る。

## 原典が見つからないとき

**理由を探し続けない。**
出典を持たない言明は規則ではない、という定めをそのまま適用する。

| 状態 | どうするか |
|---|---|
| 実績・実測が在る | **実測として書く。**測った対象・件数・測った日を添える |
| 規格も文献も実測も無い | **規則にしない。**「委譲する判断」へ移し、下の層が決める |

**「決めないことも、決定である。」**（`authoring.md`）
委譲すると宣言してあれば、書く手順は止まらない。
規則にできないものを規則の形で残すほうが、規約を腐らせる。

## 原典の読み方

| 手順 | 内容 |
|---|---|
| 1 | 原典を落とし、落とした日と `sha256` を残す |
| 2 | **原典を読む。**要約を経由しない |
| 3 | その原典の**どの考えに寄りかかるか**を、出典の表の「何を裏づけるか」へ書く |
| 4 | 規則の本文に識別子・コマンド・数値を書くときは、**原典の綴りのまま**書く |

**「何を裏づけるか」は概念で書く。**
識別子やコマンドを書いてはならない、という意味ではない ──
**原典を正しく読み、正しい識別子・コマンドで書けているなら問題は無い。**
禁じるのは、原典を勝手に言い換えることだけである。

**機械はこれを検査しない。**
文字列の一致で裏づけを裁こうとすると、両方向に外れる ──
広い語は原典が差し替わっても落ちず、
たまたま当たった語（画面部品の名前など）は原典の見た目が変わるだけで落ちる。
**原典が正しく読めているかは、AI が原典を読んで確かめ、人が承認する。**

## 版が変わったとき

**「公式」であることは、正しさを保証しない。**
版が上がったら、原典を取り直して読み直す。
見るのは「何を裏づけるか」に書いた考えが、まだ原典に在るかである。
無ければ、その規則は出典を失っている。

**機械は版の変化を知らせない。**
`sources/` の `.meta.json` に `sha256` と取得日時は在るが、比べる仕組みは持たない ──
取り直しは人が判断して起動する（論点17・20）。
