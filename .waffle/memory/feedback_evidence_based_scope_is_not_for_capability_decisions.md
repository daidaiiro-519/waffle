実例の件数を根拠に「まだ作らない」と判断してよいのは、**すでにある実例をどう抽象化するか**を決める場面だけ。
**その能力が目的の達成に要るかどうか**は、実例の件数ではなく、目的が名指ししている対象で決まる。

**Why:** 目的が「どの言語でも動くこと」なら、対象言語が要求する能力は、いまこのリポジトリに実例が
0件でも必須になる。実例の件数は「まだ書いていない」ことしか意味せず、「要らない」ことを意味しない。
件数を持ち出すと、目的そのものを縮めていることに気づかないまま「保留」と呼べてしまう。

実際に3度繰り返した。3度目は、テストの置き方（同居・鏡写し・ファイル内）を「実例0件だから保留」と
判断した場面。目的の段階が挙げている Go・Java・Rust が、その3方式をそれぞれ強制する。つまり
**保留した瞬間に目的が達成不能になる**のに、実例の件数だけを見ていた。

3度目の直接の原因は、この訂正が Claude Code 専用の記憶にしか無く、共有の記憶ストアにも
advisor のバックボーン knowledge にも入っていなかったこと。advisor 2体が同じ誤用をし、
突き合わせる材料が手元に無かった。

**4度目（2026-09-05）。** CodingSkills の設計で、「実行環境を軸に認めるか」を
「制約が分かれる実例が出た時点で軸に上げる」と判断した。**軸かどうかは独立性という概念の性質で決まり、
観測の頻度とは関係が無い**（同じ API を常駐でも都度起動でも書けるなら、実行環境は目的と独立に動く）。
ユーザーの指摘は「実例があるかどうかの具体ではなく、概念として考えるべきかという話をしている。
関係しているがまだ例が無いから要らない、は考えるべきことの先延ばしである」。

**このときは knowledge も共有メモリも揃っていた。** `architecture-evidence-based-scope` は
項目13 で「既にあるケースの中に見える構造的な違いを正確に表現してよいかには適用しない」、
項目19 で「名前を与える変更は射程外」、項目20 で「独立に動くなら種別ではなく直交する軸」と
除外規定を持っている。**それでも見出しの原則2（実例1〜2件あるか）だけを引いた。**
不足しているのは記録ではなく、**引くときに除外規定まで読むこと**である。

**How to apply:**
- 実例の件数を根拠に保留を提案する前に、**目的の記述に戻る**。目的が名指ししている対象が
  その能力を要求していないか確かめる
- advisor が実例の件数を根拠に保留を勧めてきたら、そのまま渡さない。目的との突き合わせは
  advisor の守備範囲の外にあることが多い
- 件数の基準を使ってよいのは「実例をどこまで一般化するか」を決めるときだけ。
  「作るか作らないか」には使わない
- **概念どうしの関係（独立か、従属か）を判断するときは、件数を持ち出さない。**
  独立性・包含・直交は概念の性質であって、観測の頻度ではない
- **`architecture-evidence-based-scope` を引くときは、原則2 だけでなく項目13・19・20 まで読む。**
  除外規定を読まずに見出しを当てたのが、4度目の直接の原因である
