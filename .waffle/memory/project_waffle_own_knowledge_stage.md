## 決まっていること（ユーザーの言葉から）

> **抽象は簡略化ではないし、情報の削減ではない。特徴を抽出して共通概念として表現するのが抽象。**

> **抽象は、一段下ろしたときに元の具体へ戻る高さまでしか上げてはいけない。**

犬の段：**動物**（上げすぎ。猫が混ざる）→ **耳がある・四足歩行・鼻が効く**（正しい高さ）→ **犬**（具体）→ **犬種**（規約が持つ）。

- 上げすぎと、`a.b` を `a` に潰すことは**同じ失敗**。どちらも一段下ろして元へ戻らない。症状だけが違う（別の具体が混ざる／一つの操作が能力を持ちすぎる）
- 抽象の段は **サブドメイン → BC・集約・業務ユースケース・業務サービス → 実装**（[205]）
- 上にも下にも際限はないので**際限は自分たちで決める**（[592]）。決め方は「一段下ろして具体が一意に定まる高さ」
- 仕様に具体を書くと、**具体の表現の仕方が変わったときに仕様が腐る**（[647]）
- クラス名・実装単位・置き場所・命名規則は**規約**が持つ（犬種にあたる）
- 仕様と実装をつなぐ契約は**受け入れ基準と振る舞いのシナリオ**。シナリオを一字一句テストへ転写して TDD（[65][86]）

## 未決（次の一手はここから）

**「正しい高さ」をどう言うか。**私は「どう作るか」で書いてしまう癖があり、2度指摘された。
いまの言い方は **「何が成り立つか」（条件と結果）であって、手順や仕組みではない** ——これで合っているかの確認待ち。

- ✗ 値を書き込む処理と検証する処理を分ける（作り方）
- ○ 検証だけを求めたとき、書き込みは起きない（成り立つこと）

**却下したもの**：「見る対象によって抽象度を変える」はこの概念に属さない（決定を人へどう見せるかの話で、記録の書き方の側）。
