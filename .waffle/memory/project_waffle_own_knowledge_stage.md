## この再定義で決まったこと（承認済み）

### 段の並び
| 段 | 何か | 操作 |
|---|---|---|
| **段1** | Schema の仕様 → Python の実装。**すべての schema の共通契約** | 持たない |

| **段3** | ふつうの Document | Document のコマンド |

エンティティは **Schema と Document の2つだけ**、どちらも集約ルート。ほかは全部値オブジェクト。

### Schema は3つの操作を持つ（https://claude.ai/code/artifact/995af0c1-5501-4330-87ea-f456f2684da5）
| 操作 | 何を作るか | 誰の |
|---|---|---|
| **型を起こす** | **段2 の型そのもの（構造）** | 作り手 |
| **骨格を作る** | 段3 の実体の器（値が空）。器と書き方の指針の両方を返す | 段2 のコマンド |
| **読み方の指針を返す** | そのブロックを何のために読むか | 段2 のコマンド |

**型を起こすのは、描くことでも骨格を作ることでもない。** 描くのは読み手向けの成果物へ落とすこと、
骨格を作るのは器を用意すること、型を起こすのは**器の形そのものを組み立てる**こと。
**「骨格」は器を用意することにだけ使う。**

Document は**4つ**（値を埋める／値を取り出す／逸脱していないか判定する／描く）。
**終端化するは落とした**（非推奨を持たなくなり、行き先が消えた）。
**集約は参照は持つが自分では解決しない。解決した相手を引数で受け取る。**

### Document は、導けないものだけを持つ（https://claude.ai/code/artifact/2362b93b-a1a8-4111-8b58-eff36eb61594）

持つのは **表紙／使ってよいか（`draft`・`active`）／content** だけ。
**非推奨は持たない** ── 誰も守っておらず、実物3本の参照は0件だった。退役は文書を消すことで表す。
**工程の状態（作成済・検証済・描画済）は持たない** ── 導けるものを保存すれば古くなる。
裏づけ＝`fill` は `status` に一切触れないので、**検証済のまま値を書き換えられる**。
**「検証前に描かせない」は状態の遷移ではなく、描くコマンドの事前条件。**

content は**型を知らない木**として持ち、値は外から渡される。ただし `schemaRef` を持つので、
**正しさは常に正せる**（不変条件のまま。守り方が「引数で受け取って判定する」形になるだけ）。

**完成イメージ**（https://claude.ai/code/artifact/df54f985-bf86-4931-b0be-de128ee32978）
に、持ち物・操作7つの入出力・型の解決のされ方・併用の要否を並べてある。要点：

- **型を解決するのはユースケース。** Document は参照を持つが取りに行かない
- **型が要るのは「判定する」「描く」の2つだけ。** どちらも引数で受け取るので Document 側で完結する
- **併用が要るのは索引だけ** ── 読み方の指針は型の持ち物、中身は文書の持ち物で、束ねるのはユースケース

### 段1 が部品を提供し、段2 が8つを宣言する（https://claude.ai/code/artifact/849ba715-aa46-46b7-b639-815651367236）

> **段1 はこのスキーマが表現できる部品を全て提供し、段2 がそれを組み合わせて表現する。**

**段1 の部品**：表紙／**構造の文法6つ**（値・まとまり・並び・入れ子・選び・名前で共有）／
修飾6つ（必須・決め打ち・選択肢・最小の個数・閉じる・**既定値**）／
**標準の組み立て（図・木）**／意味の語2つ（記入の指針・読み方）／描き方の語2つ。
**読む必要の度合いは持たない**（索引は部品の鍵と説明から導ける）。

**段2 の8つ**：型の名前と版／種別（**鍵の名前は宣言しない**）／ブロックの定義／枝ごとの必須ブロック／
共有する組み立て／各所の指針／描き方／成果物の宛先。

**決め手**：段2 が自前で部品を組んでいたら、それは段1 の欠落。
実例＝`KnowledgeSchema` と `SkillSchema` が同じ「深さ有界の木」を別々の名前で組んでいた。

**実物にある無駄は賄わない（後方互換と同じになるため）**：種別の鍵6つ→**1つ**（要らない軸は作らない）／
枝ごとの名前つき中身34個→**必須ブロックの一覧だけ**／`pattern` は正規表現として未使用。

### 部品に鍵と説明を持たせ、索引を取り出すときに組み立てる（https://claude.ai/code/artifact/25de7e5a-52b3-498e-9865-def7dfc5837f）

**どの部品も鍵と説明を持つ**（並び＝要素の鍵と説明／まとまり＝欄の名前と値／木＝節の名前と要約／
図＝`asserts` と `reading`＝**既にそうなっている**）。

**索引は保存せず、取り出すときに2段で組み立てる。**
1段目＝ブロックの鍵と読み方（全文の**4%**）、2段目＝そのブロックの鍵と説明（**ブロック単位で確定**）。
当たりを付けて1ブロック取っても**全文の7%**。`_index` は schema から落とす。

**裏づけ**：組の要素281件のうち**152件（54%）で説明が取れなかった**。
実装が欄名を当てていたため。落ちたものも `term`/`definition`・`conceptId`/`note` など**鍵と説明の対**で、
**形は揃っていて名前だけが違っていた**。

## この作業でやらかしたこと

**食い違い3つが、全部ユーザーの指摘で見つかった。** 自分で突き合わせていなかった。

- **「語彙7語」** ── 測定から私が計算し、会話で一度言い、計画に書き写した。**決定していない**
- **決定と完成イメージが別の語彙**（決定は「集約」、完成イメージは「段」）
- **コマンドの表と本文の食い違い**（本文だけにある操作）

ほかに：**「型ごとに自分の名前を付けているだけ」は誤り**（`specKind` は3本で共有）／
**`pattern` を制限と数えていた**（欄の名前だった）／
**`steps` を部品と数えていた**（引数名だった）／
**表の見出しとセルの数がずれていた**（検査の側も `<thead>` を `<th>` と数えて誤報）。

**4件目も同じ形で起きた。** Document の決定を承認したあと、
**図の置き場所の決定へ当て直すのをユーザーに問われて初めてやった**（「変更点はないですか」）。
当ててみると3点あった ── 先立つ決定への追加／「守り手は schema」の語の揃え／
「導いた値を持たない」の1行。**決定そのものは変わらないが、噛み合わせは自分で確かめるべきだった。**

**How to apply:** **決定を承認したら、その場で他の未承認の決定へ当て直す**（承認前ではなく承認後。
先に承認した側が動くことがある）。計画は本文を読んでから立てる。
**会話で言った数を、決定と混同しない。実測を根拠に方針を決めない。実物にある無駄を賄おうとしない。**
