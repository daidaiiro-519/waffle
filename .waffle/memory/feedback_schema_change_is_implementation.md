**schema の新版を切る、欄や種別を足す、宣言の形を変える ── これらはすべて実装である。** 仕様ではない。

決定が承認されても、次に手を付けるのは schema ではない。順序はこうなる。

| 順 | やること | 例 |
|---|---|---|
| 1 | **決定**（ADR） | 値オブジェクトを独立の単位にする |
| 2 | **仕様** | 仕様として独立に書ける単位は何か、を仕様が述べる |
| 3 | **実装** | `DomainSpecSchema` の新版を切り、`specKind` に足す |

2 を飛ばして 3 へ行くと、**説明の無い構造が増える**。転写する受け入れ基準が無いのでテストが書けず、突き合わせる宣言が無いのでドリフト検知も効かない。

**Why:** ユーザーの指摘「まず Spec から考える必要があると思ってますよ？ その行為は実装に当たると思いますが？」。決定が承認された直後、私は「`specKind` に2つ足す」を次の作業として提案した。その直前に自分で「schema を直しても仕様は何も言わない」「`x-render-order` は156か所で使われて仕様に0回しか現れない」と測っていたのに、同じ形をもう1つ作ろうとしていた。

**How to apply:** 「schema をこう変える」と言いかけたら止まる。**その変更を説明する仕様がどこにあるかを先に指させるか**を問う。指せないなら、指す先を作るのが次の作業である。schema は成果物であって、成果物から書き始めない。関連: [[correct-toward-the-right-form-not-the-existing-one]] [[spec-implementation-abstraction]]
