## 何が問題か

`check-aggregate-class-drift` は Hook（`check-drift-on-write.py`）で aggregate spec の書き込み時に動いている。しかし受け入れ基準17件のうち、クラスの存在を求める3つ（`missing_implementation_file` / `class_name_mismatch` / `missing_implementation_in_scope`）に**実装方法による分岐が無い**。無条件にクラスを要求する。

採用済み knowledge `knowledge-cand-aggregate-declaration-is-not-class-existence` は、これを「厳しすぎて同時に緩すぎる」と指摘している——要求すべきでないクラスの不在で赤を出し、本当の違反（不変条件が依存する変更がトランザクション境界をまたぐ）を見逃す。

## 原因

**分岐すべき中間項が、機械可読な形で宣言されていない。** サブドメインの `implementationGuidance` は文章（例:「一般ゆえ既製ライブラリを薄く包む」）で、検査は「ドメインモデルなのかトランザクションスクリプトなのか」を判定できない。knowledge は「分類を直接の分岐条件にするな、中間項を経由せよ」と言うが、その中間項が読めない状態だった。

## 対処（3段。1つの仕様としてまとめて書く）

1. **中間項を宣言にする** ── 業務ロジックの実装方法を値で持つ（ドメインモデル／イベント履歴式／アクティブレコード／トランザクションスクリプト）。4種類は書き起こし版の `domain-model.md` / `business-logic-simple.md` に定義済み。任意の欄なら後方互換を壊さない
2. **検査を分岐させる** ── 実装方法に応じてクラスの要求を変える
3. **境界の検査** ── 不変条件が依存する変更がトランザクション境界の内側に収まっているか

## Why: 3は新しい能力ではない

「DBが無いから語彙が無い」と考えたのは誤り。**トランザクションは元から抽象概念で、DBはその一実装**。書き起こし版も「1集約インスタンス = 1トランザクション単位」と実装を指さずに使っている。

そして今日すでに3箇所で同じ主張を書いていた——要素操作「1つでも受け付けられないなら何も保存しない」／種別の取り消し「途中で取り除けないなら何も取り除かない」／業務サービス「ひとつでも適用できないなら何も適用していない配列を返す」。**名前が無かったので毎回その場の言葉になっていた**だけ。

## How to apply

- 語彙に「トランザクション」「トランザクション境界」を追加済み（bc-waffle、81語）
- 着手時はまず実測から: `render` が正本と配置先へ何回書くか、`scaffold` の保存が何回か、`patch_schema` はどうか。実装が実際にどこで区切っているかを見てから境界の宣言の形を決める
- **順序**: サブドメインの切り方を直した直後が効く（補完へ再分類した領域で誤検知が出るのを防ぐ）
