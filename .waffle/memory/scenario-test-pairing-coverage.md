2026-08-01に、specのシナリオとテストの突き合わせのキーを、テスト関数名から文書コメントの宣言行「Scenario: {シナリオ名}」へ移した。あわせて `check-scenario-drift` に全体走査（documentsRoot / testsRoot）を足し、1組ずつの呼び方も残した。実装・移行とも完了（テスト538 passed、突き合わせが成立している39組は差分ゼロ）。

## 対応づけを何が担うかの設計結論

| 何を決めるか | どこが担うか | 状態 |
|---|---|---|
| どの層か（受け入れ／保証／不変条件・ドメインサービス） | ディレクトリの第一階層（tests/acceptance 等） | 既存の規約。**そのまま維持する** |
| どのspecか | ファイル冒頭の `Spec: {documentId}` 行 | **未実装。次のサイクルの対象** |
| どのシナリオか | 関数の文書コメントの `Scenario: {名前}` 行 | 実装済み |

**ファイル名で対応づける規則（1 spec = 1ファイル、`test_{documentId}.py` 必須）は外す。** 理由は、関数名規則と同じ欠陥を持つため——Javaはクラス名と一致必須、TypeScriptは `.test.ts` が慣習、Goは `_test.go` と、ファイル名の慣習が言語ごとに違う。名前に対応づけの情報を持たせると、また各言語の慣習と衝突する。対応づけの情報は名前ではなくファイルの中へ置く。

`Spec:` をファイル冒頭のコメントから取り出せることは、python / java / javascript / typescript の4言語で実機確認済み。

**シナリオ名は spec を跨いで一意ではない**（418件中11件が重複。「存在しないパスはINVALID_PATH」は6つのspecが持つ）。これは事故ではなく、同じ振る舞いに同じ業務語彙が付くため自然。したがって宣言行だけでは組が決まらず、`Spec:` 行が要る。キーは (層, spec, シナリオ) の3つ組になる。

## 相手のいないシナリオ176件の内訳（2026-08-01実測）

| | 件数 | 実態 |
|---|---|---|
| artifact-share 関連 | 約137 | テストは145件実在する。`tests/` の外（Skill配下）にあり実装モジュール由来の命名 |

`Spec:` 宣言を入れれば31件が即座に対応づく。artifact-share の137件は「実装を伴うSkillの扱い」（別サイクル。ユーザー判断で保留中）が前提。

## 測り方

`uv run waffle check-scenario-drift --documentsRoot .waffle/documents/specs --testsRoot tests`

**Why:** 「Gherkinのシナリオはすべてドリフト検知できる仕様か」という問いに答えるために測った。仕様上は4種すべてが対象だが、組が存在しなければ何も起きない。この差は数字にしないと見えない。

**How to apply:** 「ドリフト検知が効いている」を根拠に品質を語るときは、対象が全体の6割であることを前提にする。次のサイクルは「決める」（test-standardの3規則の書き換えと `uc-check-scenario-drift` の受け入れ基準）から入れる。新しい仕組みを足したくなったときは、**まず既存の兄弟がどうしているかを全部見る**——今回は5つの前例があるのに1つだけ見て「前例が無い」と判断しかけた。**規則を外す前に前提を実測する**——「シナリオ名で一意に決まる」と思い込んだまま進めるところだった。
