仕様（DomainSpec）と実装の抽象境界について、2026-08-09 に到達した結論。**根拠の出どころで3つに分ける**——混ぜると「原則と矛盾しない」を「原則から導かれる」と取り違える（実際にこのセッションで2回やった）。

## A. 原則から出たもの（ddd-advisor の knowledge 原文が支える）

- **仕様に実装都合の語彙を入れない**（`ubiquitous-language.md`「業務用語のみで構成すること——シングルトンやファクトリーパターンのような実装都合の語彙を持ち込まず」）。`port` / `adapter` / `Primary` / `Secondary` / `repository` はこれに該当する
- **「ポートとアダプター」は3つある技術方式の1つの名前**であり、ヘキサゴナル/オニオン/クリーンはその別名（`architecture-patterns.md`）。**レイヤードにはポートが存在しない**（業務ロジック層がデータアクセス層を直接呼ぶ）。「Port/Adapter はどのアーキテクチャでも当てはまる」は成り立たない
- **ポートはドメインモデルの部品ではない**。部品は値オブジェクト・エンティティ・集約・業務サービスの4つ（`domain-model.md:27`）。ポートは「集約と値オブジェクトを永続化の都合から分離するため」の遮蔽物（`design-heuristics.md` q6/r8）であり、分離のために作った構造の名前を分離される側の仕様へ書き戻すのは目的と衝突する
- **イベント履歴式ドメインモデルでも spec は分かれない**。「従来のドメインモデルと部品（値オブジェクト・集約・業務イベント）は同じであり、違いは永続化の対象が『状態』か『状態が変化した経緯』かという一点にある」（`event-sourced-domain-model.md`）
- **連鎖**: 区切られた文脈の大きさ→業務ロジックの実装方法→技術方式→テスト方針。**経験則であり定理ではない**（「完全性は保証されない」）。**食い違ったら前段（特にサブドメイン分類）を疑い直す**（`design-heuristics.md`）。中核にも補完にも道が2本ずつある（中核: ドメインモデル→ポートとアダプター／イベント履歴式→CQRS。判別は金銭処理・一貫した監査記録・深い行動分析が必要か）
- **イベント駆動とイベントソーシングは別の軸**。前者は「境界づけられたコンテキストの公開インターフェースを設計する手段であり、コンテキスト内部の実装方式ではない」（`event-driven-architecture.md`）＝`contextMap` の領分
- **bc の定義は2節**——「ある言葉が一貫した意味を持ち続けられる範囲」＋「同時にその意味を表現するモデルが実装として独立している範囲」（`bounded-context.md`）。前半だけを根拠に「bc だから技術は書けない」とは導けない
- **業務サービスが bc にあるのは「複数の集約にまたがる/どの集約にも属さない」から**であって、複数usecaseに共有されるからではない（`domain-model.md:34`）。knowledge の用語は「業務サービス」で、「ドメインサービス」では引けない

## B. Waffle の設計判断（原則と矛盾しないが、原則からは導かれない）

- **分類は仕様、実装方法・技術方式・テスト方針は規約に置く。** 原則が言えるのは「仕様に実装都合の語彙を入れるな」までで、**ではどこに置くかは言っていない**。DDD は「spec 文書」「規約文書」という容器を知らない。現状の割り当ては Waffle の設計であり、実物を読んで得た観測でもある
- **検知は「仕様側の構造化された要素 × 規約の規則 → 期待される姿 → 実物」の経路を通る。** 規約は紐づけていない——具体へ落とす規則を供給しているだけで、紐づけるのは仕様側の要素

## C. 私の提案（未採用・要判断）

- 連鎖の4段（分類/実装方法/技術方式/テスト方針）の整合を**差分として提示する**検知。経験則なので判定にはできず、`gherkin_mismatches` と同じ分業に乗せる。報告文は knowledge が決めている（「前段の分類を疑い直せ」）
- `thicknessBySubdomain` に4つ目の道（イベント履歴式→CQRS）を足す。現状は3つしか宣言していない

## D. 取り下げたもの

- **ポートを仕様に宣言する**（A の2〜3番目により、原則に反する）
- **「外に求めるもの」の定義を bc に置く**（`bounded-context.md` に「共有される置き場」という機能は無く、加えて「一つのコンテキストの中でも業務領域ごとに異なる技術方式が共存している」ため、bc に一覧を置くと全体に1方式を強制する）
- 代わりに、外に何を求めるかは **`preconditions` / `mainFlow` に業務語彙で**書く。`uc-check-layer-drift` が既にその形（「確認の基準となる規約が、層とその置き場所、依存してよい先を宣言している」）

**Why:** このセッションで2回、実物の並びを読んでそれを結論として提示した（bc への配置案、①②③④の置き場所）。「原則と矛盾しない」と「原則から導かれる」は別で、混ぜると根拠の出どころを取り違えたまま結論だけ合っている状態になる——advisor からも同じ指摘を受けた。

**How to apply:** 仕様の抽象について判断するときは、まず A に当たる。A に無ければ B か C であり、**B と C は変更してよい**（Waffle の判断なので）。A は変えられない。advisor へ相談するときは「knowledge の原文を引いて」と明示する——引かせないと、advisor 自身も観測からの推論を混ぜる。
