既存新設（今回の実装対象）

読み方

  1. 呼出口: 公開した人が4つの操作を呼ぶ入口。CLI・Web UI・MCP の3経路。

  2. コア: 閲覧トークンの4操作。対象を問わず共通の経路にし、違いは期限の上限だけ。

  3. application が要求する口: 閲覧トークンの保管と、対象の状態の保管。

  4. 実装: エッジから同期で読める保管と、公開した人が読む正本。

使われ方（実際の呼び出し例）

  1. ds.sh token issue <slug> --name 'デザインチーム' --days 7

  2. ds.sh token list <slug> 名前と期限が返る。閲覧トークンそのものの値は返らない

  3. ds.sh token revoke <slug> --name 'デザインチーム'

  4. ds.sh token revoke-all <slug> 渡した相手を一度に全て外す。公開は止まらない

02 詳細

ddd-advisor
閲覧トークンはエンティティであり、集約の内側に持つ
個別に無効化でき名前を持つため同一性が要る。かつ「同時に有効なのは5本まで」は本数を数えて初めて守れる不変条件なので、IDによる外部参照ではなく集約の内側に含める。閲覧トークンそのものの値は一度しか示さないため、公開した人が一覧で選ぶための ViewTokenId を別に持つ。
tech-lead-advisor
格納の向きを逆転させ、指紋から対象を引く
いまは対象IDからトークン1本を引いている（token:{artifactId} / proj:{projectId}）。複数持ちにすると1レコードに詰め込むことになり、サイズ上限に当たる。提示された閲覧トークンの指紋から引く形（tok:{指紋} → 対象種別・対象ID・期限）へ逆転させれば、何本あっても読み取りは1回で済む。いまのプロジェクト経路は proj: と pp: で2回引いているので、経路によっては現在より減る。
tech-lead-advisor
一括無効化のために、対象の状態を別キーへ置く
KVS は前方一致検索を持たないため、対象に紐づく閲覧トークンの一覧を引けない。公開停止は対象の全経路を閉じる操作なので、状態を別キー（state:{対象ID}）に持ち、ゲートは2回引く。金銭コストには影響しない（CloudFront Functions の課金は呼び出し回数に対するもので、1呼び出しの中の読み取り回数は請求に現れない）。
ddd-advisor
期限切れの記録の削除は、集約の不変条件ではなく操作の事後条件
定期実行の仕組みを持たない構成なので、削除は発行と一覧のときに行う（遅延削除）。誰も操作しない間は記録が残るため、「期限を過ぎた記録は常に残らない」は不変条件としては偽になる。上限の判定は『無効にされておらず、かつ期限を過ぎていない』本数で行い、記録が一時的に残っていても矛盾しないようにする。
platform-advisor
2つのランタイムのデプロイは原子的でない
エッジ関数と Lambda は別々に、順番にデプロイされる。その間、片側だけが新しい形式になった状態が必ず存在する。記録の形を変える今回の変更では、この隙間に「正しい閲覧トークンなのに開けない」が発生する。2026-08-01 に実際に起きた障害と同種で、しかも両側のテストはそれぞれ最新の契約に対して緑になるため構造的に捕まらない。
platform-advisor
実行予算は数値を写さず、読み取り回数の上限を自分で宣言する
AWS のクォータ値を仕様へ書き写すと宣言の重複になり、AWS が変えたときに腐ったことに気づけない。制御できるのは「何回引くか」なので、そちらを規約として宣言し、その回数で予算に収まるかをデプロイ時に実測する。予算超過は 5xx（全閲覧の停止）であり、性能ではなく可用性の問題。
platform-advisor
読み手を先に、書き手を後にデプロイする
エッジゲート（読み手）を先に出し、新旧どちらの記録形式も受け付けられる状態にしてから、管理API（書き手）を新形式へ切り替える。ゲートは publish 後に各エッジへ伝播する時間があるため、切り替わりは瞬時ではない。既存の test_deployed_gate.py を、デプロイの最終段として必須実行にする。
tech-lead-advisor
既存データの移行が要る
稼働中の環境には token:{artifactId} と proj:{projectId} の記録が実在する。向きを逆転させると、これらは新しいキーからは引けない。移行の手立て（旧キーを読んで新キーを書く一度きりの操作、または一定期間の両対応）を用意しないと、既に渡してある閲覧トークンが一斉に使えなくなる。
tech-lead-advisor
実装は稼働中であり、未着手ではない
閲覧ゲートは296行の実コードで実環境へデプロイ済み、実障害も経験している。未着手なのは lambda/admin_api の層構造への再編だけ。今回の変更は『これから書くもの』ではなく『動いているものの差し替え』として扱う。
ddd-advisor
対象による差は1箇所にだけ置く
共有アーティファクトとプロジェクトは同じ仕組みで動く。実装でも共通の経路にし、違いは期限の上限の判定だけにする（アーティファクトは1ヶ月上限、プロジェクトは期限を設けない指定が可能）。対象ごとに関数を分けると、同じ規則が2箇所に生まれる。
tech-lead-advisor
テストの置き場所は規約が決める
test-standard-artifact-share が宣言する配置に従う。ただし現状のテストは lambda/admin_api/tests/ にあり、宣言された配置と一致していない（検査が宣言漏れ11件として報告している）。今回の変更でテストを足す前に、配置を宣言どおりにするかどうかを決める必要がある。決めないまま足すと、宣言漏れが増える。
