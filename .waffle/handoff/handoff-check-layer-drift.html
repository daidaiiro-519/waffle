既存新設（今回の実装対象）

読み方

  1. 呼出口: 開発者がこの検査を呼ぶ入口。CLIとMCPの両方から同じユースケースを呼ぶ。

  2. コア: 規約から層・置き場所・依存してよい先を読み、実装の依存と突き合わせる判断そのもの。違反・宣言漏れ・未実装の3種を返す。

  3. ポート: コアが外部へ要求する口。依存を取り出す口は今回新設し、ファイルの読み出しは既存の口をそのまま使う。

  4. 実装: ポートを満たす具体。言語ごとの構文差はここだけが知る。

使われ方（実際の呼び出し例）

  1. uv run waffle check-layer-drift --architectureRef architecture-waffle

  2. 違反が無ければ {"violations": [], "unassigned": [], "missing_layer_dirs": []} を返す

  3. 宣言が許していない依存があれば、違反した実装・その層・使っている相手の層を列挙する

  4. 置き場所どうしが飲み込み合っていれば、実装を走査せず OVERLAPPING_LAYER_PATHS を返す

02 詳細

orchestrator（advisor未相談・要レビュー）
ファイルを層へ割り当てる手がかりは置き場所だけにする
あるファイルがどの層かは、規約が宣言する置き場所への前方一致で決める（最長一致を採る）。ディレクトリツリーの図は投影であって宣言ではないので参照しない。この方針は LayersBlock の x-prompt-query に既に明記してあり、検査はその読み方に従う。
orchestrator（advisor未相談・要レビュー）
宣言の健全性を、実装を見る前に確かめる
ある層の置き場所が別の層の置き場所を含んでいると、配下のファイルがどちらの層か前方一致では決まらない。この状態で実装を走査すると結果が無意味になるので、走査の前に宣言だけを見て弾く。実際に artifact-share でこの誤りが起きていた（入口の層が sourceRoot 直下を占め、他の全層を飲み込んでいた）。
orchestrator（advisor未相談・要レビュー）
依存先の解決に、新しい宣言軸を足さない
依存の書き方は言語ごとに違う（Pythonはドット区切り、TypeScriptは相対パス、Goはモジュールパス）。これを規約の新しい欄として宣言させると、プロジェクトごとに埋める項目が増える。代わりに、取り出した参照から候補パスを後ろ側から順に作り、置き場所の下に実在する最長のものを採る。実在しなければ規約の受け持つ範囲の外（標準ライブラリ・外部ライブラリ）とみなして無視する。
orchestrator（advisor未相談・要レビュー）
ports は層ではないので、特別扱いを持ち込まない
ports は application が所有する要素であり、application の置き場所の配下にある。前方一致で解決すれば application として扱われるので、検査側に ports の概念は要らない。逆に、ports を層として特別扱いするコードを書くと、その扱いが規約の宣言と二重になる。
orchestrator（advisor未相談・要レビュー）
走査する言語は規約が決める
どの拡張子を走査するかは tech-stack の runtime.languages[].extensions が宣言する。検査コードに拡張子の表を持たない（言語拡張の際に同じ表を二箇所直すことになるため）。対応する構文解析器を持たない言語のファイルは、違反ではなく走査対象外として扱う。
orchestrator（advisor未相談・要レビュー）
同じ層の中の依存は、宣言を要さない
mayDependOn は他の層への依存を宣言する欄であり、自分自身を書かせると全層に自分の名前が並んで宣言が冗長になる。自層への依存は常に許す。最内層（mayDependOn が空）が自層内で完結するのは正常な状態。
orchestrator（advisor未相談・要レビュー）
依存を取り出すポートを新設する
既存の抽出ポートは class_declaration_extractor（型名・フィールド名）と test_function_extractor（テスト関数と文書コメント）だけで、依存を取り出す口が無い。ImportExtractor を新設し、tree-sitter アダプターが8言語ぶんの構文差を吸収する。言語ごとのノード型は推測せず、実際に解析して確かめてから書く（言語拡張時と同じ手順）。
orchestrator（advisor未相談・要レビュー）
置き場所の解決は既存サービスを再利用する
sourceRoot の解決（{package} 置換を含む）は source_root_resolution に、規約からの読み出しは stack_resolution に既にある。同じ解決を検査ごとに書き直すと、今日直したような宣言の読み方の違いが再び生まれる。
orchestrator（advisor未相談・要レビュー）
置き場所の不在はエラーではなくドリフトとして返す
既存の4検査は、宣言された置き場所が無いときエラーで止まっていたのを、未実装の所見として返すよう今日改めた。新設する検査も同じ扱いに揃える（規約を先に書いて実装を後から合わせる進め方では、この状態が正常に起きる）。

受け入れシナリオは tests/application/acceptance/、保証シナリオは tests/application/integration/、ポートの契約テストは tests/application/contract/。ファイル名は test_uc_check_layer_drift.py。テスト関数の文書コメントの先頭に宣言行を置き、spec のシナリオと突き合わせる。

自分自身に掛けて、既知の答えと突き合わせる
waffle 自身の規約は層5つと依存の向きを宣言しており、実装は今日その宣言へ揃えた。実装後にこの検査を waffle 自身へ掛け、違反が出ないことを確かめる。出た場合は、検査の誤りか、今日の宣言修正の漏れかを切り分ける材料になる。
1

本セッションはサブエージェント委譲を行わない設定のため、設計観点・実装観点はOrchestrator自身の調査に基づく。ddd-advisor / tech-lead-advisor のレビューは未実施で、reviewStatus に open のまま残している。

2

依存先の解決は、参照から作った候補パスが規約の範囲の中に実在するかで決める。実装当初は実在を確かめておらず、層と同じ名前を持つ外部ライブラリ（layers に shared があるプロジェクトでの import shared 等）を層への依存と取り違える誤検知があった。テストで再現させてから実在確認を通す形へ直した。残る取り違えの芽は、同名のファイルが複数の層に実在する場合に、後ろ側からの最長一致が意図と違う層を指しうること。

3

実行時に組み立てられる依存（文字列によるモジュール参照・動的な読み込み）は構文解析では取り出せないため、検出できない。

4

1つのプロダクトが複数のランタイムを持つ場合（artifact-share の閲覧ゲート等）、層を持たないと宣言した領域は機械可読な宣言を持たないため、走査から外れるのではなく 『どの層にも属さない実装』として毎回報告される。実装して確かめた結果、引き継ぎ時点の見込み（走査対象から外れる）は誤りだった。黙って除外するより見えている方がよいと判断して現状のままとし、宣言で除外を表す軸を持つかは別サイクルで扱う。

5

実装して分かったこと: 中身の無いファイル（パッケージの目印等）は層の割り当ての対象から外す。外さないと、どの層にも属さない同じ顔ぶれが毎回並び、報告そのものが読まれなくなる。境界値シナリオとしてspecに宣言した。

6

1つの並びだけからなる参照（import shared 等）が、ファイルではなくディレクトリにしか当たらない場合は解決しない。その形は「規約の中のパッケージ」と「同名の外部ライブラリ」を構文からは区別できないため、取り違えるより報告しない方を選んだ。規約の中のパッケージを直接指す書き方は見逃す（見逃しの範囲を、誤検知と引き換えに受け入れた）。
