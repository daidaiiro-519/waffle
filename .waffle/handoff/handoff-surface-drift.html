02 詳細

（Orchestrator）
なぜ検査を先に作るか
119関数の利用者向けの文を手で移してから検査を作ると、移し間違いを検知できないまま確定してしまう。検査→宣言を埋める→移す、の順にする。
（Orchestrator）
綴りを正規化して比べる理由
同じ入力が口ごとに違う綴りで現れる（--documentsRoot / documentsRoot / documents_root）。どの綴りが正しいかを決める宣言はいま無く、それを必要とする実例も出ていない。区切りと大小を落として同一視し、名前の有無だけを見る。
（Orchestrator）
実際に見つかっている食い違い
CLIとMCPで両方にある操作20件を突き合わせたところ、1件が食い違っていた——uc-check-path-is-projection の入力が、CLIでは resolvedPath、MCPでは realPath。しかもMCP側には説明が一切ない。残り19件は揃っており、この方式で誤検知は出ない。
（Orchestrator）
口の種類を問わない設計にする理由
artifact-share の受け口は要求本文のキー（b.get("artifactId")）で入力を受け取っており、CLI/MCPとは取り出し方が違う。宣言と突き合わせるという中身は同じなので、取り出しだけを言語・口ごとのアダプターへ寄せる（既存のClassDeclarationExtractor / TestFunctionExtractor と同じ形）。
（Orchestrator）
既存の材料で足りる範囲
scan_source_code は既に signatureParams（実際の引数名）を返す。CLI・MCPの入力の取り出しはこれで足りる。新しい取り出しが要るのは、typerのOptionに書かれた説明と、要求本文のキーを読むとき。
（Orchestrator）
操作と仕様の対応づけ
CLIの関数名とMCPの関数名が揃っていない（query / query_document、render / render_document など6件）。どのユースケースの口かを決めるのに関数名は使えないので、docstringに手書きされている（uc-...）か、別の対応づけが要る。ここは実装時に決める。
（Orchestrator）
説明の一致は次の増分
この増分では名前の有無だけを見る。説明の突き合わせは、typerのOptionからhelpを取り出す新しい抽出が要るため分ける。
1

naming.cases の artifact は module / type / function / constant / field の5つで、入力に当たる値が無い。かつ naming.cases は対象ごとの宣言で、口ごとではない。1つのスタックが複数の口を持つと綴りが分かれるため、綴りまで検知したくなったらこの構造から見直す必要がある（今回は正規化で回避する）。

2

artifact-share の受け口は入力の説明を一切持たない（typerのhelpに当たるものが無い）。宣言を埋めても、突き合わせる相手が無い状態が残る。

3

CLIの関数の docstring は typer が --help へそのまま印字し、MCPの docstring は fastmcp がツールの説明にする（どちらも実測で確認）。移し先は decorator の help / description。
