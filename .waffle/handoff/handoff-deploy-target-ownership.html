既存新設（今回の実装対象）

読み方

  1. 宣言: どこへ置くかを宣言する層。設置環境の情報はconfig、文書型の定義はschemaが持つ。

  2. 判断: 配置先を解決し、所有権を判定する純ロジック。ファイルI/Oを持たない。

  3. 調整: 宣言を読み、判断へ渡し、結果に従って書く。業務ルールそのものは持たない。

  4. 文書: 実運用の定義と、移植用の雛形。種別が異なるため配置先の解決も異なる。

使われ方（実際の呼び出し例）

  1. uv run waffle render --path .waffle/documents/agent/orchestrator-template.json # canonicalのみ生成され、CLAUDE.md/AGENTS.mdは書き換えられない

  2. uv run waffle render --path .waffle/documents/agent/waffle.json # 従来どおりCLAUDE.md/AGENTS.mdへ配置される

02 詳細

ddd-advisor
投影先を識別子の関数にする（エンティティを値として扱わない）
agentKind=orchestratorの文書はdocumentIdで区別されるエンティティなのに、投影先CLAUDE.mdがそれを引数に取らないため、投影側で2つのエンティティが同一の値に潰れている。これはCQRSの投影におけるキー欠落で、後の投影が先の投影を無条件に上書きする。事故は偶発ではなく必然であり、同じ操作をすれば必ず再現する。
ddd-advisor
雛形は未完成品ではなく責務の異なる別概念として名前を持たせる
雛形は(1)値がプレースホルダー(2)投影されない(3)他プロジェクトで実体化されるために存在する、の3点で実運用文書と責務が異なる。statusで表すと「完成度」と「種類」の二義になり、タグで表すとrender経路から読まれず不変条件を持てない。ubiquitous-languageの「振る舞いに違いがあれば別概念として定義する」に該当する。
ddd-advisor
schemaが形を、configが位置を決めるという現在の分担は変えない
CLAUDE.mdや.claude/skills/という具体パスは特定AIツールの読み取り規約であり、外部連係の関心事。文書側へ持たせるとポートとアダプターが避けようとしている基盤詳細の侵入になる。scope.pathを配置先へ流用する案は、管轄範囲と設置座標という別概念に同じ語を使うことになり原則レベルで退けられる。
tech-lead-advisor
pathTemplateの変数化は原理的に成立しない
CLAUDE.mdはWaffleが決められる値ではなく外部ツールがリポジトリルートで固定的に読むファイル名。{documentId}を差し込めばツールから読まれなくなる（衝突は消えるが機能も消える）。解くべき問いは「どこへ置くか」ではなく「1枠しかないスロットを誰が占有するか」であり、これは設置環境の情報。
tech-lead-advisor
canonicalパスの真実源はschemaへ寄せ、config側の定義は廃止する
deploy先は設置環境で変わるためconfig、canonicalパスは文書型の定義で変わるためschema、と変更理由が異なる。加えて表現力が非対称で、schema側はdiscriminatorごとの分岐を持てるがconfig側は型ごと1本の平坦な文字列しか持てない。表現力の低い側を真実源にすると分岐を持つ型で表現不能になる。
ddd-advisor
雛形は種別の値ではなく、種別と直交する役割として表す
agentKindの値として雛形を足すと、AgentSchemaはその値に対応する内容の形を定義することになり、それはorchestratorとまったく同じ形になる（雛形は形が違うのではなく、同じ形で値が埋まっていないもの）。同じ形が2つ生まれ、雛形を作るたびに増える。全schema共通のdocumentRole（既定instance／template）として直交軸に置き、内容の形は1つのまま保つ。
tech-lead-advisor
雛形の除外はif文ではなく、配置先の解決キーに役割を含めることで表す
renderに『documentRoleがtemplateなら飛ばす』という条件分岐を書くと、投影アダプターが文書の分類語彙を知る形になり依存の向きが逆行する。解決キーを(documentType, documentRole, discriminator)に拡張し、config.jsonにはrole=instanceの宣言だけを置く。雛形はキーに対応する宣言が存在しないため配置先が解決できず、結果として配置されない（条件による除外ではなく構造的な不可能性）。
tech-lead-advisor
配置先解決の純ロジックをdomain/servicesへ抽出する
現在の_resolve_tool_deploy_targetsは前半でconfig.jsonのI/Oを行い後半で規則の適用を行っており、変更理由の異なる2つが1メソッドに同居している。src/waffle/domain/services/deploy_target_resolution.pyを新設し、render_document.pyのモジュールレベル関数_resolve_single_mapping_targetsと変換規則をそこへ移す。入力は読み込み済みのdictのみとし、ファイルI/Oを持たせない。
tech-lead-advisor
ガードはhookではなくrender usecase側に置く
mcp__waffle__render_documentというMCP経路が実在するため、Bashコマンド文字列を検査するhookは同じusecaseへの別の入口を素通りする。既存のEdit/Write用hookが成立しているのは「実体パス1つを渡せば判定できる」入力形だからで、renderは入力がdocument.jsonであり配置先を知るにはコアの解決ロジック全体が必要になる。
tech-lead-advisor
所有権判定をdomain serviceとして抽出しcheck_path_is_projectionと共有する
usecaseからusecaseを呼ぶのではなく、共通のdomain serviceへ抽出して両者が呼ぶ形にする。CheckPathIsProjectionはconfig/schema読み出しとResult包装のみを担う薄いusecaseにする。symlink解決はアダプター（DocumentRepository）側の責務として既存の分業を踏襲する。
tech-lead-advisor
スキップは黙って握りつぶさず理由を返す
所有者宣言や種別分離によって配置先が解決されない場合、静かに何もdeployされない状態は設定漏れと区別がつかない。renderの結果に配置先と理由（例: NOT_DEPLOY_OWNER）を明示的に含める。既存の_err規約に合わせる。
tech-lead-advisor
1実例からの一般化を避ける
今回の実例はAgent.orchestratorの1件のみ。documentTypeごとに任意の配置ポリシーを記述できる汎用ポリシー機構へ一般化すると、config.jsonがDSL化して真実源一元化の成果を相殺する。2件目（別の定数スロット、または別documentTypeでの同種の衝突）が観測されるまで共通化しない。

canonicalパスの真実源はこの増分で一度に切り替える
config.jsonのcanonicalPathTemplatesを削除し、check_path_is_projectionがschemaのx-render-target.pathを逆マッチするよう変更する。暫定の二重読み期間は置かない。切替の取りこぼしは、逆マッチ失敗時に無症状でisProjection: Falseを返す現在の挙動により検知できないため、テストで担保する。SchemaRepositoryのCheckPathIsProjectionへの注入はcomposition root 1箇所で配線する。
