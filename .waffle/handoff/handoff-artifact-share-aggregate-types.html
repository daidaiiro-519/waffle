00 完成イメージ — 予定される実装配置

既存新設（今回の実装対象）

読み方

  1. 業務の語彙: 宣言された名前が、型として存在する層。ここに名前があって初めて、宣言との突き合わせが機械に見える。dict のキーは見えない。

  2. 口: 集約の型で宣言し直す。いまは dict を受け渡しており、配置は application/ports だが形は保管の都合で決まっている。

  3. 翻訳: 保管の欄名と集約の属性名を結ぶ唇一の場所。ここだけが両方の語彙を知る。

  4. 保管: 欄名は変えない。既存の記録がそのまま読めることが、移行を不要にする根拠である。

使われ方（実際の呼び出し例）

  1. 取り出す: artifacts.find(artifact_id) が SharedArtifact を返す。呼び出し側は displayName / publishedBy という業務の言葉で読む

  2. 残す: artifacts.save(artifact) が、name / uploadedBy へ直して保管へ置く

  3. 判じる: is_published(artifact) が、dict ではなく SharedArtifact を受け取る

02 詳細

ユーザー
検査が求めているのはユビキタス言語そのもの
check-aggregate-class-drift が突き合わせているのは構造ではなく名前だけであり、「会話・仕様・コードで同じ言葉を使う」を機械化したものである。型が無いと語彙は文字列のキーとしてしか存在せず、ClassDeclarationExtractor から見えないので、離れても誰も気づかない。
tech-lead-advisor
集約を型にすべき最も強い理由は、ポートの形にある
SharedArtifactRepository は find() -> dict / save(dict) を宣言しており、配置は application/ports だが形は保管の都合で決まっている。architecture の禁止条項「配置が application/ports であっても、その形をアダプターの都合で決めているなら依存方向は実質的に逆転している」に該当する。
tech-lead-advisor
宣言どうしが矛盾していた
conceptPlacement が集約を「整合性境界を持つクラス」、値オブジェクトを「不変（frozen dataclass）」と宣言しているのに、thicknessBySubdomain の補完行へ書き足した一文だけが外れ値だった。禁止と助言の優先順位の問題ではない。
ddd-advisor
属性名は宣言（業務の言葉）を正とする
実装の名前は、同義語の乱立（displayName / name が両方の集約で別々に使われている）か、実装都合の語彙（uploadedBy は技術操作の語で、業務上の出来事は公開）のいずれかに該当する。実装側が一語に統一されていない以上、「実装を正とすれば動かさずに済む」という利点は最初から存在しない。
ddd-advisor
descriptor は値オブジェクトである
5つの値は inspect_html が一度に返し、応答では実装自身が組み立て直しており、不変条件（分類の目印が見られる相手を変えない）が一組全体にかかっている。組み立て規則（取り出せたか人が与えたか）という引き取るべき振る舞いも実在する。
ddd-advisor
所属の正は共有アーティファクトの側
強い一貫性を要求する不変条件（同時に3件まで）は共有アーティファクトの側にしか無く、プロジェクトの側の一覧は閲覧者へ見せるために組み立て直せる投影である。投影は失敗しても作り直せるので、どちらが正か分からなくなる状態にはならない。
tech-lead-advisor
翻訳表の契約テストを、翻訳の実装より先に置く
翻訳表が誤っても、テストが同じ翻訳表を使って書かれていれば全件緑になる。2026-08-01に実際に起きた事故と同型の条件であり、契約ファイルが採った対策（値を実装から生成しない）を同じく適用する。
tech-lead-advisor

StoredSharedArtifactRepository の docstring は「記録と保管の間の変換をここだけが知る」と述べているが、実際にあるのは鍵の組み立てと JSON 化だけで、変換は1行も無い。この回で実装するのは、docstring が既に存在すると宣言している機能である。

オーケストレータ
安全網は既に張ってある
集約の不変条件12件すべてが、それを検証しているテストと結びついている（test_manage 5件・test_view_tokens 7件）。属性名を動かしたときに何が壊れたかを、宣言の言葉で言える。
1

check-aggregate-class-drift は、宣言された値オブジェクトをすべて集約ルートと同じファイルの中で探す。ViewTokenId / ViewTokenExpiry / ViewTokenStatus は両方の集約に宣言されているので、この要求に従うと同じ語が2回定義され、ユビキタス言語を壊す。実装は domain/view_token.py を両方が共有する形を保つ。この3件は missing_value_object として報告され続けるが、既知の非両立として扱い、緑にすることを完了条件に含めない。検査側の修正（VO の探索範囲を value-object の placements から取る）は Waffle 本体の変更なので別サイクル。

2

保管の欄名（name / uploadedBy / contentHash / metaSource / externalRefs / wrapperHash）は変えない。repository が翻訳するので既存データの移行は不要。変えるのは domain と application が使う語彙だけ。

3

応答の status の値（"active" / "disabled"）も変えない。管理画面が7箇所で読んでおり、変えるなら app.js を同時に直す必要がある。domain の PUBLISHED / SUSPENDED との対応は受け口が翻訳する。

4

Project.memberArtifactIds を集約の属性から外したが、保管の記録には残る。repository はこれを集約の状態としてではなく、一覧を組み立てるための投影として扱う。全共有アーティファクトを走査して作り直す経路は、この回では実装しない。

5

wrapperHash を集約の外へ出すと決めたが、いまは meta に書いている。閲覧の面の側へ移す作業はこの回に含めるか、含めないなら明示的に次へ回す。

6

agg-comment の判断は保留する。この集約を作るコードは admin_api に存在せず（uc-post-comment は閲覧の面が担う）、比較対象を誤る。_record_id が鍵から識別子を復元している件だけは admin_api 側の事実として記録できる。
