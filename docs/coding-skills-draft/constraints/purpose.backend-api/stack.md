# バックエンドAPI の技術構成

## 概要

**中心が外部の機能を必要とするので、反転を持つ構成を採る。**

## 採用するアーキテクチャ

| 軸 | 値 | 採用理由 |
|---|---|---|
| アーキテクチャ | `hexagonal` | 業務の判断が外部（記憶・通知・他のサービス）を必要とし、依存の反転が要る |
| 実行環境 | `resident` | 常駐して要求を受け続ける |

**`data-port` を採らないのは、中心が外部の機能を呼ぶためである。**

## 採用する依存

| 用途 | 依存 | バージョン指定 | 採用理由 | 代替候補 |
|---|---|---|---|---|
| HTTP の受け付け | 標準ライブラリ `net/http` | 言語に同梱 | 経路の宣言と処理の登録に足りる | 経路の記述が複雑になったときに框組みを検討する |
| JSON | 標準ライブラリ `encoding/json` | 言語に同梱 | 契約が JSON で、型と対応づけられる | 速度が問題になってから替える |
| 記録 | 標準ライブラリ `log/slog` | 言語に同梱 | 構造化した記録を標準で出せる | ─ |
| 記憶への接続 | **未定** | ─ | **扱うデータの形と量が決まっていないため、まだ選べない** | ─ |

## 採用しない依存

| 依存 | 採用しない理由 |
|---|---|
| 大きな Web 框組み | 経路と処理の登録は標準で足り、框組みの作法が層の規約と競合する |
| 独自の依存注入の道具 | 結線は `cmd` で明示的に書く。道具を挟むと、依存の向きが読めなくなる |

## バージョンの固定

| 対象 | 固定の方法 | 固定するファイル |
|---|---|---|
| 言語 | `go` 行に最小版 | `go.mod` |
| 依存 | 版とハッシュ | `go.mod` ・ `go.sum` |

## 実行コマンド

| 目的 | コマンド | 実行する場面 |
|---|---|---|
| ビルド | `go build ./cmd/...` | 配布時 |
| 起動 | `./bin/api` | 実行時 |
| 端から端までのテスト | `go test ./test/e2e/...` | CI |

## 適用範囲外

| 何を | どの層が決めるか |
|---|---|

| 何台で動かすか | 運用（この規約の外） |
