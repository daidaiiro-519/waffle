## 発端

卒業制作（`spec-correspondence`）のデッキの「おまけ」で述べた4つの主張 ── テンプレートを渡すことは構造の推論までAIに任せること／構造はスキーマで持ち中身だけを推論させる／具体する高さを誤ると犬が猫になる／ナレッジと規約とシナリオが仕様と実装をつなぐ ── を実装できる形まで詰める過程で、**「AI時代の構造化文書のためのスキーマ層」を仮に `Kata` と名付けて設計し、原型を作って測った。**

その途中で、**それが Waffle の思想と同じであることに気づいた。** そこから「Kata と Waffle は schema をどう捉えているか」という比較に移り、最終的に**三層のメタ構造**に着地した。

**注意:** Waffle は再定義の最中である。この記録で Waffle の現状に触れている箇所は「いま何があるか」を数えたものであって、「どうあるべきか」の根拠には使っていない（`feedback_redefinition_does_not_reason_from_the_existing`）。**その規律を、この作業中に実際に破って5往復ぶん取り下げた。** 経緯は §5 にある。

## 1. 三層は、抽象と具体ではなくメタレベルである

```
abstract schema   ──  concrete schema を検証し、構造を決める      （段1）
concrete schema   ──  文書エンティティを検証し、構造を決める      （段2）
文書エンティティ    ──  値が推論で埋まる
```

**`concrete schema` は `abstract schema` のインスタンスであり、同時に文書の型でもある。** この二重の役が核心で、JSON Schema 自身が meta-schema を持つのと同じ形。

当初は「schema は厚い一枚か、薄い核＋複数の契約か」という問いを立てていたが、**これは誤りだった。** 厚い／薄いは同じ階層での責務の配分の話で、実際に起きているのは階層が1つ増えることである。厚さを比べても、この構造は出てこない。

### 「値だけを推論させる」は再帰する

| 何を書くとき | 構造を縛るもの | 推論に載るもの |
|---|---|---|
| 文書エンティティ | concrete schema | 値だけ |
| **concrete schema** | **abstract schema** | **欄の設計だけ** |

**`concrete schema` を書く行為そのものが構造の推論である。** domain schema を新しく起こすとき、いま人とAIが「どんな欄が要るか」を推論している。それを縛るのが `abstract schema`。

**これが段1の存在理由になる。** 共通部分をくくり出したのではなく、同じ原理をもう1段上に当てている。

## 2. 単位は、読み手に従属する（論点2・決着）

「世界の単位は文書か、1つのグラフか」という問いは**偽の二択だった。**「単位」という語が4つの別物を指していた ── 人が読む単位／検証と状態の単位／取得と参照の単位／保存の単位。

| 読み手 | 認知の条件 | だから形式は | だから単位は |
|---|---|---|---|
| **人間** | ビジュアライズされていないと認知できない | MD ／ HTML | **文書** |
| **AI** | 形式を気にしない。構造の明示と読み方が与えられて初めて従う | 何でもよい | **節** |

**検証・状態・承認は人間が読むので文書単位。取得・参照は AI が行うので節単位。**

境界を残すと動詞が二重になる（単一document用と横断用）という懸念には答えがある。**二重になるのは取得だけで、取得と参照だけを節の粒度に統一すれば動詞は1本になる。** 検証と状態は文書単位のまま残してよい。

### 代償

**文書をまたぐ規則の置き場所が無くなる。**「この仕様が指しているユースケースは実在するか」は、どの1つの文書のスキーマでも検証できない。範囲が文書を超えているためである。**これが論点6の入口になる。**

## 3. 構造と意味について、合意した3点

**① 構造が意味的空間になるのは、命名が守られているときだけである。**
構造は型を保証するが、意味は保証しない。`invariants[]` に不変条件でないものが書かれても検証は通る。`items` のように名前が意味を運ばない鍵では、自明性そのものが消える。**だから書き方の指示とセットで初めて意味的空間になる。**
帰結として、**意味は検証できない。** だから最後に人の承認が残る ── Human On The Loop が消えない理由がここで説明できる。

**② 構造化の利得は「無いことが分かる」ことである。**
grep は「見つからなかった」と「無い」を区別できない。探し方が悪かったのか本当に無いのかが決まらない。構造で引けば「その欄が空である」と言い切れる。**不在が観測できるようになる。**

**③ 取得は冪等でありうる。**
プロンプトは意図しか運べず、スキーマは手段を運べる。grep → 周辺から推論 → 横断のループは毎回違う経路を通り、**同じ問いに同じ範囲が返らない。**

```
スキーマが縛れるもの
   ↓                    ↓ 届かない            ↓
問い ──取得──→ 渡す範囲 ──推論──→ 値 ──射影──→ 文書
      冪等              冪等でない        冪等
```

**スキーマは両端を縛れるが、真ん中には届かない。** だから真ん中の揺れを減らす方法は、真ん中を直すことではなく入口を固定することになる。**取得が揺れると推論の入力が毎回変わるので、値の揺れはその手前で増幅されている。**

## 4. JSON Schema に足りないもの（6つ）

| 足りないもの | JSON Schema が持つもの | なぜ足りないか |
|---|---|---|
| 同一性 | 型の判定 | 「この節が**何であるか**」は言えるが「**どの個体か**」を持たない |
| 書き方の指示 | `description` | `x-` に載せるしかない。**そして構造化出力は `x-` を拒む**（実測） |
| 操作 | 検証だけ | 引き方・書き方のコマンドが無い |
| 射影 | ── | 出力先・出力形の概念が無い |
| **実体どうしの参照** | `$ref` | **`$ref` は型の再利用であって、インスタンス間の参照ではない** |
| 版と移行 | `$id` | 版は言えるが、実体を移す意味論が無い |

## 7. まだ論点

### 論点3　同一性（問いが変わった）

論点2の決着で「名前か、変わらない印か」という問いは死んだ。いまはこうなる。

> **AI が引く節に、人が読む文書とは別の同一性が要るか。**

文書には同一性がある（パス・ID）。**節にも要るのかが問い。**

参考として、いま仕様と実装を結んでいる鍵は「Scenario: {シナリオ名}」という文字列と、ユースケースのファイル名である。**どちらも改名で切れる**（これは数えた事実であって、あるべき形の根拠ではない）。

### 論点6　規則を、コマンドで持つか宣言で持つか

`abstract schema` がクエリとコマンドを固定すると、`concrete` 固有の規則の行き場が問題になる。

| 案 | concrete が1つ増えたとき |
|---|---|
| **A コマンドで持つ** | 新しい型が `abstract` へ動詞を足しに行く。**型が増えるたび `abstract` が太り、固定した意味が薄れる** |
| **B 宣言で持つ** | 従うだけで済む。**ただし `abstract` に「何が違反かを書く語彙」が要る** |

**この記録での見解は案B。ただし線が引けていない。** 宣言で書ける規則と、走査・構文解析・依存グラフの循環検出のような**能力を要する検査**の境界。**その線をどこに引くかが、この論点の実体である。**

### 書く単位と承認する単位のずれ（新規）

AI は読み手であると同時に書き手である。**書く単位は節**（欄を埋める）、**承認する単位は文書**（人が1本として読む）。「どこまで書いたら人に見せるか」は節の数では決まらず、文書が閉じたときに決まる。**このずれが Human On The Loop の境界そのものである。**

## 8. 未採用の提案（要判断）

- 節に**不変の印**を持たせ、突き合わせの鍵をそこへ移す。名前を鍵にすると2方向に間違える（改名で偽陽性、中身の入れ替えで偽陰性）
- **版の移行**を、閉じた操作集合の宣言として持つ（欄の改名・削除・型変更・子の許可・種別の改名・欄の追加）。既定値の無い追加だけが「穴」として残り、そこだけ推論が入る
- **参照に型と解決状態**を持たせる（実体を指す／実装を指す／外部を指す。および「検めない」という第3の状態）
- `abstract schema` に**「何が違反かを書く語彙」**を置く（論点6を案Bで閉じる場合）
