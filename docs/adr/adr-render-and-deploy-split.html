Architecture Decision Record

描くことと、配ることを分ける

いま1つのユースケースが、成果物を描くことと、各ツールが見える場所へ置くことの両方を持っている。受け入れ基準49件のうち12件が配置についてのものである。この記録は、その2つを別のユースケースへ分ける。

01決定

Waffle は、描くことと配ることを別のユースケースとして分ける。描く側は、document と schema だけを入力に取り、成果物を正本の1か所へ置く。配る側は、使う側の宣言に従って、各ツールが認識できる場所へ置く。

決め手knowledge の正本は1か所だが、読む側は多い。描く側が読む側を知る形にすると、描画のたびに他の document を走査することになる。描く側が多を知らずに済むのは、配る側だけが多を知るときである。

02変更前と変更後

この決定が変えるのは、描く側が何を知る必要があるかである。描き方そのものは変えない。

変更前 ── 1つが両方を持つ変更後 ── 2つに分かれる
描く側が知るものdocument・schema に加えて、配置先を解く材料document と schema だけ
描画のユースケースの受け入れ基準49件（うち配置が12件）37件
配置だけのやり直しできない。描き直すことになるできる
描いてから配られるまで1回の呼び出し2回の呼び出し
読む側が多い document描く側が多を知る必要がある配る側だけが多を知る

03理由

描画のユースケースの49件のうち12件が配置についてのもので、その境界は独立して失敗し、再利用され、許可も別である。

測った描画のユースケースが持つ受け入れ基準49件のうち、12件が配置についてのものだった。描画そのものは37件である
その12件を分けてよいかを、境界の実在性で当てた
測った独立して失敗する ── 配置にだけ起きるエラーが既にある（配置先が他の document に所有されている場合）。再利用される ── 指し示しが切れたとき、描き直さずに張り直したい。許可が別 ── 描画は所有権を見ないが、配置は見ている
だから
言えること描くことと配ることは、潰してはいけない境界で隔てられている
実際に症状が出た
測ったknowledge の参照の向きを直そうとしただけで、描画のユースケースへ手が伸びた。一度は「描画に他の document を読む力を足す」という設計まで書いた。一つの操作が能力を持ちすぎているときに出る症状である
合わせると
結論描くことと配ることを、別のユースケースとして分ける
ただし
反証配るのは指し示しなので、中身の更新は張り直さなくても届く。しかし読む側が宣言から外したとき、指し示しは自然には消えない。読まなくなったものを読み続ける状態が残りうる
段の裏付けと、崩れるときを開く（4件）
段裏付けの種別参照先崩れるとき
49件のうち12件が配置実測描画のユースケースの受け入れ基準を、配置に触れるかどうかで数えた配置に触れる基準が、描画と不可分だと分かったとき
配置にだけ起きるエラーがある実測所有権の衝突を表すエラーが、配置の側にだけ定義されている—
潰した境界は症状を出すknowledgespec-implementation-abstraction ── 「a.b が必要なのに a まで圧縮すると、分ける必要がある境界を無視することになる。症状は、一つの操作があらゆる能力を持ちすぎること」この knowledge はまだ DRAFT である。配布の経路が整うまで、参照先として不安定
境界の実在性を3つの問いで測るWaffle の設計判断knowledge に該当なし—

最後の段に knowledge の裏付けが無い理由 ── spec-implementation-abstraction は「潰すと境界が消える」とまでは言うが、ある境界が実在するかをどう見分けるかは持たない。ここで使った3つの問い（独立して失敗するか・再利用されるか・許可が別か）は、この決定のために置いたものである。この判定の道具は、knowledge へ戻すべきものと考えている。

05付随して決めたこと

分けると、それぞれが何を知るかが決まる。4点を同時に決めた。

論点決定
配る側が知るもの使う側の宣言。描く側はそれを知らない
正本の場所1つの document につき1か所。参照元が多くても、描く場所は増えない
実行時の読み込みどちらの責務でもない。Orchestrator・Skills・セッション開始のフックが担う
Ref に書けるものACTIVE のものだけ。作りかけのものは、読む側の宣言に載せられない
それぞれの根拠を開く（4件）
論点根拠
配る側が知るもの参照の向きを読む側からの一方向にすると決めた（承認済み）。その宣言を読むのは、配る側だけでよい
正本の場所描く場所が参照元の数だけ増えると、どれが正本かが決まらなくなる。1か所に固定すれば、配られたものはすべてその写しか指し示しになる
実行時の読み込み索引を読んで概要を把握する行為は、成果物を作る行為ではない。仕様ではなく、実行時の振る舞いとして宣言する
Ref に書けるもの作りかけのものを宣言に載せられると、配る側は「まだ確定していない場所」へ指し示しを張ることになる。正本の場所は状態を含むため、状態が変われば指し示しが切れる。ACTIVE になってから登録する順序にすれば、切れる場面がそもそも生じない。

06答えないこと

配る側の中身と、移す手順は、この決定では扱わない。

項目種別行き先
配るユースケースの受け入れ基準範囲外そのユースケースを起こす段で決める
12件をどう移すか範囲外移す作業として別に行う
宣言から外したとき、指し示しをどう剥がすか限界行き先を持たない。配る側が「宣言に無いものを剥がす」まで担うかは、配るユースケースを起こす段で決める
knowledge の状態をいつ変えるか範囲外knowledge を作り育てる側の責務。この決定は配ることだけを扱う
