集約の宣言と集約クラスの存在は別のことaggregate-declaration-is-not-class-existence

概要

集約は一貫性の境界であって、クラスであるとは定義されていない。クラス化は不変条件をカプセル化して複雑さを減らす手段であり、複雑さが無い領域では空振りする。集約は、厚いモデルを組まない領域ではトランザクション境界として現れる。

この概念が答える判断
  • spec が集約を宣言したとき、実装に集約ルートのクラスが存在しなければならないか
  • 補完サブドメインで厚いドメインモデルを組まないとき、宣言した不変条件は何が守るのか
  • サブドメイン分類を、検査の適用条件として直接使ってよいか
  • 宣言と実装の対応を機械的に確かめるとき、何を対象にすべきか
原則
  • 集約の定義は「1つのトランザクションで変更される一貫性の境界」であり、クラスであることは定義に含まれない。クラス化は不変条件をカプセル化するための手段である。
  • 手段が有効なのは、カプセル化すべき複雑さがあるときに限られる。状態遷移も業務ルールの絡み合いも無い領域でクラスを要求すると、不必要な階層を増やすだけになる。
  • 厚いモデルを組まない領域でも、集約の境界は消えない。クラスという器を失うだけで、境界はトランザクションの粒度として残る。守り手はクラスからトランザクション境界へ移る。
  • したがって「集約を宣言したのにクラスが無い」ことは、それ自体では欠陥ではない。欠陥は「宣言した不変条件を、クラスもトランザクション境界も守っていない」ときに生じる。
  • サブドメイン分類は、実装方法を決める一段上流の判断であり、実装形を直接決めない。分類と実装形の間には「業務ロジックの実装方法」という中間項があり、そこを飛ばすと取りこぼしが出る。
  • 分類は設計時の判断基準であり、検査の分岐条件へ転用すると、分類を1語書き換えるだけで検査が静かに無効化される。転用するなら中間項を経由する。
分類
  • クラスとして現れる ── ドメインモデル／イベント履歴式。集約ルートがクラスとして実装され、状態変更経路が自分のメソッドに絞られる
  • データ構造のクラスとして現れる ── アクティブレコード。データ構造はカプセル化されるが、不変条件のカプセル化までは要求されない
  • トランザクション境界として現れる ── トランザクションスクリプト
判断基準

配信の端で守るときのブラウザ側の信頼境界edge-delivery-browser-trust-boundary

概要

配信網（CDN）の端で誰が見てよいかを判定し、持ち込まれた HTML を同じ配信元から配る構成では、守りの主語がサーバーではなくブラウザになる。ブラウザが何を同じ出どころ（オリジン）とみなすかが設計の土台になり、指定の掛け方ひとつで、守るつもりだった画面自身が壊れる。

原則（12件のうち主要なもの）
  • 端で判定するとき、判定に使える材料は、あらかじめ計算して端の保管へ置いておけるものに限られる。端では網の外へ問い合わせられず、動かせるコードの大きさと時間にも上限があるため。
  • 取り決めが2か所に別々に実装されると、両方が同じ誤解でずれたとき、どちらの検証も落ちない。取り決めを1つの表として外へ出し、両側の検証がその表を読む形にして初めて、ずれが検証で現れる。
  • 隔離の指定（CSP の sandbox）は、それを受け取った文書自身に掛かる。囲う側が囲われる側を閉じ込める指定（iframe の sandbox 属性）とは向きが逆であり、混同すると閲覧画面自身を閉じ込める。
  • 隔離された文書は不透明な出どころを持つ。自分自身への問い合わせすらオリジンをまたぐ扱いになり、保管領域への読み書きは例外になる。つまり、その画面の機能が静かに全滅する。
  • すべてを1つの出どころにまとめると、オリジン間の取り決め（CORS）は要らなくなる。要らないのは省略したからではなく、またぐものが無いからであり、この不在は構成が担っている性質そのものである。
  • コマンドラインからの確認は、隔離の指定・オリジン間の取り決め・手元の記録の送出条件のいずれも解釈しない。この構成でブラウザが担っている守りの半分は、その確認からは構造的に見えない。

社内の設計文書を、招かれた人だけが上げ、合言葉を渡された人が読める仕組みを考える。読む人には利用者登録を求めない。 閲覧のたびに裏側を起こさずに済むよう、合言葉の照合は配信網の端で行う。端では外へ問い合わせられないので、照合できる形（ハッシュの先頭・期限・世代番号を並べた1行）をあらかじめ端の保管へ置く。この1行の形が、上げる側と端の取り決めになる。 ここで最初の落とし穴が来る。取り決めが両方の実装に別々に書かれていると、片方が「保管にはハッシュが入っている」、もう片方が「合言葉がそのまま入っている」と思い込んだまま、両方の検証が緑で通る。実際に、正しい合言葉でも開けない状態が、全検証を通り抜けて本番でだけ現れた。 次に、持ち込まれた HTML を配る。隔離の指定を配信全体へ掛けると、閲覧画面自身にも掛かる。閲覧画面は不透明な出どころになり、自分のコメント欄が自分の保管先へ書き込めなくなる。指定は経路の形で切り分け、持ち込まれたものにだけ掛ける。 3つ目は、確認の仕方そのものにある。コマンドラインから叩くと、どちらの掛け方でも応答は返る——隔離の指定は解釈されないからだ。全部通ったという結果を「通しで動いた」と読むと、ブラウザでだけ壊れている状態を出荷することになる。

第一級の概念として立てる要求と、早すぎる一般化を避ける規律の衝突first-class-concept-vs-premature-generalization

概要

『振る舞いが異なるなら別概念として名前を持たせよ』という設計原則と、『実例1件から一般化するな』という規律は、同じ変更に対して逆の結論を出すことがある。両者の射程を分けて裁くための着眼点を扱う。

原則
  • 『別概念として名前を持たせよ』は概念の同定に関する原則であり、その概念をどの構造で表すか（種別の値か、直交する属性か）までは決めない。
  • 『実例1件から一般化するな』は、まだ形の分からない変種を先回りして吸収する汎用機構（ポリシーエンジン・DSL・設定駆動の分岐）を対象とした警告である。列挙値や属性を1つ増やす行為は、この警告の射程外である。
  • 両者が衝突して見えるときは、提案されている変更が『名前を与える』側なのか『未知の変種を吸収する枠組みを作る』側なのかを判別すると、多くの場合いずれか一方の射程にしか入らない。
  • 概念を種別の値として表すと、その種別に対応する内容の形を定義する義務が生じる。内容の形が既存の値と同一になる場合、それは種別ではなく直交する軸であるという徴候である。
分類
  • 名前を与える変更 ── 既に観測されている振る舞いの違いに、正式な識別子と構造上の居場所を与える。実例1件でも成立する
  • 枠組みを作る変更 ── まだ観測されていない変種を吸収できるよう、汎用の記述手段を用意する。実例が複数必要
判断基準

空。理由が明記されている ── 「分岐の形はまだ1事例からしか得られておらず、判断の分岐点として構造化するには早い。採用審査で複数事例が揃った時点で構造化する」

実例
ある文書基盤で、他プロジェクトへ移植するための雛形文書が実運用中の文書と同じ配置先を奪い合う事故が起きた。設計原則の側からは『雛形は責務の異なる別概念だから正式な名前を持たせよ』、規律の側からは『雛形は今1件しかないので一般化するな』という逆の助言が出た。 判別してみると、前者は名前を与える変更を指し、後者が想定していたのは『配置先を任意に記述できる汎用ポリシー機構』であり、両者は別のものを対象にしていた。結果として、名前は与えるが汎用機構は作らない、という形に落ち着いた。 さらに、その名前を種別の値として足すと雛形の内容の形が実運用文書と同一になることが分かり、種別ではなく直交する属性として表すべきだと判明した。
注意（自己申告）

「実例が1件のみであり、この着眼点自体がまだ一般化に足るかは未検証。他の衝突事例で同じ判別が効くかを確認する必要がある」

テーゼ層の比喩でも価値の言い切りは免除されないmetaphor-must-still-say-the-thing

概要

テーゼ・見出しレベルの比喩はレジスタとして許容されていても、読者がその一文単独で製品の価値・行為を理解できるかは別に検査すべきという、生成物コピーの敵対的検証観点。

原則
  • 既存の copy-register-discipline は「比喩がテーゼ・見出し・図の視覚表現に留まっているか」というレジスタの軸で判定する。この概念は別軸であり、レジスタとして許容される見出し・テーゼ自身についても、読者が価値・行為を具体的に理解できるかを独立に検査する。
  • 見出し・リード文が語感の良い比喩1つだけで構成されていると、書き手は『それらしく聞こえる』ことと『読者が製品の価値を理解できる』ことを混同しやすい。両者は独立した基準である。
  • 検査は「その一文だけを読者が初見で読んで、何をする製品で、何が嬉しいのかを言えるか」を自問する形で行う。
  • 比較・対比構造は具体性を担保する手段の1つだが必須ではない。対比が本質的な悩みを覆い隠す場合は、対比自体をやめて悩みと解決を直接言い切る一文の方が明快になりうる。

業務ユースケースの受け入れ基準は、業務サービスの写像を言い直さないusecase-does-not-restate-service ── 今日作成

概要

業務ユースケースと業務サービスの両方に同じ主張が書かれているとき、その重複をどちらかの削除で解消しようとすると、片側にしか言えないことまで一緒に落ちる。境界は数ではなく「その主張は業務サービスに言えるか」で引く。

原則
  • 業務ユースケースが主張すべきなのは、業務サービスには言えないことだけである。写像そのものは業務サービスが持ち、業務ユースケースは「どこから何を取るか」「解決できないときどうするか」「書き込みの結果」を持つ。
  • 重複を見つけたときの正しい直し方は削除ではなく、境界の引き直しである。1つの文が両方の性質を含んでいることが多く、削ると片側にしか言えないことまで落ちる。
  • 削除の可否は、1件ずつ「削ると誰も主張しなくなるものは何か」を問うて決める。重複という括りでまとめて落とすと、数は減るが主張が欠ける。
  • 純粋な計算を業務サービスへ委譲した業務ユースケースでは、委譲した計算の意味論を業務ユースケース側で繰り返さない。
