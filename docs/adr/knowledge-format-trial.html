Ⅰ. 全体像

knowledge 文書は「1つの概念に固定のブロックがぶら下がる」形ではなく、概念の木でした。ノードが子ノードを持て、各ノードが文・図・表・原文を持てる。それだけです。

ノードの形再帰する単位

{
  "name":      // 概念の名前
  "kind":      // 定義 / 分類 / 判断基準 / 実例 /
                // 対比 / 補足 / アンチパターン / 関連
  "sourceRef": // 図1-3、1.2.3.3 など出典の位置
  "summary":   // 文章（常に必須）

  // 以下は在るものだけ
  "figure":    // 節点と関係の宣言
  "table":     // 見出しと行
  "verbatim":  // 規則性の無い原文
                // ＝コード・象限図など

  "children":  // 子ノード（深さ3まで）
}

図の形単独では置けない

"figure": {
  "intent":   // 何を示す図か（必須）
  "reading":  // 図から何が言えるか（必須）
                // ← 描画しなくても意味が取れる文
  "direction": // LR / TD
  "groups":   [{ label, nodes[] }]
  "nodes":    [ ... ]
  "edges":    [{ from, to, label?, means? }]
}

// 描画側は、図と一緒に
// 「関係の表」も必ず出す

"verbatim": {
  "intent":   // 何を示す例か（必須）
  "reading":  // そこから何が言えるか（必須）
  "lang":     // csharp / mermaid / sql …
  "source":   // 原文（変換しない）
}
// 原文のまま持つことと、描画できることは
// 両立する（mermaid ならそのまま描ける）

規則性のあるものは構造に、無いものは原文のまま

実測で分けました——図42個と表は構造に（節点と矢印という規則がある）、コード31個と象限図1個は原文のまま（規則が無い）。ただし原文側にも「何を示す例か」を必須にします。今回の欠落は何が大事かがどこにも書かれていなかったために起きたので、それをその場に書かせます。

Ⅱ. Schema の変更点

いま（KnowledgeSchema/v5）平らな8ブロック

KnowledgeContent {
  description
  principles        // 文字列の並び
  classifications   // name + description
  decisionCriteria  // stages + transitions
  examples          // text（1つだけ）
  antiPatterns      // name + problem
  provenance
  relatedConcepts
}

// 子を持てない
// 図・表・コードを持てない
// 出典の位置（図1-3）を持てない

提案（v6）木＋3つの持ち方

KnowledgeContent {
  description
  nodes[]           // ConceptNode の並び
  provenance
  relatedConcepts
}

ConceptNode {
  name / kind / sourceRef / summary
  figure? / table? / verbatim?
  children[]        // ConceptNode（深さ3まで）
}

// 既存の5ブロックは kind として残る
// → 語彙を捨てず、木の中の役割になる
変更理由由来
5ブロックを nodes[] に畳む見出し372件のうち227件が「下位概念の名前」で、平らなブロックには置けない実測
children[] を有界に再帰させる親の下に最大10個の子。深さ4（#〜####）実測 ＋ agg-schema の不変条件「再帰は常に有界」
figure を足す図42個。節点と矢印という規則がある既存 completionImage と同型
figure.intent / reading を必須にする図だけでは読み手が意味を取れない。書き起こし版でも83%は説明文が添えられていた実測
table を足す表164行。比較表は knowledge の骨格実測
verbatim（言語＋意図＋読み取り＋原文）を足すコード31個・象限図1個。構造化すると肝が消える。ただし図と同じく読み取りを必須にする——原文だけでは意味が取れない実測
sourceRef を足す「図1-3」「1.2.3.3」を持てないと、原本に当たれない今日、当たり直しに苦労した
実例は抽象化して置き換える（規則として明文化）著作権への配慮。書籍固有の企業例・図版は用いず、教材用の架空ドメインへ置き換える。ただし図が示す関係の構造は保つ——置き換えて構造まで崩れると、示していたことが消える要約版の provenance が既に同じ方針を明記していた

業務領域（サブドメイン）とは定義

企業の事業活動全体を細分化した個々の業務活動の単位。すべての業務領域が連動することで顧客へのサービス提供活動が成り立つ。

3つの分類分類

業務領域は中核・一般・補完の3つに分類される。

中核の業務領域（Core）分類

競合他社との差別化を生み出す業務活動。他社がまねできない独自製品・サービス・業務プロセスの最適化が対象で、必然的に複雑になる（単純なら競合がすぐ追いつける）。継続的な革新・進化が必要で「完了」がない。社内開発必須で、外部委託・パッケージ利用は戦略的リスク。

一般的な業務領域（Generic）分類

どの企業も同じやり方で解決する業務活動。競争優位を生まないが事業運営に不可欠。業務知識の観点では「わからないことがわかっている」領域。実績あるパッケージ製品・クラウドサービスで賄え、自社開発より既製品の活用が費用対効果で優れる。

補完的な業務領域（Supporting）分類

事業活動を支えるが、競争優位を生まない業務活動。業務ロジックが単純（基本的に CRUD・ETL 操作）で、他社も同じことを簡単にできる。社内開発でもよいが外部委託も有力な選択肢で、成長途上の若手技術者の育成の場として活用できる。

細分化の焦点補足1.2.3.3

業務領域を探す時はソフトウェアが関係しない業務機能を特定して除外することが役に立つ。ソフトウェアが関係しない業務を識別できれば、取り組んでいるソフトウェアシステムが対象とする業務領域に集中できる。

「コアドメイン」という別の呼び名補足

文献によって「コアドメイン」と呼ぶものと「コアサブドメイン」と呼ぶものがある。この knowledge では「中核の業務領域」で統一する。理由は2つ——(1) 議論しているのはサブドメインであり、ドメイン全体との混乱を避けたい。(2) 分類は変化するため、「中核の業務領域が一般の業務領域に変わった」のほうが意味が明確になる。

アンチパターンアンチパターン
中核をパッケージに外注する

中核の業務領域のソフトウェア開発を外部委託すると、短期的には安く見えるが長期的には会社の存続に関わる問題を引き起こす。変更がやりにくく危険なコードベースになり、事業目標の達成を技術面で支援できなくなる。

組織図でサブドメインを決める

部門名（「顧客サービス部」など）でサブドメインを決めると粗すぎる判断になる。業務の細部に重要な情報が隠れており、細分化してはじめて中核・補完・一般が見えてくる。

細分化をやりすぎる

分割しても設計判断が変わらないなら、その分割は必要ない。「分割した後のカテゴリーがすべて分割前と同じ」なら意味がない細分化。
