svg_engine ── ADR

図を、部品として置けるようにする

図の仕様は「対応」の要素が自分と同じ形の子図を持てると定めている。ところが描く側は、 組み立てと器づけが1つの関数に入っていて、必ずルートタグを返す ── だから図を他の図の中へ置けない。 器づけを外すだけで置けるようになることを、測って確かめた。

01何が塞がっているか

確かめたこといまどうなっているか
図を「断片」として作れるか 作れない。組み立てと <svg> の器づけが1つの関数に入っている
配置戦略を差し替える継ぎ目ある。層状・環状・放射の木が同じ契約で入れ替わる
戦略へ座標を渡せるか 渡せない。戦略が受け取るのは大きさと辺だけで、格子のどこかを知る道が無い
入れ子を要求している宣言 対応の figure。階層・包含の children は要素の入れ子で、平らにして辺へ写せている

02決めること ── 3層

概念図は、その要素として図を持てる
何が成り立てばそう言えるか
満たすべき性質 子図の中で守られている性質（辺がインクに着く・文字が重ならない）が、入れ子にしても壊れない。 親は子図の実際の大きさを知って場所を取る
それを保証する唯一の手
アルゴリズム 子図を先に描いて（中身・幅・高さ）にし、親はそれを大きさの分かった1つとして置く

この「中身・幅・高さ」は、部品の契約そのものである。 つまり必要なのは新しい仕組みではなく、図が部品になれることだけ。

03測ったこと ── 図はすでに部品の条件を満たしている

実測申告した大きさから、インクは出ていない

15枚すべてで、インクが viewBox から出た量は 0.0。 器づけの直前に、囲みのはみ出し・迂回した辺・札まで含めて外形を出し、原点を寄せているため。 部品に課している契約（申告した大きさがインクを含む）を、図は既に満たしている。

いまの形器づけは、末尾の34行だけ 
def render_figure(...):
    …組み立て（宣言 → body）… 257行

    # ここから器づけ 34行
    外形を出す（囲み・迂回・札を含む）
    原点を寄せる
    return f'<svg viewBox=…>{inner}</svg>'

外形を出す部分は、器づけではなく「申告する大きさ」の計算である。 つまり分けたときに捨てるものが無く、<svg> を被せる3行だけが上に残る。

04決定

決めること決定
図を部品として作れるようにする 組み立てと器づけを分ける。組み立ては（中身・幅・高さ）を返し、器づけはそれに <svg> を被せるだけにする。いまの呼び出しは変わらない
子図をどこへ置くか 親の要素が子図の宣言を持てるようにし、合成が再帰して大きさの分かった1つにする。 描き上がったものを外から渡す形にはしない ── props は構造だけという契約を破らないため
対応（格子）の配置 格子の配置戦略を1つ足す。座標を戦略へ渡す道を作る ── いまの戦略は大きさと辺しか受け取らない
入れ子の深さ 上限を持つ。段1 が「入れ子は深さに上限を置く」と定めているので、それに従う。値は型が宣言する

05やってみて分かったこと

決めたこと実際にどうなったか
組み立てと器づけを分ける 器づけは3行になった。外形を出す部分は「申告する大きさ」の計算だったので、 そのまま組み立ての側に残った。呼び出しは1つも変えていない
座標を戦略へ渡す道 契約を広げずに済んだ。差し替えの継ぎ目（layout=）へ、座標を束ねた戦略を 渡せばよい ── partial(layout_grid, at=…)。予想より軽かった
格子の並び 整列に頼ると見出しが中ほどへ紛れ込むので、列と行の並びを外から渡せるようにした
セルが名前と子図の両方を持つ 名前が落ちていた。「名前の節点＋子図の節点」をもう一段の子図として包んで解いた ── 足した仕組みを、そのまま使えた

06答えないこと

問いここで答えない理由
階層・包含の children も入れ子の図にするか あちらは要素の入れ子で、平らにして辺へ写せている。壊れていないものを変えない
格子のセルの大きさをどう揃えるか 子図の大きさはまちまちになる。行・列で揃えるか、いちばん大きいものに合わせるかは、 実際に不揃いな子図を並べてから決める

状態承認済み（2026-08-29） 実装済み・実測済み。組み立てと器づけを分け（器づけは3行）、節点が子図の宣言を持てるようにし、格子の配置戦略を足した。深さの上限はトークンで持つ。184試験通過。対応の入れ子が、宣言の文字を1つも落とさずに描けるようになった。
