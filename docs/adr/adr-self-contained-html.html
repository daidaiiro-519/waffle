Any Decision Record — 関門1（仕様への橋渡し）

配る成果物を、外部ホストから切り離す

Waffle が render で出す HTML は、いま閲覧のたびに外部ホストへ要求を出しています。これを断つかどうかを決めます。

01決定block 01

Waffle が render で出す HTML は、外部ホストへ一切要求を出さない。図の描画も含め、開いた時点で完結している。

主文だけでは読み方が定まらない箇所を、同時に確定させる。

確定させること決定定めないと
図をいつ描くか組み立てるとき。閲覧時ではない「外部から読まない」だけでは、描画ライブラリを同梱して閲覧時に描く形も適合してしまう
及ぶ範囲HTML の成果物のみ。Markdown は従来どおり Mermaid のまま図の記法そのものを変える決定と読まれる
版の固定別途の決定を要さない。外部を踏まない以上、描画の版は組み立て時に固定される「版を固定する」がもう一つの決定として残り、どちらが先か決まらない

02理由block 02

決め手は、配信先を選べないこと。

外部ホストを踏む成果物は、外部を止める面へ置いた瞬間に図が消えます。artifact-share がその面で、今回それを実測しました。
不利益は他にもあります。ただし他はどれも程度を下げられる——版を固定すれば再現性は上がり、控えを持てば配信元の消滅に備えられ、事前に取っておけばオフラインでも開ける。下げられないのは「開いても図が無い」だけで、これだけが成立と不成立を分けます。だからこれを決め手に採りました。

不利益手当てで下げられるか決め手か
外部を止める面で図が出ない下げられない（面の性質であってこちらの手が届かない）これ
版が流れて描画が変わる版を固定すれば下がる—
配信元が成果物より先に消える控えを持てば下がる—
オフラインで開けない事前に取っておけば下がる—
閲覧しただけで第三者へ通信が出る下がらないが、開けるかどうかは分けない—

03変更前と変更後block 03

図がどこで確定するかが、閲覧時から組み立て時へ移る。

04「決め手」を選んだ軸block 04

不利益を、程度の問題と、成立するかどうかの問題に分けました。遅い・古い・追跡される、はどれも程度です。手当てで下げられるので、決定の根拠にすると「どこまで下げれば十分か」という別の議論を呼び込みます。
開いても図が出ない、は程度ではありません。成果物としてそこで成立していない。この一線だけが、手当ての量に依存せずに決着します。

05答えないことblock 05

問いここで答えない理由
図の語彙をどう作り直すか別の決定。2つ目の描画先が実在するまで決められない、というのが ddd・tech-lead の一致した判定
どの方式で描くか（自前で組む／ライブラリを同梱する）この決定が縛るのは「外部を踏まない」までで、方式は実装の判断に属する
Markdown の Mermaid をやめるかやめない。この決定は HTML にのみ及ぶ
既存の成果物をどう扱うか再描画で追随する範囲か、手当てが要るかを、仕様を書く段で数える

06承認block 06

状態 未承認 既存の受け入れ基準1件がこの決定と正面から衝突するため、承認を待つ。

uc-render-document-viewer の3番目の基準は「mermaid コードフェンスを <pre class="mermaid"> として出力し、ブラウザ側でのレンダリングに委ねる shall」と書かれています。委ねる先のライブラリをどこから得るかを問わず、この決定を通せばこの基準は書き換えになります。
