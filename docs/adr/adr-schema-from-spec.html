Architecture Decision Record

Schema を仕様から実装し、型は Document として置く

x-render-order は156か所で使われ、仕様には0回しか現れない。誰かが消しても何も落ちない。schema が持つのは構造で、構造はその型の Document すべてへ波及する。

01決定

Waffle は、Schema を仕様から実装し、型（DomainSpecSchema など）は Document として置く。JSON Schema ファイルは手で書かず、宣言から描いた成果物とする。手で書くのは Schema の仕様1本だけになる。

決め手いまは JSON Schema が宣言そのものなので、突き合わせる相手が存在しない。宣言と成果物を分ければ、Waffle が Document に対してやっていることを Schema に対してもできる。

03理由

最も使われている語が、最も説明されていない。schema が持つのは構造であり、構造は全ての Document へ波及する。

測ったx-render-order は最新版の schema で156か所使われ、仕様には0回現れない。最も使われている x-prompt-write は623か所で、言及は19回である
さらに
測った読む相手のいない語が2つある。x-prompt-interpret と x-extraction-rules は、最新版での使用が0で、読む実装も無い
だから
言えること語彙に仕様が無いので、誰かが消しても何も落ちない。使われなくなった語が残り続けるのも、同じことの現れである
何が波及するかを見ると
前提schema が持つのは値ではなく構造である。構造はその型の Document すべてへ波及する
だから
言えること波及するものに仕様が無い状態は成り立たない。何が正しいかを誰も言えないまま、全部の Document が従うことになる
置き場所も見た
測った図の宣言の形が KnowledgeSchema の $defs.Figure にあり、ほかの型にも図の欄が散らばっている。どの型でも同じであるべき形が、型ごとに置かれている
合わせると
結論Schema を仕様から実装し、型は Document として置く。JSON Schema は手で書かず、宣言から描く
なお
前提Schema の仕様を書く時点では、それを検査する実装がまだ無い。この行き違いは最初の1回だけで、以後は起きない——自分自身を自分で組み立てる仕組みがどれも通る道である
段の裏付けと、崩れるときを開く（5件）
段裏付けの種別参照先崩れるとき
156か所で使われ、仕様に0回実測最新版の schema 10本と、仕様の全文を数えた—
読む相手のいない語が2つ実測最新版での出現数と、読む実装の有無を突き合わせた—
schema が持つのは構造である実測patch-schema の操作が add_block・rename_block・add_def・add_kind_branch であること—
図の形が段2 に置かれている実測KnowledgeSchema の $defs.Figure—
最初の1回だけ検査できない確立された型自分自身を自分で組み立てる仕組みに共通する起動の手順2回目以降も検査できない形になったとき

宣言と成果物が別で、突き合わせられる決め手突き合わせる相手が無いと、宣言が守られているかを機械で確かめられない。Waffle が Document に対してやっていることを、Schema に対してもできるかどうかがここで決まるいまのまま／説明する仕様だけ足す ── どちらも JSON Schema が宣言そのものなので、突き合わせる相手が存在しない
構造に仕様がある構造は、その型の Document すべてへ波及する。波及するものに仕様が無いと、何が正しいかを誰も言えないいまのまま 最も使われている語が、最も説明されていない
型を増やすのに実装を触らない型は利用者が足していくもの。足すたびにプロダクトを変えるなら、利用者は足せないいまのまま／説明する仕様だけ足す ── どちらも JSON Schema を手で書き足す
いまの実装を動かさずに済む動かす範囲が広いほど、途中で止まったときに新旧が混ざる仕様から実装する（採る） 段1 を書き直すことになる

05付随して決めたこと

型と実体の境目が決まると、どの値がどちらに属するかも決まる。3点を同時に決めた。

論点決定
x-* は型と実体のどちらに置くか型。実体へは写さない。描くときは schema を引数で受け取る
図はどちらに置くか形は段1、値は Document。書ける欄と主張の一覧は全型で同じ、何を描くかは文書ごとに違う
読む相手のいない2語落とす。語彙に入れない
それぞれの根拠を開く（3件）
論点根拠
x-* は型と実体のどちらに置くか同じ schema から作られるものは、構造が同じでなければ困る。実体へ写すと、一致が「成り立っていること」から「保たせること」へ変わる。直し漏れは機械で埋められるが、食い違いうる状態そのものが型を型でなくする。x-prompt-write も同じで、各欄に何を書くべきかは型が決める
図はどちらに置くか書ける欄は全型で同じでなければならないが、何を描くかは文書ごとに違う。形と値で属する場所が分かれる。いまは形のほうが KnowledgeSchema の中にあり、置き場所を間違えている
読む相手のいない2語使用0・読む実装も無い。語彙に仕様が無かったから残ったので、仕様を持つ時点で入る理由が無い

06答えないこと

語彙の中身と、移す手順は、この決定では扱わない。

項目種別行き先
語彙の粒度範囲外描き方の6語を1つにまとめる余地があるかは、まだ見ていない
足りない3語の形範囲外描き先・表紙・図をどう宣言するか。名前も欄の形も決めていない
移す順序範囲外いまの schema を段2 の Document として書き直す順序と、その間の互換
