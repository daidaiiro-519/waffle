配列の部分編集を入れると、動作はこう変わる

4つの場面を、実際にコマンドを叩いた出力で並べた。左が今の動作、右が変更後。場面1と2の「今」は推測ではなく、実物の Document で実行した結果（測定後に元へ戻してある）。

題材: ds-extract-discriminator-key（受け入れ基準3件） 測定日: 2026-08-11
場面 1 受け入れ基準を1件だけ足したい

今実測

$ waffle scaffold --operation fill \
    --values '{"content.acceptanceCriteria.items[].id":
               "new-criterion"}'

{"error": "INVALID_FIELD_PATH",
 "message": "content.acceptanceCriteria.items[].id
             は schema が宣言していない欄です"}
✕
要素を指す道はそもそも受け付けない。記入可能な道を組み立てる走査が配列で再帰を止めているため、要素の道は1本も存在しない。

変更後

$ waffle scaffold --operation 基準を足す \
    --path .../ds-extract-discriminator-key.json \
    --element '{"id": "new-criterion",
                "text": "When ... システムは ... shall。"}'

{"documentPath": "...",
 "added": ["new-criterion"],
 "items": 4}
✓
既存3件を一度も読まずに1件足せる。読み出し→組み立て→書き戻しが消えるので、その途中で落とす事故も消える。

$ waffle scaffold --operation fill \

               [{"id":"zz-probe", "text":"..."}]}'

{"written": ["content.acceptanceCriteria.items"],
 "skipped": []}          ← 成功と報告される
$ waffle query ... 'items[].id'

["top-level-branch", "nested-branch", "no-branch",

  → ['zz-probe']   3件が消えた

変更後

$ waffle scaffold --operation fill \
    --values '{"content.acceptanceCriteria.items":
               [{"id":"zz-probe", "text":"..."}]}'

{"error": "WHOLESALE_REPLACE_NOT_ALLOWED",
 "message": "この配列は要素ごとに編集します。
             基準を足す / 基準の文言を直す /
             基準を取り下げる のいずれかを使ってください"}
✓
操作を宣言した配列は、丸ごと置き換える形そのものが塞がる。取りこぼす手順に入れなくなる。

この場面が、この変更で本当に消したいものです。場面1は不便なだけですが、場面2は失敗したのに成功と報告される。そして今、消えた基準に気づく仕組みはありません——check-criteria-coverage は仕様があるだけで未実装です。

場面 3 使わなくなった受け入れ基準を取り下げたい

今

$ waffle query ...      # 3件を読み出す
$ # 手元で1件を抜いた配列を組み立てる
$ waffle scaffold --operation fill \
    --values '{"...items": [残りの2件]}'

{"written": ["content.acceptanceCriteria.items"]}
その基準を指しているシナリオ:
scenarios[1].satisfies = ["nested-branch"]
                          ↑ 宙に浮いたまま残る
✕
参照が残っていてもそのまま消える。engine は「取り下げに伴う業務ルール」を1つも知らない。

変更後

$ waffle scaffold --operation 基準を取り下げる \
    --key nested-branch

{"error": "PRECONDITION_NOT_MET",
 "message": "この基準を指すシナリオが残っています:
             『束ねられた要素の中の分岐から
               種別の欄を取り出す』"}
シナリオを先に外してから、もう一度:

{"removed": ["nested-branch"], "items": 2}
✓
Schema が「取り下げには参照するシナリオが無いことが要る」と宣言し、engine がそれを検査する。順序を守れば通る。

ここが add / remove / replace という汎用の3操作にしなかった理由です。「足す」と「取り下げる」は守るべきことが違うのに、汎用3操作はその違いを同じ形に潰してしまう。

場面 4 Schema から、使わなくなった種別を消したい

今コード確認済

$ waffle patch-schema --operation remove_field \
    --defName null \
    --fieldPath 'properties.specKind.enum.3'

{"ok": true}          ← 互換検査を素通り
検査が見ているのは3つだけ:
  required 配列への add/replace
  既存フィールドの type 変更
  必須プロパティの remove
enum 値の除去も $defs の除去も、どれにも当たらない
✕
その種別を指す Document を壊す変更が、無傷で通る。しかも分岐・enum・描画先を人が順に消すので、途中で止まると壊れた Schema が残る。

変更後

$ waffle patch-schema --operation remove_kind_branch \
    --kind domain-service

{"error": "BACKWARD_INCOMPATIBLE",
 "message": "enum 値の除去は後方互換を壊します:
             /properties/specKind/enum/3"}
意図した破壊なら、版を上げてから:

{"removed": {"branch": 1, "enum": 1,
             "renderTarget": 1}}   3箇所を同時に
✓
互換を壊す変更が止まる。通すときは分岐・enum・描画先がまとめて消えるので、半端な Schema が残らない。

まとめると、変わるのは4つ

今変更後
1件足す全件を読み、手元で組み直し、丸ごと書き戻す既存を読まずに1件足す
組み立てで取りこぼしたとき成功と報告され、消えたことに誰も気づかない丸ごと置き換える形自体が塞がる
参照されている基準を消したときそのまま消え、シナリオの参照が宙に浮く前提を検査して止まる
Schema から種別を消したとき互換検査を素通りし、3箇所を人が順に消す違反として止まり、通せば3箇所同時

入れるときに、同時に必要なもの

要素単位で書けるようにすると、丸ごと置き換えが副作用として持っていた「全体を一度読ませる強制力」が消えます。何も足さないと、失敗が欠落（見える）から不整合（見えない）へ移るだけで、悪化しかねない。だから次の4つは同じ回に入れます。

  • 鍵の一意性を validate で検査する。今これが無いので、鍵が重複した配列では部分編集が黙って最初の1件だけを書き換えうる。
  • 1つでも不正があれば何も書かない。3件のうち1件だけ通る状態は、いま消したい「何が済んでいるか分からない」を細かい粒度で再現する。
  • 要素を足すときの固定値の補完。今の補完はオブジェクトにしか降りず配列へ入らないため、このままだと「成功と報告されるのに schema へ適合しない Document」が残る。
  • 鍵が見つからなければ失敗させる。黙って足す挙動にはしない。

判断が要るのはここだけ

D2 ── 操作の名前

汎用の add/remove/replace にするか、場面3のように配列ごとに業務の言葉と前提を宣言するか。汎用にすると場面3の右側は作れません。

推奨 ── 宣言する側。ただし最初は受け入れ基準とシナリオの2配列だけで実証し、前提の検査が効くと確かめてから広げる。

D6 ── Schema 側をどこまで

場面4の remove_kind_branch を足すか。足さなくても、enum 値の除去を互換検査に加えるだけで左側の「素通り」は消えます。

推奨 ── 互換検査は今すぐ。remove_kind_branch は場面1〜3の後。

場面1・2 の「今」は ds-extract-discriminator-key.json で実際に実行した出力（測定後 git で復元）。
場面3・4 の「今」は実装コードを読んで確認。「変更後」はいずれも提案であり、出力の形は実装時に確定する。
