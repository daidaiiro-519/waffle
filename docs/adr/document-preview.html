Document は何を持ち、どう呼ばれるか

持ち物・操作の中身・型の解決のされ方・型の操作との併用が要るかどうかを、ひととおり並べる。

01Document が持つもの

導けないものだけ。値埋めの対象は content ただひとつである。

欄中身誰が入れるか

種別どの枝か同上
役どころ実体か雛形か書き手（既定は実体）
使ってよいか下書き／有効／非推奨人が決める。導けない唯一のもの

ラベル文書に付ける印書き手
content型を知らない木。値は外から渡される書き手。ここだけが値埋めの対象

02型はどう解決されるか

解決するのはユースケース。Document は参照を持つが、自分では取りに行かない。

03操作の一覧

どれも、それ自身では完結する。型が要る操作は、解決済みの型を引数で受け取る。

操作誰の入力返す／変える型が要るか完結するか

「完結する」とはどういう意味か

その操作の中で、ほかの集約のコマンドを呼ばないという意味である。型が要る操作も、型は引数として渡ってくるだけで、Document が型を取りに行くことはない。

承認済みの規律 ── 集約は参照は持つが、自分では解決しない。解決した相手を引数で受け取る。

04操作を組み合わせるとき

併用が要るのは、両方の持ち物が混ざるときだけである。

やりたいことどう組み合わせるか併用が要るか
索引を取り出す型へ読み方の指針を、Document へ中身を求め、ユースケースが束ねる要る。両方の持ち物が混ざる
描くユースケースが型を解決 → Document が判定 → Document が描く要らない。型は引数として渡るだけ
新しい文書を起こすユースケースが型を解決 → 型が骨格を作る → 書き手が値を決める → Document が値を埋める要らない。順に呼ぶだけ
逸脱を確かめるユースケースが型を解決 → Document が判定要らない
索引だけが併用を要る理由を開く

索引はブロックの読み方（型の持ち物）とそこに何がどれだけあるか（文書の持ち物）を組にして返す。片方だけでは役に立たない ── 読み方だけではどの文書でも同じになり、中身だけでは何のために読むブロックか分からない。

束ねるのはユースケースの仕事である。調整だけを担うという位置づけに、そのまま収まる。

05呼ぶ順と、その前後

「検証前に描かせない」は、描くの事前条件として現れる。状態の遷移ではない。

操作事前に成り立っていること終わったとき成り立っていること
骨格を作る型が在り、識別子と種別が与えられている器が型の形どおりに起き、書き方の指針が添う
値を埋める道が与えられているその道の先に値が置かれている
値を取り出す道が与えられているその道の先の値が返る
描く型が引数で渡され、逸脱していない決まった場所に成果物が在る
終端化する後続の版が在る使ってよいかが非推奨になっている
