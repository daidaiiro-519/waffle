受け入れ条件と振る舞いのシナリオの対応を、どう宣言するか

2つの定義だけから導きます。既存の文書がどうなっているかは、いま置き換えようとしている方式の下で書かれたものなので、根拠に使いません。

決めること
「この受け入れ条件を、この振る舞いのシナリオが満たす」という対応を、どういう形で宣言するか

対応の情報そのものは必要です。これが無いと「どの条件にシナリオが付いていないか」を機械が言えません。

01前提となる2つの定義

満たすべきこと
受け入れ条件

満たすべきことの1単位。1つの条件は1つの主張で、複数の状況にまたがって成り立つことを述べる。

切り口は「主張」
満たしていると言える筋書き
振る舞いのシナリオ

システムを1回通した筋書き。Given と When が1つの流れを定め、Then がその流れで観測できることを述べる。

切り口は「流れ」
「控え、かつ尋ねない」のように1項目に主張が2つ入っているものは、条件が1つではなく2つある状態です。これは定義から出ることで、書き方の好みではありません。

02導出：切り口が違うので、対応は多対多になる

条件は主張で切り、シナリオは流れで切ります。同じものを違う軸で切った2つの分割の間の対応は、一般に多対多になります。これが結論で、他に何も要りません。

横に見る
1つの主張 → 複数の流れ

主張は複数の状況にまたがります。流れは1つの状況しか通りません。したがって1つの主張を確かめる流れは複数ありえます——境界の内と外、別の入口、別の前提。

縦に見る
1つの流れ → 複数の主張

1つの流れを通すと、結果と状態の変化が同時に生じます。そこで観測できることは1つとは限りません。したがって1つの流れが複数の主張を同時に満たしえます。

03縦を1つに強制しない理由

「1つのシナリオは1つの主張だけを確かめる」と決めることもできます。そう決めれば対応は1対多に収まり、入れ子で表せます。採りません。理由は1つで、定義から出ます。

同じ流れに対して Then を分けて別のシナリオにすると、Given と When が複製されます。

1主張1シナリオを強制すると宣言が複製される
Scenario: 貸し出すと台帳に記録される
  Given 貸出可能な備品と、借りる資格のある人
  When  その人がその備品を借りる
  Then  台帳に貸出が記録される

Scenario: 貸し出すと返却期限が伝えられる
  Given 貸出可能な備品と、借りる資格のある人   ← 同じ
  When  その人がその備品を借りる              ← 同じ
  Then  返却期限が伝えられる

Scenario: 貸し出すと在庫が1つ減る
  Given 貸出可能な備品と、借りる資格のある人   ← 同じ
  When  その人がその備品を借りる              ← 同じ
  Then  在庫が1つ減る
流れで書くと複製が生じない
Scenario: 資格のある人が備品を借りる
  Given 貸出可能な備品と、借りる資格のある人
  When  その人がその備品を借りる
  Then  台帳に貸出が記録される
  And   返却期限が伝えられる
  And   在庫が1つ減る

この筋書きが満たす主張は3つ。
対応を宣言できれば、それで足りる。
複製された Given と When には、検知が付きません。文言の照合はシナリオ単位で行われるので、3つのうち1つだけを直しても何も落ちません。宣言の複製に検知が無い状態は、この仕組みが避けると決めた壊れ方そのものです。それを構造的に生み出す設計は採れません。

反対材料が1つあるが、成立しない

「1つの流れですべて述べると、壊れたときにどの主張が破れたか特定しにくい」——これは成立しません。特定は実行時に得られます。シナリオは実装へ転写され、Then の行ごとに確かめられます。落ちれば、どの行かは結果に現れます。仕様側の粒度で特定する必要はありません。

04形の選択

多対多を表せる形は、実質的に参照だけです。入れ子は縦方向（1つの流れが複数の主張を満たす）を表せません——その流れをどれか1つの主張の下にしか置けず、残りは「シナリオを持たない主張」に見えてしまいます。

対応の形は、条件に識別子を持たせ、シナリオがそれを並べるものにします。

受け入れ条件
  { "id": "ac-recorded",  "text": "貸出は台帳に記録されること" }
  { "id": "ac-due-date",  "text": "借りた人に返却期限が伝えられること" }
  { "id": "ac-stock",     "text": "貸出のたびに在庫が1つ減ること" }

振る舞いのシナリオ
  { "name": "資格のある人が備品を借りる",
    "satisfies": ["ac-recorded", "ac-due-date", "ac-stock"],
    "gherkin": "Given …\nWhen …\nThen …\nAnd …\nAnd …" }
参照が壊れうる形であることは承知のうえです。ただし壊れ方が違います。指す先が実在しないことは機械が判定できるので、検査で弾けます。入れ子が抱える「表せないものがある」は、検査では埋められません。

05決定

決定
受け入れ条件に識別子を持たせ、振る舞いのシナリオが満たす条件の識別子を並べる
  1. 受け入れ条件は識別子を持つ構造の並びになる。1つの条件は1つの主張とする
  2. シナリオは、満たす条件の識別子を並べる。多対多を許す
  3. 指す識別子が0件のシナリオは許さない。ただし趣旨は不要なシナリオの排除ではなく、条件の書き漏れを発見させること——0件で止まったとき、書き手はシナリオを消すのではなく条件を書き足す
  4. 同じ文書内に実在する識別子しか書けない。実在しない参照と識別子の重複は検査で弾く
  5. 識別子は手書きの短い符号とし、意味を込めすぎない。連番は並べ替えに弱く、本文から導く名前は文言の修正に弱いため
  6. 不変条件も同じ形を使う。ただし既定の多重度が違う——受け入れ条件はトリガを持つので1対1が既定、不変条件は「常に」なので1対多が既定

06担保する範囲と、しない範囲

この仕組みが担保する
  • どのシナリオからも指されていない条件が無いこと
  • 指す先が実在すること
  • 識別子が重複していないこと
  • どの条件も満たさないシナリオが無いこと
担保しない
  • その対応が正しいこと。指すことは主張であって、検証ではない
  • シナリオの Then が、指した条件を実際に確かめていること
  • 条件そのものが、業務として妥当であること
指す先を機械が確かめられることは、対応が正しいことを意味しません。最も安い埋め方は、もっともらしい識別子を並べることです。しかも識別子は読んでも正しく見えます——散文なら言い換えにすぎないと読めば分かりますが、符号にはその手がかりがありません。

したがってこの検査の位置づけは「品質のゲート」ではなく「読むべき箇所の当たり付け」です。対応の妥当性は読み手の責務であることを、書き手向けの指示に明記して残します。

07まだ決まっていないこと

参照の向き
シナリオが条件を指す向きを採りました。逆向きもありえます。前者を選んだのは、シナリオが実装へ転写される単位であり、既に名前という鍵を持っているためです。
同じ形の対
操作保証とその筋書きも同じ構造です。構造は同時に決めるべきです——別々にやると、対応の表を2度書くことになります。
業務サービス
業務サービスには受け入れ条件の欄そのものがありません。対の片側が無いため、この決定の適用より前に、条件の欄を設ける判断が要ります。
複合文の扱い
「1つの条件は1つの主張」は定義ですが、それを機械が確かめられるかは別です。1項目に含まれる主張の数を数える手段を持つかどうかは未決です。
この決定は 01 の2つの定義だけから導いています。既存の文書がどう書かれているかは根拠に使っていません——それは、いま置き換えようとしている方式の下で書かれたものだからです。03・04 の例は、導出を読みやすくするための架空の題材で、証拠ではありません。移行の手順・規模・順序は、決定の根拠と混ざらないよう別の文書に分けます。
