Schema を仕様から実装し、型は Document として置く

置き換えられた

語彙について述べた部分（11語）は、承認済みの決定「語彙を意味の名前だけにし、器と共通の欄を主張から分ける」および「段1 が部品を提供し、段2 が8つを宣言する」へ置き換わった。段1／段2／段3 の並びを示す図は、いまも成り立つ。

新しいエンティティは要らない。いまある Schema エンティティを、仕様から書き直す。型そのもの（DomainSpecSchema など）は Document になり、利用者が増やせる。

01JSON Schema はどこから来るか

いまは成果物を人が直接書いている。あるべき姿では、宣言から描かれる。

02実装と Document の境目

段は一様ではない。段1 だけが実装で、段2 から下は Document である。

03鶏卵の問題はどう解けるか

Schema の仕様を書く時点では、それを検査する実装がまだ無い。この行き違いは最初の1回だけで、以後は起きない。

順やることそのとき検査できるか
1Schema の仕様を書くできない。検査する実装がまだ無い
2その仕様から Schema エンティティを実装する（TDD で転写する）受け入れ基準とシナリオをテストへ転写するので、実装の側は確かめられる
3段2 の型を Document として書き、2 の実装で検査するできる
41 で書いた仕様自身も、3 の型で検査するできる。ここで行き違いが解消する
なぜこれで済むかを開く

1 が検査できないのは、自分自身を自分で組み立てる仕組みがどれも通る道である。自分自身を自分でコンパイルする処理系も、最初の1回だけは別の手段で組み立て、以後は自分で自分を組み立てる。

重要なのは、この行き違いが繰り返されないことである。4 を通したあとは、仕様も型も実体も、すべて同じ経路で検査される。段1 を Document として自分自身に適合させる仕掛けを組むより、1回の行き違いを認めるほうが代償が小さい。

x-render-order は最新版の schema で156か所使われ、仕様には0回現れない。転写する受け入れ基準が無いのでテストが書けず、突き合わせる宣言が無いのでドリフト検知も効かない。誰かが消しても何も落ちない。

3つが揃えば「順序を入れ替えたら成果物の並びが変わる」という筋書きが書ける。最も使われている x-prompt-write（623か所）が最も説明されていない（仕様での言及19回）という偏りも、同じ形で埋まる。

16の主張それぞれに、必須の欄と禁止の欄が付く。たとえば「階層」は items を要求し links と frame を禁じる。「量の大小」は items と frame を要求し links を禁じる。これは allOf + if/then の16件として書ける——kind による分岐と同じ仕掛けである。

入れ子は $ref ではなく深さ3まで展開する。「再帰は常に有界である」という不変条件を、schema の構造そのもので満たすため。

描き先ごとの落とし方は段1 の実装が持つ——Markdown なら Mermaid、HTML なら SVG。宣言は同じ語彙のまま変わらない。色と書体は要素の属性として持たせ、図だけを取り出しても正しく描けるようにする。

先立つ決定：「図の語彙を、描き方の名前から主張の名前へ移す」（承認済み）／「図の宣言を、主張を軸にした形へ置き換える」（承認済み）／「図の宣言を、Document の内側の値として置く」（未承認）。

08x-* は型に置く。実体へは写さない

描くとき、Document は schemaRef を解決してもらい、schema を引数で受け取る。適合を判定するときと同じ形である。

問い答え
同じ型の Document どうしが、描き方について食い違ってよいかいけない。同じ schema から作られるものは、構造が同じでなければ困る
だから x-* はどちらのものか型のもの。「この型の成果物はこの順に並ぶ」であって、「この文書はこの順に並ぶ」ではない
実体へ写すと何が変わるか一致が成り立っていることから保たせることへ変わる。直し漏れは機械で埋められるが、食い違いうる状態そのものが型を型でなくする
x-prompt-write と x-prompt-query はどちらか型のもの。同じ schema から作られるものは、各欄に何を書くべきかも同じでなければ困る。ただし応答には載る——値を取り出すと組で返り、骨格を作ると隣に返る
描くのに Document だけで足りるか足りなくてよい。Document と、解決済みの Schema で完結する。他の道具へ渡すときは、描いた成果物か、両方を一緒に渡す

09何が変わるか

手で書く JSON Schema は無くなる。代わりに、Schema を説明する仕様が1本増える。

いまあるべき
JSON Schema ファイル人が手で書く宣言から描かれる成果物
Schema を説明する仕様無いある。Document として書かれ、実装へ転写される
エンティティDocument と Schema変えない。Schema の中身を仕様から書き直すだけ
型を増やすときschema ファイルを手で書き足すDocument を1本書く。Waffle の実装は変わらない
ドリフト検知Schema には効かないSchema にも効く。宣言と成果物を突き合わせられる
