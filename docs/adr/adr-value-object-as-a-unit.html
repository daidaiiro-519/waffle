Architecture Decision Record

値オブジェクトとエンティティを、独立して書ける単位にする

ドメインモデルの部品は4つあるが、仕様として独立に書けるのは2つだけだった。残る2つは集約の内側にしか置けない。その結果、集約をまたぐ参照が、相手を特定する鍵ではなく相手の値を写して持っている。

01決定

Waffle は、値オブジェクトとエンティティを、集約や業務サービスと同じ粒度で書ける単位にする。集約は自分の一貫性の境界だけを持ち、値オブジェクトとエンティティを所有しない。参照する。

決め手Document が持つ参照7つのうち6つは、相手を特定する1つの鍵である。schemaRef だけが例外で、相手の名前と版を写して持っている。集約をまたいで型を参照できないことの帰結であり、例外が1つだけ在ることは、その形が意図ではなかったことを示す。

02変更前と変更後

この決定が変えるのは、仕様として何を独立に書けるかである。ドメインモデルの部品そのものは変えない。

変更前 ── 集約が3つを兼ねる変更後 ── 4部品が同じ格になる
仕様として独立に書ける部品集約と業務サービスの2つ4つすべて
集約をまたぐ参照相手の値を写して持つ。SchemaRef が名前と版を裸の文字列で抱え、Schema 側の振る舞いを失っている相手を特定する鍵だけを持つ。値は相手の側にある
集約が持つもの一貫性の境界に加えて、エンティティと値オブジェクト一貫性の境界だけ
置き場所が無い概念他に段が無いので集約として書く（Schema がそうなった）本来の段へ置ける

03理由

書ける単位が2つしかないため、集約をまたぐ参照が相手の値を写して持っている。7つの参照のうち、例外は1つだけである。

測ったドメインモデルの部品は4つ（値オブジェクト・エンティティ・集約・業務サービス）だが、仕様として独立に書けるのは集約と業務サービスの2つだけだった
だから
言えること値オブジェクトとエンティティは、集約の内側にしか置けない
そうすると何が起きるかを測った
測ったDocument が持つ参照は7つ。うち6つは DocumentId 型で、属性を1つ（値）だけ持つ鍵である。schemaRef だけが SchemaRef 型で、名前と版という2つの属性を持つ。しかも両方が裸の文字列で、Schema 側が持つ SchemaId・Version の型を使っていない
だから
言えること集約をまたいで型を参照できないため、参照が相手の値を写して持つことになった。写しなので、Schema 側の振る舞い（版は上げる方向にのみ進む）は失われている。例外が1つだけ在ることは、この形が意図ではなく置き場所が無かった結果であることを示す
症状も出ていた
測った置き場所が無かった Schema が、集約として書かれている。38個の型定義を1つに束ね、コマンドは0件、不変条件は12件のうち11件が静的な書き方の規則で、時間をまたいで守るものではない
合わせると
結論値オブジェクトとエンティティを、仕様として独立に書ける単位にする。集約は一貫性の境界だけを持ち、それらを所有しない
ただし
反証単位が増えると、書く文書も辿る文書も増える。集約1つを読めば済んでいたものが、複数を辿ることになる
段の裏付けと、崩れるときを開く（5件）
段裏付けの種別参照先崩れるとき
4部品のうち2つしか書けない実測仕様の種別に指定できる候補を数えた候補が増えたとき
参照7つのうち1つだけが例外実測Document が持つ参照の型と、その属性の数を数えた（6つは属性1つの鍵、schemaRef だけが2つ）他の参照にも複数属性のものが見つかったとき
Schema が集約として説明できない実測コマンドの数と、不変条件の担保のされ方を数えたコマンドを持たない集約が正しいと分かったとき
潰した境界は症状を出すknowledgespec-implementation-abstraction ── 「a.b が必要なのに a まで圧縮すると、分ける必要がある境界を無視することになる」—
4部品すべてを独立の単位にするWaffle の設計判断knowledge に該当なし—

最後の段に knowledge の裏付けが無い理由 ── spec-implementation-abstraction は「潰すと境界が消える」とまでは言うが、どの単位まで分けて書けるようにするかは持たない。ドメイン駆動設計が4部品を同じ格で置いていることを根拠に、仕様の側でも同じ格にするという判断は、この製品の側で置いている。

05付随して決めたこと

分けると、集約と値オブジェクトの関係が決まる。3点を同時に決めた。

論点決定
集約と値オブジェクトの関係所有せず、参照する。同じ値オブジェクトを複数の集約が参照してよい
いま集約の中にある10件独立した単位へ移す。移すのは別の作業として行う
写しになっている参照移すときに鍵1つへ寄せる。相手の値は相手の側に置く
それぞれの根拠を開く（3件）
論点根拠
集約と値オブジェクトの関係所有のままだと、またがる概念をどちらの集約が持つかを決められない。参照にすれば、値オブジェクトは1つで、参照する側が何個あってもよい
いま集約の中にある10件移す作業には、写しになっているものを鍵へ寄せる判断が含まれる。決定と同じ場でやると、決定の可否が個別の判断に引きずられる
写しになっている参照参照は相手を特定できればよく、相手の値を持つ必要がない。持つと、相手が変わったときに写しが古くなる。SchemaRef は鍵1つへ寄せ、名前と版は Schema の側に置く

06答えないこと

個別の移し方と、他の食い違いは、この決定では扱わない。

項目種別行き先
Schema が最終的にどの単位になるか範囲外この決定は書ける単位を増やすだけ。Schema をどこへ置くかは、移す作業で判定する
集約の中の10件をどう移すか範囲外移す作業として別に行う
仕様の種別をどう増やすか範囲外欄の形は、実装に着手する段で決める
業務サービスが仕様5件・実装24件で開いていること範囲外この決定とは別の食い違い。別に測る
