段2 の仕様 ── 材料

仕様と実装を、どこで結ぶか

基準とシナリオは振る舞いしか運ばない。TDD で緑になっても、宣言した単位が実装に在る保証にはならない。結び目をもう1本足すための設計である。いまの検査や実装の形は根拠にしていない ── あるべき形だけから組んでいる。

01乖離は3つの形しかない

仕様と実装がずれるとき、起きていることはこの3つのどれかである。

乖離の形何が起きているか
在るはずのものが無い宣言した単位を、実装の誰も実現していない。仕様には在るが、動くものが無い
無いはずのものが在るどの宣言も指していない実装が生えている。誰も仕様として合意していない振る舞いが動いている
在るが、言ったとおりに振る舞わない宣言した基準を満たさない。形はあるが、中身が違う

02結び目は2本で足りる

名乗りが存在を、転記が振る舞いを担う。名乗りは1本で両方向に数えられる。

乖離の形何で捕まえるか誰が誰を指すか
在るはずのものが無い名乗り実装 → 仕様の識別子
無いはずのものが在る同じ名乗りを、逆向きに数える実装 → 仕様の識別子
言ったとおりに振る舞わない転記テスト → シナリオ（一字一句）

2本で足りる。名乗りが存在を、転記が振る舞いを担う。名乗りは1本で両方向に数えられるので、「無い」と「余っている」に別々の仕組みを持たなくてよい。

033点が閉じる

名乗りは実装の自己申告である。三角形が閉じて初めて、裏が取れる。

3点が閉じると、自己申告の裏が取れる。名乗りは実装が自分で書くものなので、それだけでは嘘をつける。だが「シナリオ S を載せたテストが呼ぶ実装は、S が指す単位を名乗っているはず」が成り立たなければ、名乗りかシナリオのどちらかが嘘である。4辺目（テストが呼ぶ先を辿る）は呼び出しの走査が要るので、費用を別に測る。3辺だけでも、存在と振る舞いは当たる。

04実物で見る ── 1件を3か所で

同じ1件が、仕様・テスト・実装の3か所に現れる。指し先はすべて仕様の識別子である。

仕様 ── document.json
agg-document
  公開する操作
    逸脱していないか判定する
      受け入れ基準
        schemaRef を持たない文書を渡したとき、判定せず拒否する
      シナリオ
        Scenario: schemaRef を持たない文書は判定できない
        Given  schemaRef を持たない文書
        When   逸脱していないか判定する
        Then   拒否され、判定は行われない
        振る舞う単位: agg-document#逸脱していないか判定する

宣言の正本。シナリオが、どの単位の振る舞いかを指す（足すのはここだけ）

テスト ── docstring
def test_rejects_document_without_schema_ref():
    """
    Scenario: schemaRef を持たない文書は判定できない
    Given  schemaRef を持たない文書
    When   逸脱していないか判定する
    Then   拒否され、判定は行われない
    """

シナリオを一字一句で載せる。ずれれば照合が落ちる

実装 ── docstring
class Document:
    """構造化された成果物。

    実現する宣言: ent-document
    """

    def validate(self, schema):
        """schema に適合するかを判定する。

        実現する宣言:
          agg-document#逸脱していないか判定する
        """

どの宣言の実現かを名乗る。書き方（実現する宣言:）は規約が決める

05形を問わない

同じ宣言を、クラスで実現しても手続きで実現しても、検査は同じように当たる。だから仕様は実装の厚みを知らなくてよい。

厚い実装 ── クラスで実現する
class Document:
    """構造化された成果物。

    実現する宣言: ent-document
    """

    def validate(self, schema):
        """schema に適合するかを判定する。

        実現する宣言:
          agg-document#逸脱していないか判定する
        """

集約もエンティティもクラスとして現れる

薄い実装 ── 手続きで実現する
def validate_document(doc, schema):
    """schema に適合するかを判定する。

    実現する宣言:
      agg-document#逸脱していないか判定する
    """

クラスは無い。それでも名乗れる

なぜ形を問わないのかを開く
出典knowledge がアンチパターンとして名指ししている ── 「集約の宣言をクラスの存在と同一視する」。欠陥は「宣言した不変条件を、クラスもトランザクション境界も守っていない」ときに生じる
だから
言えることクラスが在るかは、仕様の関心事ではない。実装がどんな形で実現するかは、規約と実装の判断である
では何を担保したいのか
出典書き起こしはこう言う ── 「ソースコードが同じ言葉を語り、業務エキスパートの捉え方をそのまま表現する」。欲しいのは言葉が実装まで届いていることであって、クラスがあることではない
問いを置き換えると
結論検査するのは「宣言した単位が、実装のどこかで名乗られているか」。クラスでも関数でも手続きでもよい。形を問わないので、実装がどう作られるかを先に知る必要が無い
その帰結
結論仕様は、実装の厚みも様式も持たなくてよい。それを持ちたくなるのは、実装の形を当てにいっているときだけである

06仕様に足すのは1つだけ

残りは規約の管轄である。仕様は実装について一言も述べない。

何をどこへ仕様の高さを越えないか
シナリオが「どの単位の振る舞いか」を指すDomain の型○ 指すのは仕様自身の識別子。実装の語彙は1つも出てこない
実装が、どの宣言の実現かを名乗る規約（実装の書き方）○ 仕様への追加は無い。名乗るのは実装の側
名乗りの書き方（どの語で、どこに書くか）規約○ 仕様がここを決めると、実装の語彙が入る

仕様に足すのは1つだけである。しかも足すのはシナリオが単位を指すという参照であって、実装について何かを述べる欄ではない。これが無いと、シナリオが「どの単位の振る舞いを確かめているのか」が分からず、三角形の1辺が引けない。

07閉じないもの

3つ残る。残ることを明示して、赤にしない。閉じないものを閉じたことにするのが、いちばん危ない。

閉じないものなぜ閉じないかどう扱うか
「試していない」と「合っている」が見分けられないテストが緑でも、中身が空かもしれない。宣言の形では届かない ── 網羅率や変異テストの領域である型に足さない。別の道具の仕事だと明示する
宣言した「常に満たすこと」を、実装が本当に守っているか変える操作のシナリオが覆うが、言えるのは「覆うシナリオが在るか」まで。「トランザクション境界に収まっているか」を静的解析だけで判定できる範囲は限られる ── knowledge が留保として明記している判定できない部分は対象外だと明示し、赤にしない
名乗りが嘘 ── 違う宣言を指している名乗りは自己申告である三角形の4辺目（テストが呼ぶ先）で裏が取れる。費用を別に測る
