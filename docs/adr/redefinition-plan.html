03順序

縦は追い越せない。それぞれ、前の手が終わっていないと書けないものがある。

手やることなぜその順か終わったと言える条件
1Schema の仕様を書く（agg-schema を廃止して新規）語彙が決まらないと、コマンドの受け入れ基準が書けない語彙7語すべてに「何を述べる語か／どこに書けるか／描き先ごとの落とし方」が揃い、骨格を作るコマンドの受け入れ基準と筋書きが転写できる形になっている
2Document の仕様を書く（agg-document を書き直す）Schema の語彙を引数で受け取る側なので、1 が先コマンド5件それぞれに受け入れ基準と筋書きがあり、参照は持つが解決しないという規律が、引数の形として現れている
3業務ユースケース 30件を見直すコマンドが決まって初めて、ユースケースに何が残るかが決まる各ユースケースが調整だけを持ち、判断が集約のコマンドを指している。uc-check-* 11件の帰り先も決まっている
4型 11本を段2 の Document へ書き直す1 の仕様から実装した Schema が無いと、書いた型を検査できない手で書く JSON Schema が 0 になり、11本すべてが宣言から描かれている

05漏れやすいところ

この作業で実際に踏んだ落とし穴を、防ぎ方と対にして置く。

漏れやすいところどう防ぐか
決定に落とし先が無いまま残る上の対応表を、手が終わるたびに突き合わせる。落とし先が「—」か「別」の決定以外は、必ずどれかの手に現れる
古い前提の文書へ足してしまうagg-schema で二度やった。書き直すと決めたものは、廃止してから新規で書く
決定どうしが食い違ったまま進むadr-figure-placement で起きている。新しい決定を承認したら、先立つ決定の答えないことを読み返す
仕様に書くべきことを決定に書く／その逆方向を変えるものが決定、何が正しいかを述べるものが仕様、どう進めるかが計画

06いま決まっていないこと

計画の外にある未決。どの手にも属さないので、別に決める。

項目いつ決めるか
uc-check-* 11件の帰り先第3手の中で。突き合わせの仕組みは業務ユースケースではない疑いがある
業務サービス4件が残るか第2手が終わってから。集約のコマンドへ吸収される可能性がある
業務領域の切り直しこの再定義の外。別の作業として立てる
図の置き場所の決定書式を新しくして出し直す。並べて進められる
