語彙の作り直しは、まだ決められない

2人が別々の経路をたどって、同じ結論に着きました。Mermaid由来の語彙が問題であることは支持される。ただし今日8つの束を確定させるのは誤りである。理由は互いに独立しています。

先に — 私が渡した前提に誤りがありました

私は「HTMLは自前SVGで描く」を実測済みの事実として両者に渡しました。誤りです。自前SVGは私の作業場のプロトタイプにあるだけで、src/waffle には存在しません。確かめた結果：図のSVGを生成する箇所は0件、graphvizへの依存も0件、実際のHTMLビューアはCDNからMermaidを読み込んでブラウザに描かせています。

この誤りは結論を変えます。描画先は今日ひとつしかなく、「2つの下流が要求する形から語彙を決める」という私の筋書きは、まだ足場がありません。

各意見

ddd 診断の順序が間違っている

ubiquitous-language の「この用語は同じ言葉として適切か」は3つの問いからなり、並びを入れ替えられないと明記されています。第1問「業務エキスパートがこの用語で業務を説明するか」が「いいえ」で終端したら、第2問（一語一義）と第3問（同義語）は意味を持たない。

私の診断判定理由
A: 「従属する」＋アンチパターン「中核の業務領域で従属するを使う」条件付き成立するが、条件は「語彙の側が中核であること」。宣言済みの core をそのまま根拠にはできない
B: 一語一義の違反早すぎる第2問。第1問で終端している。いま分解しても技術用語が6語に増えるだけ
C: 同義語の禁止の違反弱い第3問。graph は使用0枚で衝突は起きていない。ただし死語が残っていること自体が診断Aの物証
D: 技術の言葉でモデルを名付けている支持4つで唯一、無条件に成立。Dが主診断で、B・CはDの症状

ddd 描画全体が中核だとは証明されていない

sd-document-management は classification: "core" を宣言しています。ただし描画をここへ統合した理由は「複数種のMermaid図生成まで複雑化しており、単純なCRUD/ETLではなくなっている」——複雑さです。subdomain の比較表は中核と一般をどちらも「複雑」に置き、分かれるのは競争優位の有無だと明言している。複雑さは補完の否定にはなるが、中核の肯定にはならない。

ただし診断Aは生き残ります。分けて問い直すと、図が何を主張するかを決める語彙の側は「既製品に無い」ので中核、特定の描画先へ字面を出す仕組みは「既製品がある」ので一般〜補完。つまり実測が示しているのは「中核でない領域の語彙が、中核の領域の語彙を侵食している」形です。

ddd いちばん痛い指摘 — 束の導き方そのもの

8つの束は、既存の125枚を機械分類して得たものです。しかしその125枚は、いずれも置き換えたい当の語彙の下で描かれた成果物です。過去の描画物のクラスタリングから語彙を導くことは、捨てたい語彙の痕跡から語彙を再生産する手続きにあたる。

domain-expert は「同じ言葉は技術者が作るものではなく、この人たちから採るものである」、ubiquitous-language は「たどりつく唯一の方法は質問すること」と述べています。束の妥当性は分布ではなく、その主張の区別が実在するかを当事者が答えられるかで確かめるべきです。

tech-lead 違反は名前ではなく置き場所にある

part_renderer.py（417行）は domain/services/ にあり、そこで Mermaid 構文を組み立てています。部品名を主張の名前へ変えても、この場所は変わりません。

むしろ悪化しうる。いまは部品名がMermaid由来だから、domain層にMermaid依存があることが名前から見えます。名前を中立化すると依存は見えなくなるが消えはしない。「語彙の締め出し」を名前で達成したつもりになり、構造上の違反だけが残る——これが最悪の結末です。

あわせて document_viewer_html_template.py は domain 層から CDN の mermaid@11 を直接読み込んでいます。part_renderer.py だけ動かすと、Mermaid依存が domain に半分残ります。

tech-lead 粒度は「8つに増やす」ではない公算が高い

判定の基準は「入力データの形が違うなら種別の値、同じなら属性」。flowchart 125枚が6種の主張を担っているという事実は、同じデータの形のまま6つの主張が言えていることを意味します。形が同じなら属性側に倒れる。8つ全部を部品名にする案は、この基準では成立しない見込みです。

「属性にすると名前が意味を失う」という懸念は、属性を必須にすれば消えます。書き手は器の名前と主張の名前の2語を名乗る義務を負い、判断は残る。

tech-lead direction は置き換えではなく削除の候補

19文書79箇所は結果であって原因ではありません。原因は part_renderer.py:115 の既定値 "LR" が domain のコードに埋まっていること。自前語彙へ置き換えると、翻訳表を永久に保守することになり、レイアウトの関心事が入口の構造化データに居座る構造は変わりません。79箇所は削除候補として数え直し、削除できない箇所が残ったら、それが属性として残す実例になります。
