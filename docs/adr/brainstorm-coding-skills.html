2何を作ろうとしているか

目的と対象に応じて必要な規約を作り、その規約に従って書くSkillである。規約そのものは references/ に置き、SKILL.md は索引して従う手順だけを持つ。Waffle が無い環境でも動く ── Waffle の有無を判定する処理は持たない。

規約の種別何についての決まりか

アーキテクチャ層の名前と、依存の向き
技術スタック使う道具と、その版

最初に使う先は、別リポジトリの OSS ── Go でバックエンドAPI、Rust で Hook と MCP。そこで効果を測ってから、段1・段2 が決まった時点で正式な形へ直す。

論点 6

各層の規約を、schema でどう縛るか

段に分けると決めた時点で、層ごとに必須の欄が変わる。それを型で言えなければ、段は運用の申し合わせにとどまる。ここが決まると、段1・段2 での CodingSchema の議論はほぼ済む。

2反証を通過した案

案中身代償
A層を、型の中の欄（tier）に上げる型は規約種別の5つのまま。tier は値で、tier ごとに必須の欄が変わる条件つきの型になる（tier が言語なら命名が必須、束ねなら層名が必須）。型を読むだけでは、何が必須かが一目で決まらない
B種別 × 層 を、型の名前にするcoding-standard-language、coding-standard-binding のように、組み合わせごとに型を持つ最大20の型になり、言語を1つ足すたびに上位の契約へ名前を足しに行く。空のマスも残る
C層ごとに、別々の schema を持つ言語規約Schema／アーキ規約Schema／目的規約Schema を分けて立てる同じ種別の規約が、層をまたぐと別の型になる。段1 のコーディング規約と段4 のそれを突き合わせられない

  • これは論点6（規則をコマンドで持つか宣言で持つか）と同じ形をしている。層を型の名前にすると上位の契約が太り、値にすると「何が違反か」を書く語彙が要る
  • tier が Coding だけの軸か、全ての型に共通の軸かは、まだ決めていない。段1 で問われる

推す案は A である。

段中身
