完成イメージ ── 段1

宣言1本が、型1本になるまで

段1 の仕様で、承認済みの決定から出ていないのはここだけである。9段を実際に通して、各段で何が足されるかを見る。

01使う宣言

部品を一通り使う、小さな型ひとつ。値・まとまり・並び・入れ子・図を含む。

宣言（人が書く）
型: MemoSchema/v1
種別: usecase ／ aggregate

共有する組み立て:
  KeyGloss   まとまり { key: 値(文字列), gloss: 値(文字列) }

ブロック:
  title    形=値(文字列)          修飾=必須
           読み方="まず何を扱う文書かを掴むために読む"
  errors   形=並び(KeyGloss)      修飾=最小の個数 1
           読み方="失敗の仕方を読む。条件が重なっていないかを確かめる"
  steps    形=入れ子の木(上限3)   読み方="順序を読む。分岐は誤りの側が持つ"
  figure   形=図                  読み方="何を主張する図かを読む"

枝ごとの必須ブロック:
  usecase   → title, errors, steps
  aggregate → title, figure

021 ── 表紙を置く

どの型でも同じ。中身より先に器が要る。

{
  "type": "object",
  "properties": {
    "documentId": { "type": "string" },
    "schemaRef":  { "type": "string" },
    "kind":       { "type": "string" },
    "role":       { "type": "string", "enum": ["entity","template"],
                  "default": "entity" },
    "usable":     { "type": "string" },
    "createdAt":  { "type": "string" },
    "updatedAt":  { "type": "string" },
    "tags":       { "type": "array", "items": { "type": "string" } },
    "content":    { "type": "object" }
  },
  "required": ["documentId","schemaRef","kind","usable","createdAt","updatedAt","content"]
}

032 ── 種別の枝を作る

content の形が枝ごとに変わるので、content を組む前に枝が決まっている必要がある。

1 の kind を置き換える
"kind": { "type": "string", "enum": ["usecase", "aggregate"] }

043 ── 共有する組み立てを置く

指す先が無いと $ref が書けない。だから参照より先に置く。

"$defs": {
  "KeyGloss": {
    "type": "object",
    "properties": { "key": { "type": "string" }, "gloss": { "type": "string" } },
    "required": ["key", "gloss"],
    "additionalProperties": false
  }
}

054 ── ブロックの器を並べる

宣言の順が、そのまま読む順になる。並べ替える根拠が無い。

"content": {
  "type": "object",
  "properties": {
    "title":  {},
    "errors": {},
    "steps":  {},
    "figure": {}
  }
}

065 ── 中身を、文法に従って組む

文法ひとつに、行き先がひとつ対応する。ここに型ごとの分岐は現れない。

content の中
"title":  { "type": "string" },

"errors": { "type": "array", "items": { "$ref": "#/$defs/KeyGloss" } },

"steps":  { "$ref": "#/$defs/Tree3" },

"figure": { "$ref": "#/$defs/Figure" }
入れ子は、上限のぶんだけ展開する
"Tree3": {
  "type": "object",
  "properties": {
    "name":     { "type": "string" },
    "summary":  { "type": "string" },
    "children": { "type": "array", "items": { "$ref": "#/$defs/Tree2" } }
  },
  "required": ["name", "summary"],
  "additionalProperties": false
}
"Tree2": { … children は Tree1 を指す … }
"Tree1": { … children を持たない … }
なぜ自分自身への参照にしないのか

自分自身を $ref で指すと、深さの上限を守る仕掛けが別に要る。上限のぶんだけ展開すれば、守るまでもなく成り立つ。

代償は型が大きくなること。上限3なら3つ、10なら10になる ── 上限を型ごとに宣言する理由でもある。

076 ── 修飾を当てる

修飾は形に付くので、形が決まってからしか当たらない。

"errors": {
  "type": "array",
  "items": { "$ref": "#/$defs/KeyGloss" },
  "minItems": 1
},
"content": {
  "additionalProperties": false
}

087 ── 説明を、鍵の隣に置く

鍵が全部出そろってからでないと、置き漏らしが分からない。

"title": {
  "type": "string",
  "description": "まず何を扱う文書かを掴むために読む",
  "x-write": "扱う対象を1文で書く。識別子の言い換えにしない"
}
2つの指針を、どこへ置くか

読み方は description へ置く ── JSON Schema の標準の欄なので、Waffle の外の道具も読める。

記入の指針は対応する標準の欄が無いので x-write にする。読むための言葉と書くための言葉は、宛先が違う ── 前者は文書を引く人へ、後者は文書を書く人へ向く。

索引の2段目は description から組み立てる。

098 ── 枝ごとの必須ブロックを当てる

ブロックが全部在ってからでないと、一覧が指す先を確かめられない。

"allOf": [
  { "if":   { "properties": { "kind": { "const": "usecase" } } },
    "then": { "properties": { "content": {
                "required": ["title", "errors", "steps"] } } } },
  { "if":   { "properties": { "kind": { "const": "aggregate" } } },
    "then": { "properties": { "content": {
                "required": ["title", "figure"] } } } }
]

109 ── 描き方と宛先を置く

型が組み上がってからでないと、どこへ置くかが決まらない。実体へは写さない。

"content": { "properties": {
  "errors": { "x-render": "table" },
  "steps":  { "x-render": "list" }
} },
"x-target": "docs/{documentId}.md"

11この手順が本物かを、どう確かめるか

4つ。うち2つは機械で確かめられる。

確かめることどう確かめるか外れたら何が言えるか
同じ宣言からは、同じ型になる同じ宣言を2回起こして、文字単位で比べる手順のどこかが順序に依っていない ── 欄の並びが辞書順で揺れる、など
段を飛ばすと壊れる段3 を飛ばして起こすと、段5 の $ref が指す先を失う順序が本物である。飛ばして通るなら、その順序に根拠が無い
部品だけで組める起こす手順のどこにも、型ごとの分岐が現れない現れたら、段1 の部品が足りていない
起こした型で、実物が通るその型を指す文書を、起こした型で判定する通らなければ、宣言か手順のどちらかが実物と合っていない

12ここで決めたこと

4つ。いずれも通してみて初めて決める必要が出た。

決めたこと中身なぜ
読み方は description へ置くJSON Schema の標準の欄をそのまま使うほかの道具も読める。独自の名前にすると、Waffle の外から見えなくなる
記入の指針は x-write へ置く標準に対応する欄が無いので、独自の名前にする読み方と混ぜない。読むための言葉と、書くための言葉は宛先が違う
入れ子は展開する上限のぶんだけ Tree3／Tree2／Tree1 を作る自分自身への $ref だと、上限を守る仕掛けが別に要る。展開すれば、守るまでもなく成り立つ
枝は allOf と if/then で当てる枝ごとに required だけを足す名前つきの入れ物を作らない。枝が言うのは「この枝ではこれらが要る」だけ

13まだ決めていないこと

3つ。行き先はすべて決まっている ── ただし図の仕様だけ、いつ書くかが空いている。
