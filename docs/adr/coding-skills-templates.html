CodingSkills の雛形（候補・第2版）

規約は、種別ごとに構造が違う。構造（表と図で宣言する）／規則（守るべき言明の並び）／道具（道具と版の表）／保証（何をどの単位で確かめるか）の4つの雛形を持つ。層の構成やフォルダの並びは、守るべき言明の羅列では表せない。実例は規則と構造の2本を置いた。

name: coding-skills
description: 目的と言語を受け取り、その場面に効く制約を集めて、それに従ってコードを書くときに使う。制約が足りないときは、書く前に制約を起こす手順へ回す。「Goでバックエンドを書く」「RustでHookを書く」「この規約に沿って実装して」と言われたときに使う。

目的

その場面に効く制約だけを集め、制約に従って書く。
制約は選択肢を減らす言明であり、どの制約にも、それが真であり続ける範囲がある。
範囲は軸（言語・アーキテクチャ・用途・実行環境）の組み合わせで決まる。

このSkillは、書きながら制約を作らない。
足りないと分かったら、書く手を止めて references/制約の起こし方.md へ回る。
新しい言語・アーキテクチャ・用途が来たら、そこで規約を新しく起こす ── ただし作る手順を通り、人の承認を経てからである。

語何を指すか
規約1本の文書。ファイル1つ。**

種別ごとに構造が違う**（構造／規則／道具／保証） |

語の一覧は references/語彙.md にある。

役割

- 入力の軸の値から、合致する制約を集める
- 集めた制約が、同じ対象について食い違っていないかを見る
- 実行できる制約はテストへ、それ以外は書き方の拘束として実装へ渡す
- 足りない制約に気づいたら、書く前に作る手順へ回す

処理対象と成果物

処理対象

これから書くコードと、その場面を表す軸の値である。

成果物

制約を満たすコードと、そのテストである。
集めた制約のうち、どれを満たし、どれが足りなかったかを添える。

入力の想定

受け取る情報解釈・既定値
言語明示されなければ、対象リポジトリの構成から判定せず、利用者に聞く
用途明示されなければ聞く。バックエンドAPI／Hook／MCPサーバー／フロントエンド等
アーキテクチャ受け取らない。用途の制約が指定する
実行環境明示されなければ、用途の制約が既定を持つ。常駐するか、都度起動されるか

実行手順

Step 1: 軸の値を確かめる

書く前に、どの場面に居るかを決める。
言語と用途が決まれば、アーキテクチャと実行環境は制約の側が指定する。

Step 2: 制約を集める

python3 scripts/collect.py --lang <言語> --purpose <用途>

返るのは制約の一覧である。
軸が一致したものだけが入る。
0件の欄があれば、そう表示される ── 「無い」ことが見える。

Step 3: 食い違いを見る

同じ対象について2つの制約があれば、そこで止める。
片方が穴（各自が決める）を宣言していれば、食い違いではない。

Step 4: 足りなければ、作る手順へ回す

状態次にすること
必要な制約が揃っているStep 5 へ進む
足りない書かない。

references/制約の起こし方.md へ回り、承認を経てから Step 2 へ戻る |

書きながら制約を足さない。
承認を経ていない制約は正本に入らず、次に同じ場面が来ても再現しない。
足りないのが1件でも、規約1本まるごとでも、作る手順の入り方は変わらない。

Step 5: 振る舞いを先に置く

制約は実装より先に在る。
実行できる制約をテストへ落とし、失敗させてから実装する。
実装を読んでからテストを書かない ── 実装の範囲内の振る舞いしか書けなくなる。

Step 6: 書いて、制約と照らす

書いたあと、集めた制約を1件ずつ当てる。
機械で検められる制約は、制約が持つ命令を走らせる。

出力形式

書いたコードとテストに加えて、次を報告する。

報告する内容書き方
使った軸の値言語・用途・アーキテクチャ・実行環境を並べる
集まった制約件数と、印の一覧
満たした制約印と、満たした箇所
足りなかった制約何が決まっていなかったかを書く。

推測で埋めたなら、そう書く |

ガードレール

- 書きながら制約を足さない。
足りないと分かったら、作る手順へ回す
- 実装を読んでからテストを書かない。
制約が先に在る
- 軸の値を推測しない。
分からなければ聞く
- 集めた制約を要約しない。
言明はそのまま当てる
- プロジェクト固有の決めごとを制約として扱わない。
出典を持たないものは制約ではない
- 穴（各自が決める）の外を特殊化しない。
必要なら、上の層の制約を直す

軸 ── 何が変わると、制約が変わるか

概要

軸とは、変えられるもののことである。
制約は、依存する軸の値が一致した場面でだけ効く。

軸と認める条件

一方を固定しても、もう一方が動くなら、それは別の軸である。
独立かどうかは概念の性質なので、実例の件数では決めない。

いまの軸

軸値の例何が決まるか
言語go ／ rust綴りと書式、失敗の運び方、並行の単位、テストが走る仕組み、標準の道具
アーキテクチャhexagonal層の名前、依存の向き、層ごとの責務
用途backend-api ／ hook ／ mcp-server ／ frontend外との契約、起動と終了、保証する振る舞い、採るアーキテクチャ、採る道具
実行環境resident ／ per-invocation状態の持ち方、終了の仕方、起動のたびに払う費用

軸を足すとき

手順内容
1いまの軸のどれかを固定しても、その候補が動くかを確かめる
2動くなら軸に上げる。動かないなら、既存の軸の値として表す
3既にある制約の宣言を見直す。

足した軸に依存していた制約が、広すぎる宣言のまま残る |

層

層とは、その制約が依存する軸の集合である。
層は宣言から導出されるので、あらかじめ並べない。

層依存する軸
lang.rust言語
arch.hexagonalアーキテクチャ
lang.rust+arch.hexagonal言語、アーキテクチャ
purpose.hook用途

上書き

下層は上層を上書きできない。
上書きが要ると分かったら、それはその制約の軸の宣言が足りなかったことの現れである。
値を変えず、依存する軸を直す。

例外は、上層が穴を宣言している場合だけである。
穴の外は特殊化できない。

出典 ── 制約は、何を根拠に書けるか

概要

出典を書けない制約は、制約として置けない。
「誰かがそう決めた」しか言えないものは、他のプロジェクトへ持って行けない。

認める出典

種類何を指すか添えるもの
規格言語仕様、RFC、プロトコルの仕様版と、原文で照合する文字列
原典公式ガイド、公式リファレンス、確立した文献落とした日と、原文で照合する文字列
実測自分で数えた記録測った対象、件数、測った日

認めない出典

種類なぜ認めないか
このプロジェクトの決めごと場面が変われば成り立たない。**

入れた時点で、どの場面でも同じ答えを返すという前提が壊れる** |

要約されたもの言い換えた時点で、原典とは別のものになる
出典を持たない経験則正しいかもしれないが、確かめる先が無い

照合の仕方

手順内容
1原文を落とし、落とした日と sha256 を残す
2制約が使う識別子を、原文の文字列でそのまま照合する
3照合できなかった識別子は、原典の名前として書かない

URL だけでは足りない。
指す先に届いているかを、誰も確かめられないためである。

版が変わったとき

「公式」であることは、正しさを保証しない。
版が上がったら、照合する文字列がまだ原文に在るかを確かめる。
無ければ、その制約は出典を失っている。

層ごとの規約 ── どの層に、どの規約を置くか

概要

層ごとに、決められることが違う。
だから置く規約も層ごとに違い、同じ4種別をすべての層へ並べない。

決められること／決められないこと

層決められる決められない
言語綴りと書式、失敗の運び方、並行の単位、テストが走る仕組み、標準の道具どんな層があるか（アーキテクチャが決める）／何を保証するか（用途が決める）
アーキテクチャ層の名前、依存の向き、層ごとの責務それを何で表すか（言語が決める）
言語 × アーキテクチャ層を何で表すか、向きを何で守るか、テストの置き場所何を保証するか（用途が決める）
用途外との契約、起動と終了、保証する振る舞い、採るアーキテクチャ、採る道具── ここが可変で、上の3層が空けた穴を埋める

種別

種別は、規約の型である。

制約の起こし方 ── 作る手順

概要

制約は、書く手順の中では作らない。
足りないと分かったら、この手順へ回る。承認を経たものだけが正本に入る。

手順

Step 1: 原典を落とす

要約を経由しない。
原文を落とし、落とした日と sha256 を残す。

対象どう落とすか
言語仕様・公式ガイド原文を取得して保存する。.md が返るなら、それが原文である
規格版を明示して保存する
実測測った対象・件数・測った日を、そのまま記録する

原典が見つからないなら、そこで止める。
出典を持たない制約は置けない。

Step 2: 言明を一文にする

検査できる最小の言明にする。
理由も例外も混ぜない。

悪いなぜ悪いか良い
エラーは値で返す。例外は呼び出し側が見落とすため言明と理由が1文に入っているエラーは値で返し、例外で流さない
命名は分かりやすくする検査できない型名は名詞句にし、動詞で始めない

1文に2つの命題が入るなら、それは2件である。

Step 3: 依存する軸を決める

その言明が、どの軸を固定したときに真であり続けるかを問う。

問い判定
言語を変えても真か真なら、言語には依存しない
アーキテクチャを変えても真か真なら、アーキテクチャには依存しない
用途を変えても真か真なら、用途には依存しない

依存する軸の集合が、そのまま置き場所（層）になる。

Step 4: 欄を埋める

templates/制約.md を写して埋める。
埋まらない欄が残るなら、まだ制約になっていない。

Step 5: 検め方を決める

誰が検めるか書くこと
機械走らせる命令を、そのまま書く
人何を見るかを書く。「気をつける」とは書かない

Step 6: 人の承認を得る

承認を経てから、正本へ置く。
承認されていない制約は、集める側から見えない。

Step 7: 索引を作り直す

python3 scripts/index.py

索引は導出物である。
手で書かない。

穴を宣言するとき

決めないことも、決定である。
「ここは各自が決める」と書けば、下の層がそこだけを埋められる。

書き方意味
穴か＝閉じている下の層は、これを特殊化できない
穴か＝ここは各自が決める下の層が、この1点だけを埋めてよい

穴を宣言しないまま、下の層が特殊化を求めてきたら、軸の宣言を疑う。

Rust における失敗の運び方

概要

回復できる失敗を値で運び、回復できない失敗だけを巻き戻しに任せる。

規則

印規則水準検証
RS-ERR-01回復できる失敗は Result で返し、panic! で流さない必須機械
RS-ERR-02失敗の型は、呼び出し側が分岐できる列挙にする必須人
RS-ERR-03失敗を握りつぶさない。捨てるなら、捨てる理由を書く必須機械

規則ごとの詳細

RS-ERR-01　回復できる失敗は Result で返し、panic! で流さない

項目内容
水準必須
検証cargo clippy -- -D clippy::unwrap_used -D clippy::expect_used
例外テストの中と、不変条件が破れた場合（回復できない失敗）
fn read_port(raw: &str) -> Result<u16, ParsePortError> {
    raw.parse::<u16>().map_err(ParsePortError::Invalid)
}
fn read_port(raw: &str) -> u16 {
    raw.parse::<u16>().unwrap()
}

RS-ERR-02　失敗の型は、呼び出し側が分岐できる列挙にする

項目内容
水準必須
検証失敗の型が String や Box<dyn Error> になっていないかを見る
例外無い
pub enum ParsePortError {
    Invalid(std::num::ParseIntError),
    OutOfRange { got: u32 },
}
pub fn read_port(raw: &str) -> Result<u16, String> { /* … */ }

RS-ERR-03　失敗を握りつぶさない。捨てるなら、捨てる理由を書く

項目内容
水準必須
検証cargo clippy -- -D unused_must_use
例外無い
if let Err(e) = flush() {
    // 書き出しの失敗は、次の起動で回復する
    tracing::warn!(error = %e, "flush failed");
}
let _ = flush();

対象外

何をどの層が決めるか
どの失敗を利用者へ見せるか用途
失敗をどの層で受けるかアーキテクチャ

下位へ委ねる判断

委ねる判断委ねる先委ねる理由
失敗の列挙をどこまで細かく分けるか用途分岐の必要は、外との契約で決まる

ヘキサゴナル構成の層

概要

業務の判断を中心に置き、外の世界との出入りを外周に置く。

構成要素

要素責務置き場所
domain業務の語彙と規則を持つ。外の世界を知らないdomain/
application業務の操作を組み立て、境界を跨ぐ入れ物を定めるapplication/
adapter（入口）外からの呼び出しを、業務の操作へ渡すadapter/inbound/
adapter（出口）業務が要る外の機能を、技術で満たすadapter/outbound/

関係

flowchart LR
    inbound[adapter 入口] --> app[application]
    app --> domain[domain]
    app --> port{{出口の約束}}
    outbound[adapter 出口] -.実装.-> port

許される依存

参照元参照先可否
domainいずれの層不可
applicationdomain可
applicationadapter不可
adapterapplication可

対象外

何をどの層が決めるか
層を何で表すか（package／module／crate）言語 × アーキテクチャ
どの層を実際に持つか用途

下位へ委ねる判断

委ねる判断委ねる先委ねる理由
出口の約束をどこに置くか言語 × アーキテクチャ置ける場所は言語の仕組みで変わる

概要

集める・検める・索引を出すの3つを、機械が行う。
同じ問いに同じ範囲が返らないと、そのあとの推論の入力が毎回変わるためである。

置くもの

命令何をするか返すもの
collect.py --lang <言語> --purpose <用途>軸の値が一致する制約を集める制約の一覧。0件の層も、0件として出す
check.py制約の形を検める欄の欠け、出典の空、フォルダ名と宣言した軸の食い違い
index.py人が読む索引を作り直す層ごとの一覧（生成物。手で書き換えない）

検めること

検査落ちる条件
欄の欠け言明・依存する軸・出どころ・検め方のどれかが空
出典原文で照合する文字列が空、または原文に無い
置き場所フォルダ名と、宣言した軸が食い違う
重なり同じ対象について2つの制約があり、どちらも穴を宣言していない
