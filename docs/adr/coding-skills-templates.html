name: coding-skills
description: 目的と言語を受け取り、その場面に効く規約を集めて、それに従ってコードを書くときに使う。規約が足りないときは、書く前に規約を起こす手順へ回す。「Goでバックエンドを書く」「RustでHookを書く」「この規約に沿って実装して」と言われたときに使う。

目的

その場面に効く規約だけを集め、それに従って書く。
規約が持つ規則は選択肢を減らす言明であり、どの規則にも、それが真であり続ける範囲がある。
範囲は軸（言語・アーキテクチャ・用途・実行環境）の組み合わせで決まる。

このSkillは、書きながら規約を作らない。
足りないと分かったら、書く手を止めて references/authoring.md へ回る。
新しい言語・アーキテクチャ・用途が来たら、そこで規約を新しく起こす ── ただし作る手順を通り、人の承認を経てからである。

語何を指すか
規約1本の文書。ファイル1つ ── 種別ごとに構造が違う（構造／規則／道具／保証）
規則守るべき言明1件。規則の規約と保証の規約だけが持つ

語の一覧は references/glossary.md にある。

役割

- 入力の軸の値から、合致する規約を集める
- 集めた規約が、同じ対象について食い違っていないかを見る
- 検証できる規則はテストへ、それ以外は書き方の拘束として実装へ渡す
- 足りない規約に気づいたら、書く前に作る手順へ回す

処理対象と成果物

処理対象

これから書くコードと、その場面を表す軸の値である。

成果物

規約を満たすコードと、そのテストである。
集めた規則のうち、どれを満たし、どれが足りなかったかを添える。

入力の想定

受け取る情報解釈・既定値
言語明示されなければ、対象リポジトリの構成から判定せず、利用者に聞く
用途明示されなければ聞く。バックエンドAPI／Hook／MCPサーバー／フロントエンド等
アーキテクチャ受け取らない。用途の規約が指定する
実行環境明示されなければ、用途の規約が既定を持つ。常駐するか、都度起動されるか

実行手順

Step 1: 軸の値を確かめる

書く前に、どの場面に居るかを決める。
言語と用途が決まれば、アーキテクチャと実行環境は規約の側が指定する。

Step 2: 規約を集める

python3 scripts/collect.py --lang <言語> --purpose <用途>

返るのは規約の一覧である。
軸が一致したものだけが入る。
0件の欄があれば、そう表示される ── 「無い」ことが見える。

Step 3: 食い違いを見る

同じ対象について2つの規則があれば、そこで止める。
片方が「下位へ委ねる判断」と宣言していれば、食い違いではない。

Step 4: 足りなければ、作る手順へ回す

状態次にすること
必要な規約が揃っているStep 5 へ進む
足りない書かずに止める ── references/authoring.md へ回り、承認を経てから Step 2 へ戻る

書きながら規則を足さない。
承認を経ていない規則は正本に入らず、次に同じ場面が来ても再現しない。
足りないのが規則1件でも、規約1本まるごとでも、作る手順の入り方は変わらない。

Step 5: 振る舞いを先に置く

規則は実装より先に在る。
検証できる規則をテストへ落とし、失敗させてから実装する。
実装を読んでからテストを書かない ── 実装の範囲内の振る舞いしか書けなくなる。

Step 6: 書いて、規則と照らす

書いたあと、集めた規則を1件ずつ当てる。
機械で検証できる規則は、その規則が持つ命令を走らせる。

出力形式

書いたコードとテストに加えて、次を報告する。

報告する内容書き方

集まった規約本数と、規則の印の一覧
満たした規則印と、満たした箇所
足りなかった規則何が決まっていなかったかを書く ── 推測で埋めたなら、そう書く
検証した手段走らせた命令と、その結果

軸 ── 何が変わると、規約が変わるか

概要

軸とは、変えられるもののことである。
規約は、依存する軸の値が一致した場面でだけ効く。

軸と認める条件

一方を固定しても、もう一方が動くなら、それは別の軸である。
独立かどうかは概念の性質なので、実例の件数では決めない。

いまの軸

軸値の例何が決まるか
言語go ／ rust綴りと書式、失敗の運び方、並行の単位、テストが走る仕組み、標準の道具
アーキテクチャhexagonal ／ data-port層の名前、依存の向き、層ごとの責務
用途backend-api ／ hook ／ mcp-server ／ frontend外との契約、起動と終了、保証する振る舞い、採るアーキテクチャ、採る道具
実行環境resident ／ per-invocation状態の持ち方、終了の仕方、起動のたびに払う費用

値を足すとき

値を足しても、既にある規約は変わらない。
新しいアーキテクチャを採るときは、その値の層を作り、規約を書く。

手順内容
1その値でしか成り立たない規約を書く（arch.<値>/）
2言語との組が要るなら、束ねの層を作る（lang.<言語>+arch.<値>/）
3用途の規約で、どの値を採るかを宣言する

軸を足すとき

手順内容
1いまの軸のどれかを固定しても、その候補が動くかを確かめる
2動くなら軸に上げる。動かないなら、既存の軸の値として表す
3既にある規約の宣言を見直す ── 足した軸に依存していた規則が、広すぎる宣言のまま残る

層

層とは、その規約が依存する軸の集合である。
層は宣言から導出されるので、あらかじめ並べない。

層依存する軸
lang.rust言語
arch.hexagonalアーキテクチャ
arch.data-portアーキテクチャ
lang.rust+arch.hexagonal言語、アーキテクチャ
lang.rust+arch.data-port言語、アーキテクチャ

1つの軸は、値を複数持つ。
hexagonal と data-port は並び、どちらを採るかは用途の規約が指定する。

上書き

下層は上層を上書きできない。
上書きが要ると分かったら、それはその規約の軸の宣言が足りなかったことの現れである。
値を変えず、依存する軸を直す。

例外は、上層が穴を宣言している場合だけである。
穴の外は特殊化できない。

出典 ── 規則は、何を根拠に書けるか

概要

出典を書けない規則は、規則として置けない。
「誰かがそう決めた」しか言えないものは、他のプロジェクトへ持って行けない。

認める出典

種類何を指すか添えるもの
規格言語仕様、RFC、プロトコルの仕様版と、原文で照合する文字列
原典公式ガイド、公式リファレンス、確立した文献落とした日と、原文で照合する文字列
実測自分で数えた記録測った対象、件数、測った日

認めない出典

種類なぜ認めないか
このプロジェクトの決めごと場面が変われば成り立たない ── 入れた時点で、どの場面でも同じ答えを返すという前提が壊れる
要約されたもの言い換えた時点で、原典とは別のものになる
出典を持たない経験則正しいかもしれないが、確かめる先が無い

照合の仕方

手順内容
1原文を落とし、落とした日と sha256 を残す
2規則が使う識別子を、原文の文字列でそのまま照合する
3照合できなかった識別子は、原典の名前として書かない

URL だけでは足りない。
指す先に届いているかを、誰も確かめられないためである。

版が変わったとき

「公式」であることは、正しさを保証しない。
版が上がったら、照合する文字列がまだ原文に在るかを確かめる。
無ければ、その規則は出典を失っている。

層ごとの規約 ── どの層に、どの規約を置くか

概要

層ごとに、決められることが違う。
だから置く規約も層ごとに違い、同じ4種別をすべての層へ並べない。

決められること／決められないこと

テスト観点 ── 何を確かめるかの一覧

概要

観点は、規約ではなく技法である。
言語にも用途にも依らないので、ここに一覧を置き、採るかどうかは用途の規約が宣言する。

観点

観点何を確かめるか効く場面
正常系期待された入力で、期待された結果になるすべて
境界値上限・下限・その前後で振る舞いが変わらない上限が契約に在るとき
異常系壊れた入力・欠けた入力を、失敗として扱う外部から入力を受けるとき
冪等性同じ入力を2度与えても、結果が同じになる再試行される可能性があるとき
順序非依存実行の順を変えても結果が変わらない並列に走るとき
並行性同時に走らせても、状態が壊れない常駐して複数を受けるとき
障害注入外部が失敗したとき、こちらが壊れない外部へ依存するとき
資源の解放失敗した経路でも、資源が返るファイル・接続を持つとき
後方互換前の版の入力を、いまの版が受け付ける契約を公開しているとき
性質テスト入力を機械的に広げても、性質が保たれる入力の形が広いとき

採り方

手順内容
1用途の契約を読み、そこに現れる制限（上限・順序・再試行）を書き出す
2制限に対応する観点だけを採る
3採らない観点は、採らない理由を書く

全部を採らない。
採る理由が書けない観点は、確かめる対象が無い。

順序非依存・資源の解放単体・結合

規約の起こし方 ── 作る手順

概要

規約は、書く手順の中では作らない。
足りないと分かったら、この手順へ回る。承認を経たものだけが正本に入る。

手順

Step 1: 原典を落とす

要約を経由しない。
原文を落とし、落とした日と sha256 を残す。

対象どう落とすか
言語仕様・公式ガイド原文を取得して保存する。.md が返るなら、それが原文である
規格版を明示して保存する
実測測った対象・件数・測った日を、そのまま記録する

原典が見つからないなら、そこで止める。
出典を持たない規則は置けない。

Step 2: 言明を一文にする

検査できる最小の言明にする。
理由も例外も混ぜない。

悪いなぜ悪いか良い
エラーは値で返す。例外は呼び出し側が見落とすため言明と理由が1文に入っているエラーは値で返し、例外で流さない
命名は分かりやすくする検査できない型名は名詞句にし、動詞で始めない

1文に2つの命題が入るなら、それは2件である。

Step 3: 依存する軸を決める

その言明が、どの軸を固定したときに真であり続けるかを問う。

問い判定
言語を変えても真か真なら、言語には依存しない
アーキテクチャを変えても真か真なら、アーキテクチャには依存しない
用途を変えても真か真なら、用途には依存しない

依存する軸の集合が、そのまま置き場所（層）になる。

Step 4: 欄を埋める

その規約の種別に当たる雛形（templates/構造の規約.md など）を写して埋める。
埋まらない欄が残るなら、まだ規約になっていない。

Step 5: 検め方を決める

誰が検めるか書くこと
機械走らせる命令を、そのまま書く
人何を見るかを書く。「気をつける」とは書かない

Step 6: 人の承認を得る

承認を経てから、正本へ置く。
承認されていない規約は、集める側から見えない。

Step 7: 索引を作り直す

python3 scripts/index.py

索引は導出物である。
手で書かない。

下位へ委ねる判断を宣言するとき

決めないことも、決定である。
「ここは各自が決める」と書けば、下の層がそこだけを埋められる。

書き方意味
委ねない下の層は、これを特殊化できない
下位へ委ねる下の層が、この1点だけを埋めてよい

委ねると宣言しないまま、下の層が特殊化を求めてきたら、軸の宣言を疑う。

概要

回復可能な失敗を値として運び、回復不能な失敗だけをパニックに任せる。

規則一覧

ID規則水準検証方法適用範囲
RS-ERR-01回復可能な失敗は Result で返し、panic! で流さない必須静的解析公開関数すべて

規則の詳細

RS-ERR-01　回復可能な失敗は Result で返し、panic! で流さない

項目内容
水準必須
根拠呼び出し側が回復の可否を選べなくなり、失敗が制御の外へ出る
検証方法cargo clippy -- -D clippy::unwrap_used -D clippy::expect_used

既存コードへの適用改修時に是正

適合例

fn read_port(raw: &str) -> Result<u16, ParsePortError> {
    raw.parse::<u16>().map_err(ParsePortError::Invalid)
}

違反例

fn read_port(raw: &str) -> u16 {
    raw.parse::<u16>().unwrap()
}

RS-ERR-02　失敗型は、呼び出し側が分岐できる列挙にする

項目内容
水準必須
根拠文字列の失敗は分岐に使えず、呼び出し側は文面の一致で判定するしかなくなる
検証方法公開関数の失敗型が String ・ Box<dyn Error> になっていないかを見る
例外実行ファイルの最上位（main）は集約した失敗型でよい
既存コードへの適用改修時に是正

適合例

#[derive(Debug, thiserror::Error)]
pub enum ParsePortError {
    #[error("port is not a number: {0}")]
    Invalid(#[from] std::num::ParseIntError),
    #[error("port out of range: {got}")]
    OutOfRange { got: u32 },
}

違反例

pub fn read_port(raw: &str) -> Result<u16, String> { /* … */ }

RS-ERR-03　Result を捨てない。捨てる場合は理由を残す

項目内容
水準必須
根拠捨てた失敗は観測できず、原因の切り分けができなくなる
検証方法cargo clippy -- -D unused_must_use
例外なし
既存コードへの適用一括是正

if let Err(error) = flush() {
    tracing::warn!(%error, "flush failed; retrying on next start");
}

違反例

項目内容
水準必須

Hook のテストの重心と計画

概要

外から観測できるのは標準入出力と終了コードだけなので、端から端までを厚く持つ。

保証する振る舞い

ID振る舞い検証の単位前提条件失敗したときの現れ方
HK-TS-01重心の配分どおりにテストが在る─単位ごとに件数を数えられる端から端までが薄いまま公開される
HK-TS-02すべてのテストが、変更のたびに走る─実行が1つの命令で済む走らないテストが残る

重心

確かめる単位重心根拠
単体高業務モデルと業務操作は、外部を用意せずに確かめられる
結合中入力アダプタの形式変換と、出力アダプタの契約を確かめる
端から端まで高呼び出し元から観測できるのは、標準入出力と終了コードだけである
性能低起動時間だけを見る。それ以外の要求が無い

端から端までを高くするのは、この用途では外部との接触面が狭いためである。
接触面が広い用途（バックエンドAPI）では、同じ配分にならない。

採るテスト観点

観点採否理由
境界値採る要求の上限（1 MiB）が契約に在る
異常系採る壊れた要求の扱いが契約に在る
冪等性採る同じ要求に同じ応答を返すことを保証している
並行性採らない呼び出しごとに1件だけを処理する
障害注入採らない外部への通信を持たない
性質テスト保留要求の形の幅を見てから決める

観点の一覧は references/test-perspectives.md にある。

テストの計画

項目定め
実行のタイミングコミット前（ローカル）と、変更の取り込み時（CI）
通過の条件すべてのテストが緑であること
実行の上限全体で30秒以内。超えたら、遅いテストを結合から単体へ落とす
対象外負荷試験。要求は1件ずつで、同時実行が無い

項目定め

使い方未到達の行の一覧を、確かめ漏れの発見に使う

Hook の実行時の依存

概要

起動のたびに払う費用を小さく保つため、実行時の依存を最小にする。

採用するアーキテクチャ

軸値採用理由
アーキテクチャdata-port中心が外部の機能を必要とせず、写して検めて出すだけで閉じる。反転が要らない
実行環境per-invocation呼び出しごとに1件を処理して終わる

別の用途が hexagonal を採ってもよい。
軸は値を複数持ち、どれを採るかはこの規約が指定する。

採用するツール

用途ツールバージョン指定採用理由代替候補
JSON の解釈と生成serde ＋ serde_json1契約が JSON で、型と対応づけられる手書きの解析
診断の出力tracing ＋ tracing-subscriber0.3標準エラーへの出力先を差し替えられるeprintln!
失敗型の実装thiserror1言語の規約（RS-ERR-04）を満たす手書き

採用しないツール

ツール採用しない理由
非同期の実行環境（tokio 等）呼び出しごとに1件を処理するだけで、並行の必要がない。起動の費用だけが増える
HTTP クライアント契約が標準入出力であり、外部への通信を持たない
設定用のフレームワーク読む設定が少なく、環境変数で足りる

バージョンの固定

対象固定の方法固定するファイル

対象更新の頻度判断者
