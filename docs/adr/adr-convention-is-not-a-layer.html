Architecture Decision Record

規約は層ではなく、実装を導くもう一つの入力とする

仕様・規約・実装の関係を、一直線の積み重ねから、knowledge だけを共通の出発点とする2つの経路へ改める。

01決定

規約は仕様の上でも下でもない。仕様と規約は同じ格で、knowledge だけを共通の出発点とし、実装とテストで合流する2つの経路である。

主文だけでは読み方が定まらない箇所を、同時に確定させる。

確定させること決定定めないと
仕様を書くとき規約を読むか読まない。読むのは schema の記入指示と knowledge だけ仕様に「この製品ではこう綴る」が流れ込み、実装の綴りが仕様へ回り込む
実装を導く入力仕様と規約の両方。どちらか一方では具体が決まらない仕様だけで実装が決まる形になり、仕様が実装の転記になる
schema と仕様の間に規約を置くか置かない。その位置に相当するのは、もう一方の経路の CodingSchema対称性のために層が増え、「仕様の綴り方」という名で実装の綴りが入る口ができる
どこまでを文書にするか上は knowledge（共通の出発点）、下は実装とテスト（2つが合流する先）抽象の段は上にも下にも無限に作れるので、どこまでを文書にするかが決まらない

02理由

実測規約は仕様を書くときに読まれていない

仕様の文書で規約を名指ししているのは3件だけで、いずれも規約そのものを扱うユースケース（check-usecase-class-drift 等が architectureRef を入力に取る）。仕様の執筆が規約に依存している箇所は1つも無い。

帰結層に置くと嘘になる

規約を仕様の上の層とすると「仕様は規約から導かれる」と読めるが、実際の依存はそうなっていない。規約が効くのは実装を導く辺だけであり、そこでのみ仕様と合流する。

読み取れる事実出所
規約は CodingSchema/v7 に従う文書で、仕様と同じ格architecture / coding-standard / test-standard の3件を実測
実装の置き場所・命名・単位・依存は、すべて規約の宣言から導出されている6つのドリフト検知が architectureRef を起点に動く
仕様は「何ができるか」しか持たない受け入れ基準・シナリオ・エラー契約。綴りは持たない設計

03変更前と変更後

何が何から導かれるか。

変更前

規約が仕様の上に居る。仕様は規約から導かれる、と読める

変更後

knowledge だけが共通で、そこから2つに分かれ、実装とテストで合流する

04この決定が動かすもの

対象どう変わるか
要件の一覧「5つの層・4本のつながり」という整理を、「2つの経路・6本のつながり」へ書き換える
網の穴の位置検知が無いのは、knowledge から記入指示へ向かう2本だけに特定される
規約の改訂の影響範囲規約を変えても仕様は変わらない。変わるのは実装とテストの導出結果だけ

05答えないこと

論点いまは決めない理由
knowledge から記入指示への2本を、どう突き合わせるか別の決定として起こす。この決定は形だけを定める
仕様と規約の分け目を裁く基準別の決定として起こす。形が決まらないと、どちらへ落とすかを論じられない
実装の綴りをどこから導くか別の決定として起こす（operationName の扱いを含む）

06承認

状態未承認この形に合意が取れてから、残る3つの決定を起こす。
