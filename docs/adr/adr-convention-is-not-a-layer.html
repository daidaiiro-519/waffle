Architecture Decision Record

規約は層ではなく、実装を導くもう一つの入力とする

Waffle では、何ができるかを仕様が、実装がどう在るべきかを規約が宣言し、その2つから実装とテストを導く。この決定は、その仕様と規約が互いにどういう関係にあるかを定める。以前は一直線に積んでいた。

01決定

規約は仕様の層ではない。仕様と規約は同じ格で、knowledge だけを共通の出発点とし、実装とテストで合流する2つの経路である。

決め手仕様の執筆は規約を読んでいない。上に積むと「仕様は規約から導かれる」と読め、実際の依存と食い違う。

03理由

仕様の執筆は規約に依存しておらず、規約が効くのは実装とテストを導くところだけだった。上下に積むと、無い依存を有ることにする。

測った仕様の文書のうち、規約を名指ししているのは3件だけ。いずれも規約そのものを入力に取るユースケースだった
だから
言えること仕様の執筆は規約に依存していない
一方で
測った実装とテストの置き場所・命名・単位・依存は、すべて規約の宣言から導出されている
ここで置いた前提
確かめていない今後も、仕様の執筆に規約が要る場面は現れない
合わせると
結論規約が効くのは実装とテストを導くところだけ。上下に積むと依存の向きを偽ることになる
ただし
反証「規約を扱うユースケースだから例外」は私が付けた解釈であって、観測ではない
段の裏付けと、崩れるときを開く（4件）
段裏付けの種別参照先崩れるとき
仕様のうち規約を名指しは3件実測仕様の走査と、各文書の入力欄の確認規約を入力に取らない仕様が、規約を参照し始めたとき
置き場所・命名は規約から導出される実測ドリフト検知が規約の識別子を起点に動く導出せず、対応を保存する検知が増えたとき
今後も規約は要らない確かめていない—製品ごとに仕様の書き方を変える必要が出たとき
規約が効くのは実装を導くところだけWaffle の設計判断knowledge に該当なし—

最後の段に knowledge の裏付けが無い理由 ── 近い knowledge に architecture-dependency-direction があるが、あれが扱うのはコードの依存（import・参照・依存性逆転）であって、文書どうしの依存ではない。原則と矛盾しないことと、原則から導かれることは別なので、引かない。

上から下へ読み順が通る上から順に追うだけで関係が分かる形なら、説明が要らない採る案 2本を並行に読む必要がある

05付随して決めたこと

対称性のために層を作らない、が4件を貫く。

論点決定
Schema と仕様の間に規約を置くか置かない。その位置に相当するのは CodingSchema
仕様を書くとき規約を読むか読まない。読むのは Schema が持つ記入と読取の指示と、knowledge だけ
実装を導く入力仕様と規約の両方。どちらか一方では具体が決まらない
どこまでを文書にするか上は knowledge、下は実装とテスト
それぞれの根拠を開く（4件）
論点根拠
schema と仕様の間対称性のために層を作ると、そこが実装の在り方を仕様へ持ち込む口になる
規約を読むか読ませると、規約が定めていること（置き場所・依存の向き・検証の置き方）が仕様へ流れ込む
実装を導く入力仕様だけで実装が決まる形にすると、仕様が実装の転記になる
どこまでを文書にするか抽象の段は上にも下にも無限に作れるので、どこで切るかを決めないと際限がなくなる
