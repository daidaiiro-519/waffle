Architecture Decision Record

図の宣言は、切り替えの前に全部移す

図の宣言を主張を軸にした形へ置き換えると決めたが、いまの宣言・schema・描画は古い形のままである。この記録は、移行の途中で描画が何を読むかを定める。

01決定

Waffle は、最新版の schema が持つ図の宣言8件を先にすべて書き直し、そのうえで描画を切り替える。古い宣言を読む経路は作らない。

決め手移行の対象は宣言8件だけで、切り替えの前に直しきれる。描かれた図180枚は、その宣言が読む値であって、人が1件ずつ判断する対象ではない。

02変更前と変更後

この決定が変えるのは、切り替えと書き直しのどちらを先に置くかである。宣言の形は前の決定で決まっている。

変更前 ── 順序を決めていない変更後 ── 書き直しを先に置く
描画が読む宣言の形古い形だけ新しい形だけ。古い形を読む経路は作らない
書き直す対象「180枚を1件ずつ」と見積もっていた最新版の宣言8件。180枚はこれに追随する
移行の途中の成果物—出る。切り替えの瞬間まで古い描画が動く
古い schema 版に残る26件—触らない。描画は最新版だけを読む

03理由

移行で書き直すのは宣言8件で、180枚はそれに追随する。量が小さいので、両方読めるようにして方針を緩める理由が無い。

測った図に相当する宣言は、最新版の schema 4種に8件だった（DomainSpecSchema に2、KnowledgeSchema に3、PlatformSpec に2、PresentationSpecSchema に1）。古い版まで含めると34件あるが、描画が読むのは最新版だけである
一方で
測った描かれた図は180枚ある。これらは8件の宣言が読む値であって、宣言そのものではない
だから
言えること移行で書き直すのは8件で、180枚はその書き直しに追随する。全部を人が1件ずつ判断する作業ではない
拠り所に当てると
言えること両方の宣言を読めるようにする案は、逸脱の量を理由に方針を緩めることに当たる。しかも量は8件で、緩める理由そのものが小さい
合わせると
結論8件の宣言を先に書き直し、そのうえで描画を切り替える。古い宣言を読む経路は作らない
ただし
反証1つの宣言が、主張の違う図を同時に受け持っている可能性がある。1つの名前で描かれた125枚が5種類の主張を担っていたという実測がある。宣言を1つ書き直すだけでは足りず、図ごとに主張を分ける必要が出るかもしれない
段の裏付けと、崩れるときを開く（4件）
段裏付けの種別参照先崩れるとき
最新版の宣言は8件実測schema 10種の最新版を走査し、図に相当する宣言を数えた描画が古い版の schema も読むと分かったとき
描かれた図は180枚実測図を持つ document の全数（承認済みの前の決定で測った）—
量を理由に方針を緩めないknowledgepolicy-is-ssot-measurement-is-judged ── 「逸脱の量を理由に方針を緩めると、作り直す意味が消える」「既存を根拠にしてよいのは、移行の入力としてなど3つに限られる」この knowledge が作り直し以外の場面にも当てはまると分かったとき
先に直してから切り替えるWaffle の設計判断knowledge に該当なし—

数の使い方 ── policy-is-ssot-measurement-is-judged は、既存の実測を移行の入力として使うことを認めている。ここで8件という数を使っているのは移行の段取りを決めるためであり、宣言の形そのものは、この数から決めていない。形は前の決定で既に決まっている。

04判断を分けた軸

採る案は4つの条件のうち3つを満たす。落とすのは1つで、8件すべてを直してから切り替えることになる。

案 移行の途中でも成果物が出る

移行の途中でも成果物が出る決め手描画は日々の作業で使う。途中で図が出なくなると、移行のあいだ他の作業が止まるか、図の無い成果物が配られる先に切り替える 直していない宣言の図が出なくなる
新旧2つの経路を実装に抱えない同じ対応が2か所にあると食い違う。しかも古い経路をいつ落とすかを後で決めることになり、たいてい落とされない両方読む 2つの経路を抱える
移行し忘れが分かる直し忘れた宣言が黙って古いまま動くと、いつまでも混在に気づけない両方読む 古いままでも動くので、気づく機会が無い
切り替えの前に全部直さなくてよい対象が多いと、全部直すまで切り替えられないことが止まる理由になる8件を先に直す（採る） 8件すべてを直してから切り替える

この条件を最後に置いた理由 ── 対象が8件だと分かったので、重みが小さい。数十件なら、この条件が決め手になっていた可能性がある。

05付随して決めたこと

書き直しを先に置くと、どこまでを書き直しの範囲とするかが決まる。

論点決定
描かれた180枚をどうするか触らない。宣言が読む値の形が変わらない限り、書き直しの対象にしない
古い schema 版に残る26件触らない。描画は最新版だけを読む
書き直しの単位schema の版を切って移す。宣言を版の中で書き換えない
それぞれの根拠を開く（3件）
論点根拠
描かれた180枚をどうするか宣言は値の在りかを指す。指し方が変わっても、指される値は同じ場所にある。値まで書き直す前提で見積もったのが、180枚という数の出どころだった
古い schema 版に残る26件古い版は、その版で作られた document のために残っている。描画が最新版だけを読む以上、書き直しても誰も読まない
書き直しの単位版を切らずに書き換えると、同じ版の宣言が途中で意味を変える。その版で作られた document が、作られた時と違う描かれ方をする

06答えないこと

宣言の中の判断と、実装の順序は、この決定では扱わない。

項目種別行き先
1つの宣言が主張の違う図を受け持つとき限界行き先を持たない。反証に挙げた通り、8件を書き直す途中で分かる。分かれた時点でこの決定を見直す
描画の実装をどの順で作り直すか範囲外仕様の受け入れ基準をテストへ落とす段で決める
Markdown の構文をどう組み立てるか範囲外仕様に受け入れ基準がある。この決定は順序だけを扱う

07承認

状態取り下げいつ2026-08-15承認を求めずに取り下げた。移行の対象を数えた結果を決め手に据えたが、この作業で引いている knowledge は、実測を方針の根拠にすることを禁じている。そのうえで向き（古い宣言を読む経路は作らない）は、その knowledge から直接導かれるため、決めることが残っていない。
