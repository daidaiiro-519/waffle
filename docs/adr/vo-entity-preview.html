# Schema を特定する鍵：vo-schema-ref

## 概要

Document が適合する Schema を、名前と版の組で一意に指す鍵。
鍵であって、Schema の中身の写しではない。

## 何を表すか

適合する Schema そのものではなく、**それを特定できる鍵**を表す。
どの Schema かが決まればよく、その Schema が何を宣言しているかは持たない。

## 属性

| 属性 | 型 | 説明 |
|---|---|---|
| value | string | `<スキーマ名>/<版>` の形（例: `KnowledgeSchema/v6`） |

## 振る舞い

不変。値が等しければ等価。
指し先の Schema が新しい版を持っても、この鍵は変わらない。

## この値が常に満たすこと

| 規則 | 担保 |
|---|---|
| 値は、実在する Schema の名前と版を指す | 検査 |
| 版の部分は、Schema の側が持つ版の表記と一致する | 検査 |
| 名前と版を分けて持たない。分解は、指し先を解決するときに行う | 構造 |

## この値が常に満たすことの筋書き

### 版を欠いた値では作れない

| 分類 | 観点 |
|---|---|
| 異常系 | 不変条件: 値は、実在する Schema の名前と版を指す |

```gherkin
Scenario: 版を欠いた値では作れない
  Given `KnowledgeSchema` という版を欠いた文字列
  When Schema を特定する鍵を作る
  Then 拒否される
```

### 実在しない Schema を指す値では作れない

| 分類 | 観点 |
|---|---|
| 異常系 | 不変条件: 値は、実在する Schema の名前と版を指す |

```gherkin
Scenario: 実在しない Schema を指す値では作れない
  Given `NoSuchSchema/v1` という文字列
  When Schema を特定する鍵を作る
  Then 拒否される
```

### 同じ値なら同じものとして扱う

| 分類 | 観点 |
|---|---|
| 正常系 | 振る舞い: 値が等しければ等価 |

```gherkin
Scenario: 同じ値なら同じものとして扱う
  Given 同じ文字列から作った2つの鍵
  When 2つを比べる
  Then 等しいと判断される
```

# Schema に適合する文書：ent-document

## 概要

Schema で構造を定義された JSON。作られ、検証され、描かれ、置き換えられる。
中身も状態も変わるが、同じものであり続ける。

## 同一性

**`documentId` で同一性を持つ。**
content が入れ替わっても、状態が進んでも、同じ Document である。
ここがエンティティと値オブジェクトの分かれ目で、
Schema は変わらないため値、Document は変わるためエンティティになる。

## 属性

| 属性 | 型 | 説明 |
|---|---|---|
| documentId | DocumentId | 同一性を決める |
| schemaRef | SchemaRef | 適合する Schema を特定する鍵。Schema の中身は持たない |
| status | Status | 進む向きが決まっている |
| content | 構造化データ | `schemaRef` が指す Schema に適合する |

## この型が常に満たすこと

| 規則 | 担保 |
|---|---|
| content が Schema に適合しない限り、確定した状態へ進めない | 守り |
| 終端の状態に達したあとは、いかなる操作も受け付けない | 守り |
| `schemaRef` は、実在する Schema を指す | 検査 |

## この型が常に満たすことの筋書き

### 適合しない中身では確定へ進めない

| 分類 | 観点 |
|---|---|
| 異常系 | 不変条件: content が Schema に適合しない限り、確定した状態へ進めない |

```gherkin
Scenario: 適合しない中身では確定へ進めない
  Given Schema に適合しない content を持つ Document
  When 確定した状態へ進めようとする
  Then 拒否される
```

### 終端に達したあとは何も受け付けない

| 分類 | 観点 |
|---|---|
| 異常系 | 不変条件: 終端の状態に達したあとは、いかなる操作も受け付けない |

```gherkin
Scenario: 終端に達したあとは何も受け付けない
  Given 終端の状態にある Document
  When いずれかの操作を求める
  Then 拒否される
```

### 中身が入れ替わっても同じ Document である

| 分類 | 観点 |
|---|---|
| 正常系 | 同一性: documentId で同一性を持つ |

```gherkin
Scenario: 中身が入れ替わっても同じ Document である
  Given ある Document
  When content を書き換える
  Then 同じ documentId のまま、同じ Document として扱われる
```

05この案が抱えている、まだ決めていないこと

完成イメージを作って初めて見えた3点。ここは判断を仰ぎたい。

論点何を決めるか
受け入れ基準ではなく不変条件を持たせること呼び出せる操作を持つのは3つに限られるため受け入れ基準は持たないが、不変条件とその筋書きは持ち、集約と同じ形でテストへ転写する。この分け方でよいか
不変条件の 担保 の列どこで守るか（検査／構造）を仕様が述べている。既存の集約が持つ欄を写したもの。取り除いても仕様が述べることは変わらないなら、上限を越えている可能性がある。12件が使っているため、この場では決めない
エンティティの declarationsSchema が持つ x-prompt-write などの宣言を、この属性に束ねている。宣言そのものを値オブジェクトとして立てるなら、ここは参照になる
