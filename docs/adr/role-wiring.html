skill-router ／ 抽象の作り直し

役で配線する

skill-router は、router になっていない。 「実務Skill」「advisor」というWaffle の分類が、欄の意味そのものに入っているので、 別のプロジェクトへ持っていくと語ごと合わない。 欄を「役」で書き直すと、Waffle の語は1つも要らなくなる ── 同じ8行はそのまま書ける。

いまの欄と、役で書いた欄

どこが Waffle に固まっているか

「表の中身はこのリポジトリ固有のデータで、機構本体は使い回せる」とガードレールに書いてある。 だが実際には、データではなくモデルの側に Waffle が入っている。

いまの作りモデルか、データか
欄名combinedSkills＝「一緒に呼ぶ Skill」 モデル。役という概念が無く、呼び方だけが残っている
制約「指定できるのは advisor Skill のみ」 モデル。advisor は Waffle の分類で、他所には無い
強さ必須 ／ 推奨（＝結果を参考情報として渡す） モデル。advisor が居る前提の意味づけで、「飛ばす」が無い
呼び出し元Investigation ・ Spec-authoring ・ Handoff-authoring ・ Implementation モデル。役割・入力の想定に固有名が直接書かれている
例外規則「Handoff-authoring と Implementation の行は動的に引き継ぐ」 モデル。特定の行についての規則が、機構の側に居る
別ブロックadvisorBoundaries（advisor 間の委譲マップ） モデル。配線とは別の関心で、router の持ち物ではない
表の8行Spec-authoring × ddd-advisor … データ。ここだけは正しくデータになっている

直したあと ── 欄は4つ

同じ8行が、役の形でそのまま書ける

役ドメイン仕様の設計判断を確かめる
　要求元Spec-authoring（ドメイン仕様書）
　担い手ddd-advisor ・ tech-lead-advisor
　無いとき止める
役原典を落とし、原文の語で照合する
　要求元brainstorm（原典の札を付けるとき）
　担い手source-fidelity
　無いとき飛ばす ── 呼ぶ側が自分で落として手元に残す
役（利用者が足す）── 1行足すだけで、ブレストが通る

advisor だけを当てる、という慣習はデータの側に降りる ── このリポジトリでは実際そう運用するが、機構がそれを強制しない。 advisorBoundaries は配線とは別の関心なので、router から外す （どこへ置くかは、まだ決めていない）。

それで、最初の問いはどうなるか

私の答え skill-router のモデルを「役 ・ 要求元 ・ 担い手 ・ 無いとき」の4欄へ作り直します。 表は増やさず、1つのままにします。 source-fidelity は「原典を落とす役」に当てられた1実装、 advisor は「確かめる役」に当てられた実装 ── どちらも同じ表の行になります。
  • brainstorm 側に書くのは1文だけ：「原典の札を付けるときは、その役が配線されていれば通る。無ければ自分で落として手元に残す」。Skill の名前は出てこない
  • 拡張の口：利用者は1行足すだけ。役に名前を付け、担い手を当て、無いときどうするかを書く
  • 引き受けること：これは SkillSchema への破壊的な変更（欄の意味が変わる）。 決まりでは破壊は認めるが、静かに壊さず、まとめて上げる。 既存8行は移せることを上で確かめた
  • いま決めないこと：advisorBoundaries の行き先。 router から外すことだけ決め、置き場所は別に問う
  • 落とした案：表を2つにする → 1つ目が router でないという問題が残ったまま／ いまの欄名のまま制約だけ緩める → 「一緒に呼ぶ」という呼び方の語が残り、役が現れない
