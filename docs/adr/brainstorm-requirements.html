brainstorm ／ 要件

brainstorm の要件と、根拠の出どころ

この Skill が何をするかと、どう作られていなければならないか。 そして、ブレストの結果が何を一次情報にして、何と突き合わせて答えになるのか。 外部依存がどこに在り、持ち出したら何が切れるのかまで、隠さずに置く。

根拠は、どう作られるか

案は「良さそうだから」残るのではない。三種の札のどれかで支えられたものだけが残り、 支えられない案は落ちる ── 落ちた案は名前と『何が壊れるか』を添えて残す。

一次情報は、三種類しかない

札何が一次情報かどこから取るか突き合わせる相手
原典 外にある文献・規格・実装の原文 落として保存したもの（docs/adr/sources/ の14件）と、 advisor が蓄えた知識（.waffle/skills/ddd-advisor/references/knowledge/ の22件） 案が原文の記述と食い違っていないか。言い換えず、原文の語で当てる
実測 このリポジトリを数えた結果（hook 15本の内訳、CLI に在る命令、規約の層の数） その場で数える。利用者には聞かない 案が「いまそうなっている」という前提を置いていないか
決まり この盤面ですでに決着した論点 盤面そのもの 案が、先に決めたことと衝突していないか
前提 まだ支えが無い置き方。そう書いて残すー のちに原典か実測で置き換わるべきもの

再定義の対象そのものを根拠にしない、という決まりがここに掛かる ── いまの schema が「そうなっている」ことは、その schema をどう作るかの根拠にはならない（循環する）。

機能要件 ── 何をするか

要件満たしていないと、どうなるか
F-1論点を3〜5個立て、依存関係を自分の側で持つ 順番の管理が承認者へ渡り、盤面全体を頭に入れないと答えられなくなる
F-2案を複数出し、提示より前に反証して1つに絞る 落ちると分かっている案を出すことになる
F-3前提が片付いた問いだけを1回にまとめて出す 答えられない問いに答えさせるか、1問ずつの往復になる
F-4答えの直下に完成イメージ（図、または変更前後の差分）を畳まずに置く 文章だけで決定を受け取ることになり、納得できないまま押すことになる
F-5出どころ・道筋・落とした案を畳んで添える 根拠を見ないまま押した承認になる ── それは承認ではない
F-6どの問いにも自由に書ける欄を置く 決められた値で言えないことが、どこにも行き場を失う
F-7承認・差し戻し・書き足しを受け取り、1件ずつ残す 何を差し戻したかが、あとから読めなくなる
F-8差し戻された問いは、直した答えを1つ出す 案を並べ直すことになり、また選ばせることになる
F-9決着を盤面へ記録し、次に答えられる問いを引き直す 決着が反映されず、同じ問いが二度出る
F-10変わった箇所を印として残す（変更前と理由が開く） 履歴が別の場所へ行き、いまの盤面と突き合わせながら読むことになる

非機能要件 ── どう作られていなければならないか

要件どう確かめるか
N-1認知負荷：1回に出すのは答えられる問いだけ。読む量は、答え＋完成イメージで足りる 画面に出ている字数を数える（実測）。裏づけは畳んであり、数に入らない
N-2追跡できること：どの根拠にも札が付き、回答は1回1件で残る 札の無い根拠は置けない（道具が止める）。回答は消さずに積む
N-3図が壊れていないこと：文字の重なり・はみ出し・線が箱を貫くことが無い figcheck.py に通す。目で読み返しても見落とすので機械で当てる
N-4形が決まっていること：回答の諾否と差し戻し理由は決められた値だけ JSON Schema と、受け取り側の検査。形しか見ない ── 中身の妥当性は人が見る
N-5沈黙すること：未読の回答が無ければ、Hook は何も出さない 回答0件で走らせて、出力が空であること
N-6他人の道具に依らないこと：やり取りはテキストとファイルだけ Skill の受け渡しに特定ツール専用の仕組みを使わない。回答は素の JSON
N-7独立して判断されること：反証は提示より前に済ませる 提示後に反証すると、結論に引きずられる

いま、外部依存はどこにあるか

実線は要るもの、破線は無くても止まらないもの。 build_board.py ・ figcheck.py ・ serve.py の import を数えたところ、 標準ライブラリ以外は0件だった（実測）。

何に依るか持ち出したら
道具何にも依らない ── 標準ライブラリだけ そのまま動く
見た目書体を外から読む 読めなくても崩れない（代わりの書体を並べてある）
原典外の文献・規格・実装 落として保存した分は残る ── いま14件、sha256 と日付つき
knowledgeadvisor が蓄えた22件 切れる ── ただし在れば使う扱いなので、止まらない
実測対象のリポジトリそのもの 持ち出し先にもリポジトリはある ── 依存として健全
受け渡しHook だけ Claude Code に依る フックは動かないが、「読んで」の一言で回る

この分かれ方が、あるべき形だと考えます。 道具は自己完結、材料は外に在る ── 原典が内側にあったら、それは原典ではない。 危ういのは依存があること自体ではなく、取ってきた原文が手元に無いのに、札だけ付く状態です。

私の答え 「原典の札を付けるなら、原文を落として手元に残す」という規律を1つ足します。 落とす手段の在り処（source-fidelity）だけを書き、呼び方は書きません。 advisor の knowledge は参照として足さず、「在れば使う」に留めます。
  • なぜ足すか：取得の経路を書かない原則は、言明としては在っても実行時に参照先を持たない
  • なぜ knowledge を足さないか：持ち出すと切れる参照を必須にすると、上の図の箱が閉じなくなる
  • 引き受けること：brainstorm が他の Skill の名前を1つ知る ── ただし在り処だけなので、テキストで疎に結んだままにできる
  • 落とした案：brainstorm 自身に原典を落とす手順を持たせる → 同じ手順が2か所になり、片方が古くなる
