Architecture Decision Record

コマンドを、判断に要るデータのある場所へ戻す

Schema の実装は27行でクラス宣言だけ、コマンドは0件。一方で骨格を作るユースケースは412行ある。骨格の形を知っている唯一の相手が空で、判断が外へ出ている。

01決定

Waffle は、集約のコマンドを、その判断に要るデータのある場所へ置く。Schema は「骨格を作る・新しい版を切る・適合を判定する」を持ち、Document は「値を埋める・値を取り出す・描く・終端化する」を持つ。ユースケースは調整だけを担う。

決め手骨格の形を知っているのは Schema だけである。いまは Document の create が「schemaRef と documentId から骨格を生成する」と述べており、作られる側が自分を作ることになっている。

03理由

骨格の形を知っている唯一の相手が空で、判断が外へ出ている。値を埋めるコマンドは宣言にすら無い。

測ったSchema の実装は27行でクラス宣言だけ、宣言されたコマンドは0件。一方、骨格を作るユースケースの実装は412行ある
だから
言えること骨格の形を知っている唯一の相手が空で、判断が外へ出ている
Document の側も見た
測ったDocument のコマンド4件は、名前がユースケースと同じである。しかも create の説明が「schemaRef と documentId から骨格を生成する」で、作られる側が自分を作ることになっている
さらに
測った値を埋めるコマンドが宣言に無い。それでいて適合を判定するコマンドの説明が「判定結果の永続化は別途行う」と、宣言されていない操作を前提にしている
拠り所に当てると
言えること呼び出せる操作を持つのは業務ユースケース・業務サービス・集約のコマンドの3つである。集約が持つべき操作が、ユースケースの側にある
合わせると
結論コマンドを、判断に要るデータのある場所へ戻す。ユースケースは調整だけを担う
ただし
反証単体の取得は、Document の値と Schema の読み方の指針を組み合わせて返している。Document のコマンドだけでは完結せず、ユースケースに残る仕事がある。「単体の操作はすべて集約のコマンド」とは言い切れない
段の裏付けと、崩れるときを開く（5件）
段裏付けの種別参照先崩れるとき
Schema が27行・コマンド0件、ユースケースが412行実測実装の行数と、集約が宣言するコマンドの数を数えた—
Document のコマンドがユースケースの写し実測4件の名前と説明を読んだ名前が同じでも中身が違うと分かったとき
値を埋めるコマンドが宣言に無い実測コマンドの一覧と、適合を判定するコマンドの説明—
呼び出せる操作を持つのは3つknowledgeoperation-contract-closes-invariants—
判断はデータのある場所へ置くWaffle の設計判断knowledge に該当なし—

最後の段に knowledge の裏付けが無い理由 ── operation-contract-closes-invariants はどこに操作が付くかまでは述べるが、同じ集約の中でどの判断をコマンドに持たせるかは持たない。データのある場所へ置くという指針は、この製品の側で置いている。

05付随して決めたこと

コマンドを移すと、ユースケースに何が残るかが決まる。3点を同時に決めた。

論点決定
ユースケースをどうするか無くさない。中身を移し、調整だけを残す
単体の取得はどちらか両方。値は Document、読み方の指針は Schema。束ねるのはユースケース
実装の domain/services 24件移し先を1件ずつ判定する。この決定では判定しない
それぞれの根拠を開く（3件）
論点根拠
ユースケースをどうするかユースケースが在ること自体は誤りではない。誤りは、判断がその中にあることである。調整と判断を分ければ、判断は他からも呼べる
単体の取得はどちらかいまの取得は値と指針を組にして返している。値は Document のもの、指針は Schema のもので、束ねる相手が要る。「単体の操作はすべて集約のコマンド」とは言い切れないのは、このためである
実装の domain/services 24件仕様に書かれた業務サービスは5件で、19件の開きがある。この開きが、集約から出された判断なのか本当の業務サービスなのかは、1件ずつ見ないと分からない
