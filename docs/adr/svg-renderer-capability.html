00結論

中心の問いへの答え

構造化データが指定できる範囲は、表現の範囲ではない。データが言えることは、レンダラが描くことの内側にある。そしてレンダラはその外側へ、頼まれていない線を描き足す。さらに、ADRの関門1が要求する表現は、そのどちらの内側にも無い。

仕組みそのものは completion_image_layout.py（90行）が座標を計算し、handoff_html_template.py（481行）がそれを <rect> と <path> に変換する、という2段である。人が座標を書く場所は無い。

01いま指定できること

構造化データ側の語彙は、実際にはこれだけだった。件数は出荷済みの引き継ぎ文書19本を数えたもの。

箱 nodeid / title / sub—本文は2行まで。3行目を置く場所が無い

03実際に渡して測った

ADRの関門1の図が言いたいことを、いまのデータ形式へ翻訳して compute_layout に渡した。囲みと左右2面は渡す口が無いので、層として積むしかない。

# 問題空間に 事業領域・業務領域、解決空間に 区切られた文脈・業務ユースケース・集約
# 引きたい関係は「業務ユースケース → 業務領域（対応）」の 1本だけ

viewBox: 700 x 184

自動で引かれた包含の矢印:
  (事業領域 → 区切られた文脈)  (事業領域 → 業務ユースケース)  (事業領域 → 集約)
  (業務領域 → 区切られた文脈)  (業務領域 → 業務ユースケース)  (業務領域 → 集約)

宣言した関係の矢印:
  (業務ユースケース → 業務領域, dependency)
表3 ── 頼んだものと、出てきたもの
　本数中身
データで宣言した線1業務ユースケース → 業務領域（対応）
実際に描かれた線7上記1本 ＋ 自動導出6本
✗ 事実と食い違うもの6事業領域は集約を含まない。業務領域は区切られた文脈を含まない（向きが逆）
この6本が意味すること

レンダラが、データが一度も言っていないことを図として主張した。隣り合う層のノード数が 2 と 3 で一致しないため、全対全（2×3）のフォールバックが働いた結果である。仕様どおりの挙動でバグではない——ノード数が 1 対 n か n 対 n のときだけ意図した線になる、という前提で書かれている。

つまり表現の上限は「描けるかどうか」だけでは測れない。描かれてしまうものも上限のうちに入る。

足りないものいまの状態手を入れる場所

05では構造化データの範囲は何が決めるのか

測定から言えること

レイアウトの計算式が先にあり、構造化データの形はそれに従って後から決まる。schemaに frames を足しても、座標計算が囲みを知らなければ描かれない。逆に、座標計算が囲みを解けるようになれば、schemaに何を足すべきかは自動的に決まる。
