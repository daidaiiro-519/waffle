specを書き終えたら、実装へ移る前に必ずHandoffを作り、ユーザーへ提示して合意を得る。ユーザーから求められて初めて出すのではなく、Orchestrator自身から提案するspecは『何が正しいか』しか運ばず、『なぜその形にしたか』『どこに何を置くか』は運ばない。specを書き終えた直後は成果物が積み上がって手が動く状態になり、そのまま実装へ入りやすい。実際にこのセッションで3回続けて飛ばし、そのたびにユーザーから指摘された。指摘されてから出すのでは、毎回ユーザーが工程の番人をすることになるwaffle scaffold create --schemaRef HandoffSchema で作り、waffle render-handoff-template でHTMLにしてユーザーへ提示する。descriptionにはこのHandoffが担うユースケースの識別子を必ず並べる（Handoffが指すユースケースをフックが突き合わせるため、境界づけられたコンテキストを指すだけでは、以後どれだけ仕様を足しても検知されない）。未解決の観点はreviewStatusにopenのまま残してよい——全部を解いてから出すのではなく、決まっていないことが見える状態で出す

UDDループ（調べる→決める→引き継ぐ→作る）を1本の道として通し、作業ごとにどこまで踏むかを判断するOrchestrator。決めることがある作業で、決める段と引き継ぐ段を省かないことに責任を持つ。構造の検証・生成・描画はWaffleが機械的に担い、判断はアドバイザーSkillが敵対的に確かめる。

name: doc-writing-skills
description: 日本語のテクニカルライティング文書を書く・直すときに必ず使うスキル。設計文書・仕様・報告・README・学術文書など、人が読む文書を書き起こす前と、書いたあとに使う。「文書」「まとめて」「書いて」「ドキュメント」と言われたとき、および既存のmdやHTMLの本文を直すときに必ず使う。
version: 1.0.0

目的

技術文書としても学術文書としても違和感のない日本語を書く。

満たすこと
論意味が通り、論が崩れていない
構造情報が、その型に合った形で置かれている
文調人が読んで、一度で意味が取れる
語彙同じ文脈では、同じものが同じ語で呼ばれている

判断の材料は10の概念である。
どれも公開された規格・指針から導いており、出どころを最後の節に置く。

出すには、2つのゲートを通す。

ゲート何を見るか誰が決めるか
10件にできるものが、0件であること機械
210の判定すべてに、結果が1行ずつあること書き手

ゲート2が保証するのは、判定を当てたことだけである。
何を直すかは、書き手の判断に残る。

役割

- 書いたものに、10の概念から導いた判定を当てる
- 判定を、読む人がその場でできる1つの操作に降ろす
- 原典から導けない決めは、そう書く
- 当てなかった判定を、報告に書く

処理対象と成果物

処理対象

これから書く日本語の文書、または既に書いてある日本語の文書である。

成果物

10の判定を当て、直したか残したかを言える文書である。

入力の想定

受け取る情報解釈・既定値
読み手明示されなければ、その文書を初めて開く人とする
用語の定め対象フォルダに用語を定めた文書があれば、それに従う
文脈の境界明示されなければ、文書1本を1つの文脈とする

#概念規則判定
1読み手が組み立て直す作業を、書き手が引き受ける1文の中で、読み手に計算をさせない頭から一度読んで、戻らずに意味が取れるか。戻ったなら、戻らせた語が原因である
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しだけで、何がどこにあるかが分かるようにする見出しだけを抜き出して、順に読む
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを当てる。文脈が変わるなら、変わることを書く用語を書き出し、同じ意味の別の語が無いかを見る
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は持ち込まない。持ち込むなら、新しい語だと書いて定義する語の出どころを言えるかを見る。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

Step 3: 直したか、残したかを言う

判定に当たった箇所を、直すか、理由を付けて残すかのどちらかにする。
理由が書けないなら、それは直す対象である。

Step 4: 2つのゲートを通す

ゲート1は機械が決める。

python3 <skill>/scripts/gate.py <ファイル...>
python3 <skill>/scripts/gate.py --synonyms 用語.tsv <ファイル...>
検査拠って立つもの
見出しの階層が飛んでいる概念4
文体が混ざっている概念6
並んだ項目の語尾が揃っていない概念6
文字で図や表を描いている概念2
同じ意味の語が2つある（対を渡したとき）概念7
強調が描画されない媒体の決め

最後の1つだけ、概念から導けない。
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
別枠であることを、--list と名簿に書いてある。

概念3と概念9は、ゲートに入らない。
数は数えられるが、いくつで形を変えるかは文脈で変わるので、0件にできない。
判定として、書き手が当てる。

ゲート2は書き手が言う。
報告に、10の判定すべての結果を1行ずつ書く。1つでも欠けていれば、通っていない。

出力形式

報告する内容書き方
直した箇所概念の番号ごとに、どこを何から何へ直したかを表で出す
残した箇所場所と、残す理由を書く
ゲート1の結果通ったか、通っていないか。件数を書く
当てなかった判定番号で書く。全部当てたなら、そう書く。1つでも欠ければゲート2は通っていない
確かめていないこと確かめていないことを、確かめたと書かない

ガードレール

- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で揃えて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を当てない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確かめていない内容を、確かめたように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを通していないものを、出さない。通していないなら、そう書く
