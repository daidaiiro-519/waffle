03図

図を何で表し、どこに置くか。文字と図をひとつの語彙として扱う。

成果物種別状態何を決めたか
図の語彙を、描き方の名前から主張の名前へ移す決定承認済みWaffle は、図の部品名を描き方の名前からその図が何を主張するかへ置き換える。書き手が使える形は固定し、どの欄を書けるかは主張が決める。描き方は、書き手が選ぶのではなく主張から決まる。
図の宣言を、主張を軸にした形へ置き換える決定承認済みWaffle は、図の宣言の軸を描き方の指定から主張へ移す。描き方の指定は宣言から外し、主張から決まるようにする。
図の宣言を、Document の内側の値として置く決定承認済みWaffle は、図の宣言を、Document の集約の内側にある再帰する値として置く。16の主張はその属性であり、種別ではない。欄の必須・禁止を守るのは schema ひとつとする。
語彙ごとの描画イメージ材料—語彙ごとに、どう描かれるかを並べたもの
部品ごとの描画結果材料—描画部品ごとに、実際の出力を並べたもの

04仕様と実装の境界

仕様がどこまでを言い、規約がどこからを担うか。型と文書の外側にある線である。

成果物種別状態何を決めたか
規約は層ではなく、実装を導くもう一つの入力とする決定承認済みWaffle は、規約を仕様の層として扱わない。仕様と規約は同じ格に置き、knowledge だけを共通の出発点として、実装とテストで合流する2つの経路とする。
仕様は実装の型名を持たず、規約が識別子から導く決定承認済みWaffle は、仕様に実装の型名を持たせない。規約が「識別子から型名をどう作るか」を宣言し、ドリフト検査はその規則で綴りを計算して実装と照合する。
仕様の下限を、具体が一意に導けるかで測る決定承認済み仕様をどこまで抽象化してよいか、その下限を次の測り方で決める。読み手が仕様だけを読んで実装の具体を組み立てたとき、その具体が2通り以上に成り立つなら、その仕様は特徴が足りていない。
knowledge は、自分を読む相手を知らない決定承認済みWaffle は、knowledge に読む相手を持たせない。読む側（advisor と Orchestrator）だけが、自分が読む knowledge を宣言する。配置先は、その宣言から導く。
