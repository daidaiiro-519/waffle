# 社内AI人材育成ワークショップ：運営設計案

身近な業務課題を自分で選び、エージェントやSkillsを使って小さな仕組みを作り、他者の利用結果から改善する力を育てる。課題の選択と解法の判断を参加者に委ね、概念教材と継続的な相談で支える。

部長向けの説明は [スライド](director-deck.html)、話す内容は [発表原稿](speaker-notes.md) を参照する。本書は開催条件を詰めるための案であり、以下の提案事項は確定していない。

## 主催者の条件と今回の提案

| 区分 | 内容 |
|---|---|
| 主催者の目的 | 0から1を作る能力と考え方の育成。将来の課題探索や価値創出の土台を作る |
| 主催者の教育方針 | 身近な課題を扱う。概念を中心に教え、具体的な解法を与えすぎない。用途のヒントは紹介できる |
| 主催者の対象条件 | 開発者、PM・PLなど約15名。10月開始、下期を通して実施 |
| 主催者の運営条件 | 固定日の集合は難しい。中間成果物発表を挟む。Teams相談とブログで支援する |
| 主催者のツール条件 | Kiroが主。Claudeは一部利用可能 |
| 主催者の教材構想 | エージェントの利用・作成・可能性を説明する概念スライドと、音声付き動画 |
| 今回の期間提案 | 2026年10月〜2027年3月。終了年は会話時点の暦と「下期」から設定した計画上の解釈 |
| 今回の参加形態提案 | 個人の課題と試作を基本に、3名ずつ5組の相談グループを置く |
| 今回の時間提案 | 参加者は週2時間を業務内に確保。試算上の実働期間は20週 |
| 今回の発表提案 | 12月の中間共有、3月の最終共有を非同期で行う |

## 到達目標と評価

完成品の規模だけでなく、課題設定・AIへの委任・検証・共有の行動を確認する。

| 観点 | 補助が必要な状態 | 自分でできる状態 | 他者にも渡せる状態 |
|---|---|---|---|
| 課題の設定 | テーマはあるが対象者や場面が曖昧 | 困る場面と変えたい状態を説明する | 他者の反応に基づいて課題を絞り直す |
| AIへの委任 | 設定や出力の意味を説明できない | 目的・材料・制約・完了条件を渡し、出力を確認する | エージェントとSkillsの分担を説明し、他者の環境で試せる |
| 検証と改善 | 動いたことだけで判断する | 使用結果から修正点を決める | 新しい入力や利用者でも試し、限界を説明する |
| 共有と再利用 | 本人しか動かせない | 使い方と必要な材料を残す | 別の人が実行し、困った点を改善する |

開始時・中間・終了時に同じ観点を使う。開始時に経験していない項目は「未実施」とし、低評価と同一視しない。本人と主催者が、各段階の記録を見て確認する。修了条件には、全観点で「自分でできる」ことと、少なくとも一人の他者による使用記録を持つことを提案する。未到達の観点は、次に試すことを決めて引き継ぐ。

仕組みの効果は、確認や修正の手間も含めて調べる。同じ種類の作業について、従来と試作利用後の所要時間、誤り、やり直し、利用者の困りごとを記録する。処理件数や入力条件が違う場合は分けて示す。少数の試行から部署全体の削減効果を断定しない。

運営側は参加継続、他者が使えた成果物、相談の停滞を把握する。集計値には対象人数を添え、完成品数だけで育成の成否を決めない。目標値は参加者の開始時点の経験を確認してから設定する。

## テーマの選び方

参加者には幅のある領域を渡す。最初に本人の経験を言葉にしてもらい、下表のヒントは必要になった人へ示す。解決策の完成例や推奨構成は指定しない。

| 対象 | 領域 | 課題を見つけるためのヒント |
|---|---|---|
| 開発者 | 開発プロセスの効率化 | 毎回の確認や引き継ぎで、同じ手間が生まれる場面 |
| 開発者 | Webアプリ作成の始めやすさ | アイデアがあっても、試し始めるまでに時間がかかる場面 |
| 開発者 | オンボーディング | 新しく参加した人が、情報や判断の根拠を探し回る場面 |
| PM・PL | 提案準備 | 資料を作る前に、必要な情報の収集や比較で止まる場面 |
| PM・PL | 関係者調整 | 決定・保留・依頼の認識が、人によって異なる場面 |
| PM・PL | 状況把握 | 進捗を集めても、支援の必要性や依存関係が分からない場面 |
| PM・PL | チームの相談 | 困りごとを言い出す相手やタイミングが分からない場面 |
| 共通 | 知識共有と引き継ぎ | 記録はあるが、次の人が仕事に使えない場面 |

「コミュニケーションを活性化する」は広いため、相談・判断・引き継ぎなどの場面へ絞る。発言数や自動生成した投稿数だけを成果にしない。「メンバー管理」も、個人の自動採点より、仕事の状況と支援の必要性を本人と共有する方向を勧める。

| 課題を絞る問い | 記録する内容 |
|---|---|
| 誰が、いつ困るか | 実際に観察した一つの場面 |
| 何が変われば役に立つか | 対象者が確かめられる変化 |
| 最初に何を試せるか | 小さな入力と一つの動作 |
| 何をまだ知らないか | 未確認事項と、確かめる相手 |

テーマ変更は認める。試した結果と変更理由を残し、規模を小さくすることも前進として扱う。既存のSkillや設定の改良も認め、本人が見つけた課題と変更判断を説明できることを求める。

## 概念教材と操作教材

概念教材は短い音声付きスライド動画に分ける。下表は制作する教材の構成案であり、動画そのものはまだ制作していない。

| 回 | 概念教材の中心 | 図で示す関係 | 視聴後に本人が考えること |
|---|---|---|---|
| 1 | エージェントで仕事を進める | 目的→計画→道具の使用→結果→見直し | 自分の仕事のどこに試行と確認があるか |
| 2 | 人とAIの分担を決める | 任せる範囲と、人が判断する境界 | 何を任せ、何を自分で確かめるか |
| 3 | 必要な情報を渡す | 目的・材料・制約・完了条件と実行結果 | AIに渡っていない情報は何か |
| 4 | 役割に合うエージェントを作る | 役割と、道具・参照情報・権限の関係 | 分ける理由がある仕事は何か |
| 5 | Skillsで仕事の進め方を共有する | 手順・判断基準・参考資料と利用場面 | 繰り返す判断のうち、何を残せるか |
| 6 | 作った仕組みを検証する | 入力→実行→観察→修正→別条件での試行 | どんな結果なら、考えを変えるか |

各動画は8分を目安に制作する案とする。視聴だけで終えず、本人の仕事について一つ考えてメモする。長くなる内容は分割する。

操作教材は、Kiroでファイルや設定を用意し、読み込ませ、実行し、結果を確認するまでの最小構成にする。形式を学ぶための意味の薄い短文などを入力にし、業務改善の完成例を再現する課題にはしない。Agent Skillsとエージェント設定の基本的な書き方は示す。

用途の紹介は、参加者が困る場面を一度書いた後に行う。資料作成・データ分析・可視化・Web画面などの可能性を短く示し、完成テンプレートの配布を必須にしない。試作が始まってから他者の発想を見る機会を増やす。

## 月ごとの進行案

| 月 | 主な活動 | 残すもの | 主催者の関わり |
|---|---|---|---|
| 開始前 | 利用環境の確認、教材の用意 | 開始案内、共通の操作確認、利用ルール | Kiroの社内版で手順を通し、学習時間を上長と確認 |
| 10月 | 概念学習、操作、課題の観察 | 開始時の記録、課題候補、最小操作の結果 | 初回投稿を全員確認し、未着手者を支援 |
| 11月 | 課題の絞り込み、小さな試作 | 動く一部分と初回の試行記録 | 作る範囲を絞る相談、操作の障害への対応 |
| 12月 | 中間成果物発表 | デモ、迷っている点、次に試すこと | 非同期でコメントを返す。完成度の競争にしない |
| 1月 | 方向の修正、Skillsの整理 | 変更理由、使い方の下書き | 手順を固定しすぎていないか確認 |
| 2月 | 他者による利用、改善 | 別の人の使用結果、修正内容 | 本人の口頭補足なしで使えるか確認 |
| 3月 | 最終共有、振り返り | 成果物、変わった判断、今後の扱い | 到達度を確認し、継続・共有・終了を判断 |

## 非同期運営とサポート

| 項目 | 運営案 |
|---|---|
| 個人の活動 | 週2時間に、教材・制作・相談・発表準備を含める |
| 相談グループ | 約15名を3名ずつ5組にする。各人が課題と試行を持つ |
| 進捗投稿 | 隔週。試したこと、分かったこと、次に試すことを短く投稿 |
| Teams相談 | 目的、試したこと、詰まっている箇所、必要な助けを書く。書けない場合も相談可 |
| 主催者の確認 | 週2回を目安にTeamsを確認。回答が難しいものは次に確認する時点を返す |
| 個別支援 | 操作の障害は直接支援。課題や解法の相談には、問いや比較する観点を返す |
| ブログ | よくある疑問を記事化し、概念教材・操作教材・補助記事を索引で探せるようにする |
| 停滞時 | 投稿がない場合は主催者から声をかけ、時間不足・操作・課題の迷いを区別する |
| 繁忙時 | 試す範囲を縮小する。期限調整や再開予定を本人と決め、未参加のまま放置しない |

グループ制作を選ぶ場合も、全員が設定の実行と自分の判断を説明できることを求める。発表者だけが理解している成果物は、個人の到達を示す証拠にしない。

## 中間・最終の成果物発表

| 項目 | 中間共有の案 | 最終共有の案 |
|---|---|---|
| 時期 | 12月 | 3月 |
| 形式 | 1人5分の録画と要点メモ。録画が難しければ動作画面と説明文 | 同じ形式で、他者の利用結果と変更理由を加える |
| 共有期間 | 提出・視聴・コメントの期間を1週間設ける | 同じ方法で非同期に実施 |
| 見る範囲 | グループ内の他2名と、他グループの1名 | 同じ範囲を基本に、再利用したい成果物も確認 |
| 返す内容 | 役立ちそうな場面、疑問、次に確かめてほしいこと | 使えた点、困った点、今後の利用条件 |
| 主催者の対応 | 全員に次の試行につながるコメント | 到達度と、継続・共有・終了の扱いを本人と確認 |

## 最低限の提出物

| 提出物 | 必要な内容 |
|---|---|
| 動く仕組み | エージェント設定やSkillなど、繰り返して利用するための構成。役割分担を説明する |
| 使い方 | 対象者、必要な環境と材料、実行方法、期待する結果、分かっている限界 |
| 試した記録 | 入力条件、結果、他者の反応、直した点とその理由 |

出力はアプリに限らず、分析・文書生成・業務支援などから選べる。エージェントやSkillsは既存の利用・改良も認め、選んだ構成の役割を説明する。両方の新規作成を必須条件にはしない。使うエージェントの数や、生成したファイル数を評価基準にしない。社内で確認されたデータの扱いとツール権限を守り、初回操作には架空データを使う。

## 必要時間と承認前の確認

今回の部長向け説明では、育成方針への合意と業務内の学習時間の確保を相談する。運営担当・利用環境・日程を具体化し、必要な予算の承認はその条件が揃った時点で受ける構成を提案する。

以下は予算検討のための仮定であり、効果の実測値ではない。実働20週は半年間から休暇・繁忙期の余裕を見込んだ試算条件である。

| 対象 | 仮定 | 試算 |
|---|---|---|
| 参加者 | 週2時間 × 実働20週 × 15名 | 延べ600時間。1人40時間 |
| 運営の事前準備 | 概念動画6本を各4時間で構成・収録・確認 | 24時間。動画制作の経験により再見積もり |
| 運営の継続支援 | 週3時間 × 実働20週 | 60時間。Teams、進捗確認、短いブログ記事を含む |
| 運営の成果確認 | 中間・最終それぞれ、1人20分 × 15名 | 10時間。視聴・コメント・記録を含む |
| 運営の合計 | 24＋60＋10 | 94時間。環境整備、日程調整、個別の追加支援は別途見積もる |
| 利用料金 | Kiroの契約・利用枠、Claudeの補助利用 | 未算定。既存契約と追加枠の要否を確認する |

参加者と運営担当を同一人物が兼ねる場合、重複する活動時間を除いて見積もり直す。

| 部長と確認すること | 決める必要がある内容 |
|---|---|
| 育成方針 | 自分で課題を選び、試すことを重視する評価方針 |
| 参加者の時間 | 業務時間内の枠と、各上長との調整 |
| 運営体制 | 主担当、補助担当、教材制作と支援の工数 |
| 利用環境 | Kiroの版・利用枠・権限、社内データの扱い |
| 日程 | 実施年、共有期間、繁忙期との調整 |

## Kiroの確認根拠と教材更新

Kiro公式の [Agent Skills](https://kiro.dev/docs/skills/) と [Creating custom agents](https://kiro.dev/docs/cli/custom-agents/creating/) を2026-09-05に確認した。Skillsの利用と、エージェントに道具や参照情報などを設定する構成を、企画の技術的な前提にしている。

社内のKiro環境はまだ確認していない。開始前に、参加者と同じIDE／CLIの版・権限・契約枠で、作成→読込→実行→結果確認を通す。全員の必須課題をKiroで完了できるようにし、Claudeは任意の補助利用にとどめる。

概念教材と操作教材を分けることで、操作が変わった場合は該当する短い教材を更新する。公開資料の機能説明だけをもって、社内環境でも動くと扱わない。
