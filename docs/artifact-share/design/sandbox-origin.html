artifact-share / 設計の確認

なぜコメントが動かないのか

閲覧画面に付けた1行のヘッダーが、守るはずだった画面自身を締め出しています。仕組みと、直し方と、この構成が最適かどうか。

01いま何が起きているか

閲覧の配信には、持ち込まれたHTMLを閉じ込めるためのヘッダーを付けています。実測した結果がこれです。

$ curl -I https://…/p/j94np6re/
content-security-policy: default-src 'none'; … ; sandbox allow-scripts allow-top-navigation-by-user-activation

$ curl -I https://…/p/j94np6re/content.html
content-security-policy: default-src 'none'; … ; sandbox allow-scripts allow-top-navigation-by-user-activation

2つは別の役割を持つファイルなのに、同じヘッダーが付いています。

/p/{id}/ （閲覧画面）

index.html — こちらが作ったもの

コメント欄を持ち、中身を枠の中で読み込む。閉じ込める側

/p/{id}/content.html

アップロードされたHTML

誰が書いたか分からない。閉じ込められる側

配信の既定の振る舞いが /p/* 全体に掛かるため、両方に同じヘッダーが付く。

02sandbox は「そのページ自身」に掛かる

ここが誤解の出どころです。sandbox と聞くと「枠の中のものを閉じ込める指定」に見えますが、ヘッダーの sandbox は、そのヘッダーが付いて届いたページ自身を閉じ込めます。

<iframe sandbox="…"> は「この枠に入るものを閉じ込めろ」という親から子への指示です。対してCSPの sandbox は「これを受け取ったあなたを閉じ込めろ」というページからブラウザへの指示です。同じ言葉で向きが逆です。

iframe の属性

<iframe sandbox="allow-scripts">

親が、枠に入る子を閉じ込める。親自身は無傷

CSP のヘッダー

content-security-policy: sandbox allow-scripts

ブラウザが、それを受け取ったページ自身を閉じ込める

向きが逆。閲覧画面には後者が付いているため、閉じ込める側が閉じ込められている。

03なぜ「不透明なオリジン」になるのか

閉じ込めるといっても、何をどこまで許すかは札で決まります。私たちが渡している札は2枚です。

渡している札意味
allow-scriptsJavaScriptを動かしてよい
allow-top-navigation-by-user-activation人が押したときだけ、外側ごと移動してよい

渡していない札に allow-same-origin があります。 これが無いと、ブラウザはそのページを「どこの出身でもないもの」として扱います。これが不透明なオリジンです。

札があるとき

allow-same-origin あり

出身 https://…cloudfront.net

同じ出身の相手とは自由にやり取りできる

札が無いとき（いまの状態）

allow-same-origin なし

出身 null

自分の配信元とすら「別人」になる

同じURLから届いていても、ブラウザの中では別人として扱われる。これが要点。

なぜそんな仕組みなのか

持ち込まれたHTMLに出身を与えると、それは配信元と同じ出身になり、同じ出身の資格（Cookieや保管領域）に手が届いてしまいます。allow-same-origin を渡さないのは、まさにそれを防ぐためです。content.html に対しては完全に正しい設定で、閲覧画面にも掛かってしまったことだけが誤りです。

04その結果、何が壊れるか

閲覧画面のコメント機能は、自分の配信元へ2回話しかけます。どちらも「同じ出身どうしの会話」を前提にしています。

// コメントを読む
fetch('/comments-list/' + ARTIFACT_ID)      ← 別人からの要求として遮断

// コメントを書く
fetch('/comments/' + ID + '/…', {method:'PUT'})  ← 同上

閲覧画面（出身 null）

/p/{id}/index.html

別オリジンへの要求として扱われる（CORSの許可が無いので遮断）

コメントの置き場

/comments/… ／ /comments-list/…

さらに、閲覧トークンのCookieは SameSite=Strict で発行しています。不透明なオリジンからの要求にはCookieが添付されませんので、仮に遮断を越えられたとしても、閲覧ゲートは「トークンなし」と判定します。

できるはずのこといまの状態
コメントを読むできない
コメントを書くできない
閲覧トークンのCookieが送られる送られない
中身を枠の中に表示するできる

05なぜ通し確認で気づけなかったか

実環境の確認は curl で行いました。curl はCSPを解釈しません。 オリジンという概念を持たず、指示されたCookieをそのまま送ります。

curl

ヘッダーを受け取るが、従わない

コメントの読み書きは成功する

ブラウザ

ヘッダーに従う

コメントの読み書きは遮断される

同じ操作で結果が逆になる。この不具合は、道具を替えない限り永久に見つからない。

06直し方

ヘッダーを掛ける範囲を、持ち込まれたHTMLだけに絞ります。配信の口に経路を1本足すだけで、保管の形も、公開の処理も変えません。

経路付けるヘッダー理由
/p/*/content.html sandbox あり 持ち込まれたHTML。閉じ込める対象
/p/*（それ以外） sandbox なし こちらが作った閲覧画面。閉じ込める側
/comments/* ・ /comments-list/* sandbox なし コメントの読み書き。ページですらない

より具体的な経路が先に評価される。content.html だけが閉じ込められ、他は元に戻る。

隔離は弱くなるのか

なりません。 持ち込まれたHTMLは、いま2重に閉じ込められています。

1枚目 — 枠の属性

<iframe sandbox="allow-scripts allow-top-navigation-by-user-activation">

閲覧画面が枠に付けている。変更なし

2枚目 — ヘッダー

content-security-policy: … sandbox …

配信が content.html に付ける。これも残す

2枚とも content.html に対して効いたまま。減るのは、閲覧画面に誤って掛かっていた分だけ。

07これが最適な構成か

「持ち込まれたHTMLを、こちらの資格に触れさせずに表示する」という要件に対して、取りうる形は3つあります。

形隔離の強さ費用・複雑さ評価
別ドメインに置く
中身専用のドメインを取る		 最も強い 独自ドメインと証明書が要る 要件に反する
「AWSアカウントさえあれば完結」できなくなる
枠＋ヘッダーの2重
いまの形（範囲を直したもの）		 十分 追加費用ゼロ これを採る
枠の属性だけ
ヘッダーを付けない		 1枚のみ 追加費用ゼロ 枠の指定を1行落としただけで隔離が消える
結論

構成は最適です。掛ける範囲だけが誤っていました。 別ドメインはこの製品の要件（AWSアカウントさえあれば完結する）と両立せず、ヘッダー無しは二重化を捨てることになります。いまの形のまま、範囲を content.html に絞るのが正解です。

08この見落としが教えていること

この不具合には、直し方より重い教訓があります。

  1. curlでの通し確認は「通った」の証拠にならない。 ブラウザが従う決まりを、curlは一切見ません。画面の振る舞いは画面で確かめるほかありません。
  2. 安全のための設定ほど、範囲を間違えても静かに壊れる。 権限を絞りすぎた側の失敗は、エラーではなく「なぜか動かない」として現れます。
  3. 「同じ配信だから同じ設定でよい」は成り立たない。 同じ /p/ の下に、信頼するものと信頼しないものが同居していました。信頼の境界は、URLの形とは別に引かれます。
