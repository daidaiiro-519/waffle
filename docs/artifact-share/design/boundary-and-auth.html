境界と権限の設計

アーティファクトシェアの「見るのは不特定多数、上げるのは限られた人」という非対称な境界を、どう実装するか。AWSアカウントさえあれば動くOSSという制約のもとで、認証基盤・ティア・オリジン分離の3点を決めるまでの整理。

01前提の転換

当初は「ローカルの管理コンソールをクラウドへ移設したい」という枠で検討していたが、実際の要件は違った。手元で作ったHTML（AIに生成させたもの等）を、リポジトリやCLI環境なしでその場で上げてURLをもらいたい——これがブレストで既に合意していた「テンプレートを経由しない持ち込みHTML」の実現に必要な経路だった。

この転換により、当初「複数アクターが存在しないためアクセス制御は時期尚早」とされていた判定が覆った。公開エンドポイントがインターネットから到達可能になる以上、もう一方のアクターは「インターネット全体」であり、アクセス制御は先回りではなく必要条件になる。

検討の途中で判明した重要な事実

書き込みの実体はS3のPutObjectとCloudFront KeyValueStoreのPutKeyであり、これらは既にIAMで完全に保護されている。「公開できるのはIAM権限を持つ者だけ」という要件は、新しい認可レイヤーを作らなくても既に成立していた。要件が本当に求めていたのは認可の追加ではなく、ローカル環境なしにその実行環境へ到達する手段だった。

また、当初「社内利用」を例として話していたが、実際はAWSアカウントさえあれば完結するOSSであり、特定企業の従業員向けではない。この点が後述の認証基盤の選定を決定づけた。

023つのアクター

境界を定義する側

デプロイする責任者

AWSアカウントの管理者権限を持ち、CloudFormationでスタックを作成・削除でき、IAMポリシーも自分で定義できる。この層には新しい認可の仕組みが一切不要——既存のIAMがそのまま効く。構築は1回きりなので、この層のUXは最適化対象ではない。

認証あり（招待制）

アップロードする人

責任者とは別人。責任者が招待した人だけが認証を通り、アップロードできる。プロジェクトへの所属指定・コメント・エクスポート・データの永続化といった機能が使える。

認証なし（トークンのみ）

閲覧する人

不特定多数。slug単位のトークンを持っていれば誰でも見られ、コメントを投稿できる。アカウント登録は不要——この気軽さが中核の価値であり、変更しない。

03ティア設計

当初は「認証なしでもアップロードでき、揮発する無料枠」という2ティア案を検討した。フリーミアムの発想として筋は通るが、匿名の閲覧と匿名のアップロードはリスクの質がまったく違うという問題があった。

匿名アップロードが抱える3つのリスク

コストが青天井——誰が上げたか特定できないため利用者ごとの制限がかけられず、スクリプトで叩かれればS3とCloudFrontの費用がデプロイ者の請求に乗る。ドメインがフィッシングの配信元になる——攻撃者にとって「無料で使える、TLS証明書付きの、信頼されたホスティング」であり、ブロックリストに載れば正規利用者も巻き添えになる。後述のオリジン問題が事故から攻撃に変わる——悪意ある第三者が意図的に仕掛けられるようになる。

次にセルフサインアップ（メール確認だけで誰でも登録可）を検討したが、これは問題を消さず、検知できるようにするだけだった。捨てメールで登録して1回フィッシングを置いて去る経路が残る。属性付けは抑止であって防止ではない。

結論として招待制を採る。デプロイした責任者が一人ずつ明示的に承認するため、信頼が帯域外で確立される。これは重要で——セキュリティ分析全体が前提にしていた「アップロード者は信頼できる」という仮定を、招待制は実際に成り立たせる。匿名／セルフサインアップで壊れていた前提が回復し、リスクの質が「攻撃」から「事故（信頼できる人が精査せずAI生成HTMLを上げる）」へ戻る。

機能の割り当て

閲覧者（認証なし）アップロード者（招待制）
アーティファクトの閲覧できる（トークン必要）できる
コメント投稿できる（アカウント不要）できる
アップロード・URL発行できないできる
プロジェクトへの所属指定できないできる
エクスポートできないできる
データの永続化—される

なお「無料ティアは揮発する・機能制限あり」という体験自体は、招待制の中でティアを設ける形でも実現できる。匿名書き込みを許すこととは独立した設計。

04認証基盤の選定

CognitoとIAM Identity Center（IIC）のどちらを使うかは、AWSへの書き込みを誰が実行するかで決まる。ブラウザが直接S3へ書くならSigV4署名のための一時AWS認証情報が要り、それを発行できるのはCognito Identity Pool。裏側のLambdaが書くならブラウザは身元を証明するだけでよく、認証基盤の選択肢が広がる。

OSSであることが決め手になった

当初は「社内の従業員を管理するならIICが本来の用途」と考えたが、これは「社内利用」という誤った前提に立っていた。実際はAWSアカウントを持つ誰もがデプロイするOSSであり、デプロイのハードルを上げたくないという制約がある。

CognitoIAM Identity Center
デプロイ時のハードルCloudFormationテンプレートに含められる。追加手順ゼロ有効化・ユーザー登録・アプリ割り当てを利用者が事前に実施
性格アプリが自前でユーザーを持つ。自己完結を求めるOSSに合うアカウントレベルの事前設定。アプリのデプロイに含められない
利用者管理招待制なら管理者が数人を招待する規模。SCIM同期のような仕組みは不要外部IdP連携なら自動同期できるが、そもそも外部IdPがある前提
拡張余地外部のSAML/OIDC IdPをフェデレーション先にできる。社内で使いたい人はIICやEntra IDを繋げばよい—

Cognitoを採る。既定は自己完結（招待制・セルフサインアップ無効）、必要な人だけ外部IdPを繋げばよい、という形がOSSとして素直。IICはアカウントレベルの事前設定を強いる点が、低ハードルという方針と衝突する（AWS Organizationsは必須ではなくスタンドアロンアカウントでもアカウントインスタンスとして有効化できるが、事前設定であること自体は変わらない）。

任意オプション：IP制限

CloudFront Functionsのイベントにはevent.viewer.ipが含まれるため、既存のedge-gate.jsと同じ仕組み（KVSに許可IPリストを置いて照合）で追加コストゼロで実装できる。WAFを持ち込むと月額の固定費が発生するが、その必要はない。使わないなら空のままでよい。

05オリジン分離

オリジンとはスキーム＋ホスト名＋ポートの組み合わせで、ブラウザのセキュリティの単位。同じオリジンのページ同士は「同じサイトの一部」とみなされ、互いのデータへのアクセスが許される。

現状：すべて同一オリジン

https://d123abc.cloudfront.net/p/aaa/  ← Aさんのアーティファクト
https://d123abc.cloudfront.net/p/bbb/  ← Bさんのアーティファクト
https://d123abc.cloudfront.net/gallery/  ← ギャラリー
https://d123abc.cloudfront.net/  ← トークン入力画面

パスが違うだけではブラウザは別サイトと見なさない。

「トークンを知らなければ見られないのでは？」への答え

攻撃者はトークンを知る必要がない

条件は「攻撃者がトークンを知っているか」ではなく「被害者がトークンを持っているか」。攻撃者は被害者が既に持っているアクセス権を踏み台にする。

1. 悪意ある（または精査されていない）HTMLが /p/evil/ に置かれる

2. 被害者がそれを開く

このとき被害者のブラウザには、過去に開いた他のアーティファクトのCookie（share_xxx）が既に入っている

3. ページ内のJSが fetch('/p/xxx/') を実行する

4. 同一オリジンなのでブラウザがCookieを自動的に付ける

edge-gateから見れば正当なアクセスなので通る

5. JSが中身を読んで外部へ送信する

影響範囲はその閲覧者がアクセスできるアーティファクト数に比例する。特にギャラリーの共通トークン（share_gallery）を持つ閲覧者が踏むと、Cookie1つで全アーティファクトが読める

Cookieが1つも無い場合でも、偽のトークン入力画面は出せる。正規ドメイン・正規TLS証明書のページなので見分けはつかない。なおCookieにはHttpOnlyが付いているためdocument.cookieからの直接読み出しは防げている——これは既存設計の美点だが、同一オリジンのfetch()にCookieが自動付与される経路は防げない。

採る構成：認証面と閲覧面を分ける

ディストリビューションA — 認証が要る面

https://dAAA.cloudfront.net/  ← アップロードUI（Cognito認証）
https://dAAA.cloudfront.net/...  ← Cognitoのコールバック等

ディストリビューションB — トークンで見る面

https://dBBB.cloudfront.net/p/{slug}/  ← アーティファクト本体
https://dBBB.cloudfront.net/comments/{slug}/  ← コメント投稿
https://dBBB.cloudfront.net/comments-list/{slug}  ← コメント一覧
https://dBBB.cloudfront.net/gallery/, /proj/  ← ギャラリー

ギャラリーとコメントをB側に置くのが要点。ギャラリーの共通トークンCookieはedge-gateが読む必要があり、Cookieはホスト単位でスコープされるためアーティファクトと同一オリジンでなければ機能しない。コメントも同一オリジンに置くことで、既存の template-pattern-page.html のfetch処理を一切変えずに済む。edge-gate.js はほぼそのままB側に載る。

この構成で守れるもの・守れないもの

守れる：Cognitoでログイン中のアップロードUIが、悪意ある（あるいは精査されていない）アーティファクトのJSから隔離される。同一オリジンだと、そのJSがログイン中の権限でアップロードAPIを叩けてしまう——これが最も重要な保護対象。

守れない：アーティファクト同士の踏み台攻撃。/p/aaa/ と /p/bbb/ は同じホスト名にあるため、前述の経路は残る。これを消すにはslugごとに別ホスト名（{slug}.artifacts.example.com）が必要で、独自ドメイン＋ワイルドカード証明書が要る。

アーティファクト同士の分離は独自ドメインを持つ人向けの任意オプションとして設計に余地だけ残す。招待制により信頼が担保されるため、残るリスクは「事故」の水準に収まる。

懸念だった2点は、どちらも解消した

懸念調べた結果
独自ドメインとACM証明書が要るのでは（OSSの低ハードル方針と衝突）cloudfront.netはPublic Suffix Listに登録されているため、d123abc.cloudfront.netとd456def.cloudfront.netはブラウザから別サイトとして扱われ、Cookieは共有されない。独自ドメインもACM証明書も不要
ディストリビューションを増やすとコストが上がるのではCloudFrontは従量課金（リクエスト数＋転送量）が基本で、ディストリビューション数そのものへの課金ではない。2つに分けても同じトラフィックなら合計はほぼ変わらない（トラフィックが分かれるだけ）。※2025年11月開始の定額プランは1プラン＝1ディストリビューションのため、定額を選ぶ場合は本数が効く。無料プランはアカウントあたり3つまで

今しか入れられない

ホスト名が変わるということは発行済みの共有URLが全部変わるということ。後から分離すると既に配ったURLは全て死ぬ。スタックを作り直す今が唯一の機会であり、この項目だけは「実例が出るまで作らない」という規律の対象外になる。

06アップロードとmeta

実装方式：Lambda経由（裏側が書く）

ブラウザが直接S3へ書く方式（Cognito Identity Poolで一時AWS認証情報を取得しSigV4署名）ではなく、裏側のLambdaが自分の実行ロールで書く方式を採る。理由は3つ。

  • 契約検証・slug発行・トークン生成・予約名前空間チェックを必ず通る関門に置ける。ブラウザ直書きだとこれらを挟む場所が構造的に存在しない
  • Identity Poolが不要。Cognito User Poolだけで済み、部品が1つ減る（ブラウザはJWTを持つだけでAWS認証情報を持たない）
  • S3にCORS設定を追加せずに済む。現行テンプレートは意図的にCORSを持たない設計で、その方針を崩さない

注意：Lambda経由はペイロードサイズに上限がある（API Gateway経由で10MB、Lambda同期呼び出しで6MB程度）。実測ではアーティファクト1件が約200KBのため通常は問題ないが、大きなものを想定するなら「Lambdaが署名付きURLを発行してブラウザが直接S3へ上げ、S3イベントで検証・公開する」二段構えへ移行する。まずは上限付きの直接方式で始める。

UI：ドラッグ＆ドロップ

ドロップ →（表示名の入力）→ アップロード → URLとトークンが1度だけ表示される、という流れ。トークンを平文保存しない既存の原則があるため、その場でコピーしてもらう。「AIに作らせたHTMLをブラウザにドロップしたらURLが返ってくる」という体験が、CLIを使わない利用者にとっての価値そのものになる。

2種類のHTMLをどう見分けるか

アップロードされるHTMLには、既定4テンプレート等で作られたものと、それ以外のツールで作られた野良HTMLの2種類がある。ただし「どのツールが作ったか」と「どの経路で入ってきたか」は直交する——テンプレートで作ったADRをローカルに持っていて、それをUIにドロップすることもあり得る。

システムが振る舞いを変える基準

「どのツールが作ったか」ではなく「HTMLからメタデータを取り出せるか否か」で判定する。既定4テンプレートは <head> にdocument-graph契約のmetaタグ（id/type/title/description/tags）を持つため、アップロード時にパースすれば自動で埋まる。ユーザーに「これは野良ですか？」と聞く必要はない——見れば分かる。

metaタグあり（テンプレート製）metaタグなし（野良）
ユーザーへの質問ゼロ（表示名もtitleから取れる）表示名だけ1つ
任意入力—説明・タグを折りたたみで（省略可）
docTypemetaタグの値をそのまま格納空

副次的な利点：metaタグの有無は「そのHTMLが契約を意識して作られたか」の指標にもなる。持たない野良HTMLはCSPや予約名前空間チェックで弾かれる可能性が相対的に高いため、アップロード時に「このHTMLは外部リソースを参照しています」と警告を出す、といった親切をここに乗せられる。

metaスキーマ

フィールド内容
slug / name / status / updatedAtスラッグ・表示名・active/disabled・更新時刻既存
projects所属するプロジェクトIDの配列（タグ式・複数所属可）既存
sourceFile / sourceHashローカルソースの識別とSHA-256（同期判定用）既存
metaSourceextracted（タグから取れた） / manual（手入力）追加
docTypemetaタグのtype値をそのまま格納。プラットフォームは等価比較しかせず意味を解釈しない追加
docId / description / tagsdocument-graph契約のmetaタグ由来追加
uploadedByCognitoのsub。誰が上げたかの帰属（招待制の実効性・濫用時の追跡）追加
wrapperHash配信ラッパーの版。これが無いとコメントUIを修正しても既存slugへ届いたか判定できない追加

docTypeを不透明なラベルとして持つのが要点。DecisionRecordでもPostmortemでも、design-shareが将来独自の値を入れても、プラットフォーム側は意味を解釈しない。これで「親は子の文書種別を知らない」という依存方向が保てる。野良HTMLはdocTypeが空、というだけの扱いになる。既存の type（mock/design-review）はこのdocTypeへ吸収する。

ギャラリー・プロジェクト・タグの区別

既存実装には性格の異なる3つの概念がある。混同すると権限設計を誤るため、役割を明確に分ける。

数誰が決めるか何を制御するか
共有ギャラリー1つだけ—（公開すれば自動的に載る）公開中の全アーティファクトを単一の共通トークンで横断閲覧させる入口。個別に「追加」する操作は存在しない
プロジェクト
（projects）		複数人の明示的な操作（アップロード時に選択、またはCLI/管理画面）アクセススコープ。そのプロジェクトのトークンで、入れたアーティファクトだけが開ける。ローカルにも作業フォルダを持つ
タグ
（tags）		自由アップロードした人（HTML内のmetaタグに記述）絞り込み・分類のみ。既にアクセスできる範囲の中での探しやすさ

タグにアクセス権を持たせない

tagsの出どころはアップロードされたHTMLの中身であり、ユーザーが自由に書ける値。もしタグがプロジェクト所属＝アクセススコープを決めるなら、metaタグを1行書き換えるだけで、自分のアーティファクトを他人のプロジェクトのトークンで見える場所に紛れ込ませられる。これは権限昇格になる。所属は必ず人の明示的な操作で決まる。

タグは「見える範囲を広げる」ことはできず、「見える範囲の中を整理する」ためのもの。この線を守れば、タグを自由なカテゴリとして使える。副次的に、タグがHTMLに埋まっているのでre-uploadすると自動で更新される——管理画面で付け直す必要がない。これはdocument-graph Skillの契約とも一致する（あちらもタグを分類情報として扱い、アクセス制御には使っていない）。
